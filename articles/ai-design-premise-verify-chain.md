## はじめに

少し前に [AI 多層防御を通り抜けた重大インシデント未遂 — verify 経路の真正性と人間の批判的圧力](https://zenn.dev/fixu/articles/ai-multi-agent-verify-authenticity) という記事を書きました。AI multi-agent + Copilot レビューの座組がコードレベルで機能しても、verify が「広い権限経路で bypass されている」という構造的な blindspot は残る、という話でした。

あれから同じ運用で別機能の設計タスクを AI に任せたところ、最終的に **誤前提が 17 連鎖する catch chain** が積み上がりました。起点は、全環境に存在しない DB テーブル名を前提にした設計書が上流から下流まで 4 層通り抜けたこと。さらにその真の root は **設計書中の typo 1 文字** にありました。

一連の catch chain を経て得た最大の手触りを先に書いてしまうと、

> **AI は user の入力を verbatim 信頼する default を持つ。catch chain が連鎖するときは、AI だけでなく user input 自体も疑うべき信号だった。**

この記事は、17 連鎖 catch chain の構造と、それを業務設計として断つ 8 件の具体策を書き残すものです。

---

## 1. 前作からの差分 — verify の何が抜けていたか

| 観点 | 前作 (verify 経路の真正性) | 今回 (verify 対象の実在性 + user input の真正性) |
|---|---|---|
| 抜けていた問い | その verify は **どの権限経路** で通したか? | その前提となる entity は **実在するか**? その input は **typo でないか**? |
| 通った成果物 | `aws s3 ls` → 1099 件 list 成功 → ✅ PASS | 設計書に書かれたテーブル名 → 「これで進める」承認 |
| 実態 | サブの広い権限で通り、実 app 経路では 404 | そのテーブルは全環境に存在しない。しかも設計書の起点は **typo** だった |
| 構造的盲点 | 同じ model 系列の AI は path authenticity を問わない | 同じ model 系列の AI は entity authenticity も user input の typo も問わない |
| 人間の検出契機 | 「もっと踏み込んだ verify できそう?」の追加要請 | 「これ、既存のカラムで足りるのでは?」「これ typo です」の 2 段 catch |

前作は「verify の **どう走らせるか**」、今回は「verify の **そもそも走っているか** + **前提自体が正しいか**」の話です。対策する層が一段手前になります。

## 2. 何が起きたか — 17 連鎖 catch chain

### 2-1. 最初の 4 層: 存在しないテーブル名が verbatim 引き継がれた

ある機能拡張の設計タスクで、AI が DB 設計書に「`<あるテーブル名>` の workflow を多拠点対応に拡張する」と書きました。そのテーブル名は、全環境のどの DB にも存在しないものでした。

| 層 | 主体 | なぜ通したか |
|---|---|---|
| 1. 上流設計書 | 親エージェントが DB 設計書を起こす段階 | 「自社 DB だから知っているはず」default で実機 verify なし |
| 2. 中流引き継ぎ doc | サブセッション用 input を作成する段階 | 「上流 doc = 確定情報」default で再 verify なし |
| 3. 下流サブ kickoff | 着手前の強制チェック段階 | 「公式 doc 一次情報 verify」を外部 API に適用したが、自社 DB schema は射程外と暗黙解釈 |
| 4. 完遂 review | 設計成果物を承認する段階 | review 軸に「設計前提の entity 実在性」が含まれていなかった |

検出は設計レビュー担当者 (人間) の「これ、過去の機能拡張時に既に追加されたカラムで足りるのでは?」という素朴な疑問から始まりました。

> 「呆れるを通り越して笑うしかないですね。私のレビューがあってよかった。」

### 2-2. v5-v9: memory 化・protocol 追加後も連鎖は続いた

最初の catch を受けて memory 化・protocol 追加を行いましたが、catch は積み上がりました:

- **v5**: DDL の implicit commit を知らず、本番 DB でのトランザクションロールバック不可を見落とした
- **v6**: ログ確認経路を問われ「CloudWatch 経由」と即答したが、実際の経路は別系統だった
- **v7**: 実行ログの確認で本番 DB の実データを混入させる手順を提案してしまった
- **v8**: API エンドポイント名を複数形で設計したが、実際のプロジェクト規約は単数形だった
- **v9**: 「Copilot review は自動起動される」という誤前提で運用していた

いずれも根本は同じ — **「知っているはず」 default と、実機 verify を skip する pattern** です。

### 2-3. v10-v17: 真の root はまだ下にあった

memory 化しても protocol 化しても catch は続きました:

- **v10**: memory に「確立済みの手順」があるのに、それを verify せず自前の手順を実装
- **v11**: 別リポジトリとの同一 namespace に 218 ファイル衝突が発覚 (後に「真の root は別」と判明)
- **v12**: 「DRY = 常に正しい」という暗黙前提が、「リポジトリ複製 OK」というユーザー方針と衝突
- **v13**: 「コンポーネント B で完結する」という業務原則を見落とし、別リポジトリ依存の設計を提案
- **v14**: autonomous mode で「silent = 何もしなくていい」と誤解し、進捗を一切報告しなかった
- **v15**: 218 ファイル衝突を「問題あり」と見なしたが、ユーザーの認識は「ハードコピー由来で当然」
- **v16**: 別リポジトリへの issue/branch/commit を当然のように計画した (アクセス範囲制約を確認せずに)
- **v17**: 設計変更でスコープが縮小したのに「タスク起票済 = scope 残存」と暗黙仮定してテスト更新を提案

### 2-4. v18: 真の root は typo 1 文字だった

v18 で判明したのが最大の catch です。設計書の上流にあったコンポーネント名の記述に **typo** があり、1 文字誤っていました。AI はその typo を verbatim 信頼し、サブへの引き継ぎ doc にもそのまま流用した。

**v11-v17 の 7 件以上の catch chain の真の root は、この typo 1 文字でした。**

その後、設計レビュー担当者自身が typo に気づき、v11-v17 の連鎖の真の root がここにあったことが判明しました。AI は「違和感はあったが、ユーザーが書いた設計書だから正しいはず」と判断し、確認を先送りにしていた箇所でした。**catch chain が連鎖するときは、前提に typo がある signal かもしれない。**

### 2-5. v19-v20: 設計方針と戦略 timing の差

- **v19**: 「法人機能の親子カラム (既存資産)」と「多拠点機能の親子 entity (別概念)」を混同して設計した。業務概念の分離 verify が不足していた
- **v20**: AI は「影響範囲を最小化する保守的判断」を推奨したが、ユーザーは「破壊的変更を加えられる最後の timing を逃したくない」という戦略的判断で即断した

## 3. なぜ起きたか — AI の humility 欠如と「verify したかどうか」の区別不足

### 3-1. 「自社の code / DB は知っているはず」 default

LLM は大量のコンテキスト (会話履歴 / memory / 過去成果物) を抱えた状態で動きます。特に自社の codebase / DB に対しては、外部 API 以上に「知っているはず」 default が強く働きます。

しかし、過去会話 / memory / 設計書はすべて「誰かが verify したかどうか不明な情報」です。それらの合成は「推測の合成」であって、現時点での実機 fact ではない。ここの区別が default では曖昧になります。

### 3-2. user input も「検証対象」である (v18 追加教訓)

AI は user input を verbatim 信頼する default を持ちます。設計書に書かれた文字列が typo であっても、「ユーザーが書いた = 正しい」default で処理します。

**catch chain が連鎖するとき、それは「前提に typo がある」という signal でもあります。** 違和感があれば確認する閾値を下げる、というのが今回得た新しい教訓です。

### 3-3. memory 化しても再違反は起きる

protocol を memory に書いても、それを verify せずに別の手順を実装してしまう (= v10) ことがあります。「memory に書かれている = 自動的に守られる」ではない。自分が memory にある手順を**今この瞬間参照しているか**を意識的に確認する必要があります。

### 3-4. 同じ model 系列は同じ blindspot を共有する

前作で書いた構造原則ですが、今回も全く同じことが起きました。**独立性は「セッション分割」ではなく「観点の埋め込み」で稼ぐ必要があります。** サードパーティ (Copilot 等) が新しい観点で入ってくるまで、同系列 AI は同じ盲点を共有し続けます。

## 4. 順守すべき 8 件 — kickoff の ritual に組み込む

元の 5 件に、v10-v20 で得た 3 件を追加しました。

### 4-1. 設計対象 entity の全件実機 verify
設計に登場する全 entity (テーブル / カラム / クラス / エンドポイント / ファイルパス) は kickoff 着手前に実機 verify します。テーブル名は `SHOW TABLES` + `DESCRIBE`、クラスは `grep` / `find`、エンドポイントは routes ファイルで実在確認。**自社 DB / コードに対しても「外部 API と同じ厳しさ」を適用する。**

### 4-2. 過去軸 Pre-mortem
「この設計の前提が、今すでに間違っていたら何が起きるか?」を 1 件以上立てる。未来軸だけでなく、**現在すでに前提が崩れている可能性を kickoff で問う。**

### 4-3. 「設計書 = 仮説」 default の徹底
上流 doc / 前サブ成果物 / 過去会話は全部仮説扱いとし、実機 verify で fact 化されるまで信頼しない。kickoff 冒頭の ritual に「上流 doc の entity 名を全件抽出 → 実機 verify」を強制で入れる。

### 4-4. 「素朴な疑問 1 件」の強制発信
kickoff の最後に「人間に確認すべき素朴な疑問を 1 件」AI 側から強制発信する。AI が持たない文脈 (5 年運用の業務知見、legacy 設計の意図) は人間に依存しないと埋まらない。

### 4-5. AI humility default 仮説
「自社 codebase / DB について、AI である自分は何も知らない」を default 仮説として宣言する。context + memory + 過去会話の合成は「推測の合成」であり、実機 verify ベースの fact ではない。

### 4-6. typo verify — catch chain 連鎖時は user input を疑う (v18 由来・新)
catch chain が連鎖するとき、それは「前提に typo がある」信号かもしれない。**違和感を感じたら user input を確認する閾値を意識的に下げる。** AI が「ユーザーが書いた = 正しいはず」と verbatim 信頼する前に一歩立ち止まる。

### 4-7. 3 層 review を構造化する (v8/v11 由来・新)
人間 review + AI self review だけでなく、**サードパーティ (Copilot 等) を構造的に含める。** 同系列 AI は同じ blindspot を共有するため、異なる観点を持つレビュアーが入ることで初めて発見できる catch がある。

### 4-8. memory 化は「起点」であり「終点」ではない (v10 由来・新)
protocol を memory に書いた後も、「その memory を今参照しているか」を意識的に確認する habit を組み込む。**「memory 化 = 自動的に守られる」ではない。**

## 5. メタ教訓 — 17 連鎖が明らかにした構造原則

### catch chain は「多層 + 多軸」で重なる
今回の 17 件は、既存資産 verify / base knowledge / 設計方針 / 暗黙期待 / repo 範囲 / user input と、**複数軸にわたっていました。** 1 件 catch しても、別軸に新たな暗黙前提が残存し続けます。

### 「丁寧の罠」
AI が「より丁寧に進めようとした行為」自体が新たな違反を生む場面がありました (本番データを混入させないよう丁寧に確認しようとした結果、実データへのアクセスを提案してしまった等)。**丁寧さのベクトルが設計原則とずれると、意図しない侵害が起きます。**

### AI の保守判断 vs 人間の戦略 timing 判断
AI は「影響範囲を最小化する保守的判断」に傾きます。しかし人間は「今しかできない破壊的変更の timing」という戦略的判断を持つことがある。**timing の判断を AI に委ねると、戦略的なチャンスを逃すリスクがあります。**

## 6. まとめ — 双方の reflection と、AI agent 運用への希望

前作と今回で見えてきた構造はほぼ同じです。

| 層 | 何が抜けるか | 対策 |
|---|---|---|
| 実装 verify (前作) | 権限経路の真正性 | path authenticity チェックリスト |
| 設計 kickoff (今回前半) | 対象 entity の実在性 | entity authenticity 実機 verify ritual |
| user input verify (今回 v18) | typo / 前提ミス | catch chain 連鎖時に user input を疑う閾値設定 |

どちらも「AI multi-layer は通り抜ける」「同じ model 系列に同じ blindspot がある」「人間の批判的圧力を構造に組み込む必要がある」という結論に着地します。

今回の最後に残ったのは、v18 でのやりとりでした。

> 「あー！ごめんなさい。人間側の重大なミスに気づきました。真摯に謝罪します。この記述を AI が解釈してここまでの方針がすれ違っていたということをようやく私が理解できました。これは typo です」

そして:

> 「私の typo も要因の一つなのでお互い反省ですね」

17 連鎖の catch chain を経て、AI と人間が互いの誤りを認め合った瞬間でした。**AI agent との協働は、互いの humility と反省のやり取りの中で成熟していく** のだと思っています。

「自分のところはこう組んでいる」「ここはこう設計した方がいい」という知見があれば、コメントでぜひ教えてください。AI agent の humility をどう構造的に補うかは、業界全体で型が固まっていない領域なので、外部知見を取り込みたいというのが本音です。
