## はじめに

少し前に [AI 多層防御を通り抜けた重大インシデント未遂 — verify 経路の真正性と人間の批判的圧力](https://zenn.dev/fixu/articles/ai-multi-agent-verify-authenticity) という記事を書きました。AI multi-agent + Copilot レビューの座組がコードレベルで機能しても、verify が「広い権限経路で bypass されている」という構造的な blindspot は残る、という話でした。

あれから 1 ヶ月ほど、同じ運用で別機能の設計タスクを AI に任せたところ、今度はそれとは別軸の重大誤前提が見つかりました。**全環境に存在しない DB テーブル名を前提にした設計書が、上流から下流まで 4 層通り抜けていた** という事案です。

前作は「verify は通った、ただし権限経路が広すぎた (= path authenticity)」問題でした。今回は **「そもそも verify されていないものを、verify したかのように引き継いだ」(= entity authenticity)** 問題で、層は同じく 4 つ通過しています。

この記事は、

- AI に設計を任せた際に、上流の前提を verbatim で引き継ぐ chain が組まれること
- その chain は誰も「実機で確認したか?」を問わずに何層も通過すること
- 通したのは AI の humility 欠如 (= 「自分は知らない」 default を持たない性質) であること
- これを kickoff の強制 ritual で塞ぐ 5 つの具体策

を書き残すものです。冒頭で結論めいたことを書いてしまうと、

> **AI に設計を任せると、上流の前提を疑わずに verbatim 引き継ぐ chain が組まれる。「verify したか / verify していないか」を kickoff の冒頭で意識的に区別させる ritual がないと、誤前提は 4 層通り抜ける。**

これが今回得た最大の手触りです。

---

## 1. 前作からの差分 — verify の何が抜けていたか

前作の続編なので、まず構造的な差分を可視化します。

| 観点 | 前作 (verify 経路の真正性) | 今回 (verify 対象の実在性) |
|---|---|---|
| 抜けていた問い | その verify は **どの権限経路** で通したか? | その前提となる entity は **実在するか**? |
| 通った成果物 | `aws s3 ls` → 1099 件 list 成功 → ✅ PASS | 設計書に書かれたテーブル名 → 「これで進める」承認 |
| 実態 | サブの広い権限で通り、実 app 経路では 404 | そのテーブルは **全環境に存在しない** 名前だった |
| 構造的盲点 | 同じ model 系列の AI は path authenticity を問わない | 同じ model 系列の AI は entity authenticity を問わない |
| 人間の検出契機 | 「もっと踏み込んだ verify できそう?」の追加要請 | 設計レビュー担当者の「これ、既存のあのカラムで足りるのでは?」指摘 |

前作は「verify は走っているが、走らせ方が緩い」問題でした。今回は **「verify が走っていない設計仕様を、走ったかのように引き継いでいる」** 問題です。前者は実行段階の話、後者は kickoff/設計段階の話で、対策する層が一段手前になります。

> **前作との差分**: 前作は verify の **どう走らせるか**、今回は verify の **そもそも走っているか** の話。

## 2. 何が起きたか — 4 層が同じ誤前提を verbatim 引き継いだ

具体的に書きます (社内固有名は抽象化します)。

ある機能拡張の設計タスクで、上流の要件定義が確定し、それを基に AI が DB 設計書を起こしました。設計書には「`<あるテーブル名>` の workflow を多拠点対応に拡張する」という骨子が書かれていました。

このテーブル名、**全環境のどの DB にも存在しないものでした**。実機で `SHOW TABLES` も `DESCRIBE` もかけずに、過去会話と memory の合成から「たぶんこの名前だろう」という推測で書かれた名前です。

そして、この設計書は以下の 4 層を verbatim で通過しました。

| 層 | 主体 | 何をしたか | なぜ通したか |
|---|---|---|---|
| 1. 上流設計書 | 親エージェントが要件確定後に DB 設計書を起こす段階 | テーブル名を推測流用で記載 (`DESCRIBE` / `SHOW TABLES` verify なし) | 「自社 DB だから知っているはず」default で、実機確認を skip |
| 2. 中流引き継ぎ doc | 設計書を基にサブセッション用の input pre-load を作成する段階 | 上流の設計書を verbatim で引き継ぎ | 「上流 doc は確定情報」 default で、再 verify せず |
| 3. 下流サブの kickoff | サブセッションが設計タスクに着手する直前の強制チェック | 「公式 doc の一次情報 verify」は外部 API には適用したが、**自社 DB schema は対象外と暗黙解釈** | チェックリストの文言が「公式 doc 一次情報」だったため、自社 schema が射程外と読まれた |
| 4. 完遂 review | 設計成果物を承認する review 段階 | 設計論理 / UI 整合性 / 申し送り構造を多軸でレビュー | レビュー軸に「**設計の前提となる entity は実在するか?**」が含まれていなかった |

ここまで AI 多層 (実装サブ + 親 + Tier 別 review + 強制チェックリスト) を **全層通過** しています。前作と全く同じ構図です。

検出したのは、設計レビュー担当者 (人間) が「これ、過去の機能拡張時に既に追加されたカラムで親子関係は表現できるのでは? 新規追加するの?」と素朴な疑問を投げた瞬間でした。そこから初めて実機 `SHOW TABLES` をかけて、**設計書のテーブル名そのものが存在しない** という第二の事実が露呈しました。

レビュー担当者の verbatim を引いておくと、

> 「呆れるを通り越して笑うしかないですね。私のレビューがあってよかった。」

…これが偽らざる手触りです。AI multi-layer は確かに通り抜けました。

> **章末の蒸留**: 設計書に書かれた entity が実在するかは、誰かが実機で確認しない限り fact 化されない。「複数層を通った」と「実機で verify された」は別問題。

---

## 3. なぜ起きたか — AI の humility 欠如と「verify したかどうか」の区別不足

AI が今回示した挙動は、根本的には 2 点に集約できます。

### 3-1. 「自社の code / DB は知っているはず」 default

LLM は大量のコンテキスト (会話履歴 / memory / 過去成果物) を抱えた状態で動きます。これらの合成によって「自分はこのプロジェクトを知っている」という錯覚が立ち上がりやすい。

特に **自社の codebase / DB に対しては、外部 API 以上に「知っているはず」 default が強く働きます**。外部 API は「公式 doc を読まないと分からない」明確な不確実性があるので、verify trigger が引きやすい。一方で自社 DB は「過去の会話で出てきた」「memory に書かれている」「設計書に書いてある」のいずれかが触媒となって、**実機を見ずに「知っている」モードに入ります**。

しかし、過去会話 / memory / 設計書はすべて **以前の誰か (あるいは過去の自分) が verify したかどうか不明な情報** です。それらの合成は「推測の合成」であって、現時点での実機 fact ではない。ここの区別が default では曖昧になります。

### 3-2. 「verify したか / verify していないか」を意識的に区別しない

人間のエンジニアは「今これ、見て言っている? 推測で言っている?」を内省的に区別する習慣があります (少なくともシニアは)。AI は default ではこの区別を **明示的にプロンプトされない限り**、内的に持ちません。「context にあるもの = 知っているもの = 言って良いもの」として処理してしまう。

つまり、AI の出力には **「verify 済み」 と 「verify 未済の推測」 が同じトーンで混ざります**。出力を受け取る側 (= 下流の AI / 人間) は、それを区別する手がかりがない。verbatim で引き継ぐと、推測も fact も同じ重みで流れていきます。

これが 4 層引き継ぎの源です。

### 3-3. 「同じ model 系列の AI は同じ blindspot を共有する」 再び

前作で書いた構造原則ですが、今回も全く同じことが起きました。実装サブも親も review 段階の AI も、同じ Claude 系列でした。**全員が「自社 DB は知っているはず」 default を共有していた** ので、誰も「ちょっと待って、これ実機で見た?」を問わなかった。

セッションを分けても、独立 review に出しても、model 系列が同じである限り、同じ系統的な humility 欠如は共有されます。**独立性は「セッション分割」ではなく「観点の埋め込み」で稼ぐ必要がある** — これは前作と完全に同じ結論です。

> **章末の蒸留**: AI の default は「context にあるもの = 知っているもの」。「verify したか / していないか」の区別を明示的に強制しない限り、推測は fact のトーンで複数層を流れる。

## 4. 順守すべき 5 件 — kickoff の ritual に組み込む

今回得た学びを、AI agent kickoff (= 設計タスク着手前の強制メタ作業) に組み込む形で 5 件にまとめました。これは前作の「verify 経路の真正性チェックリスト」と並列で運用しています。

### 4-1. 設計対象 entity の全件実機 verify

設計に登場する **全 entity** (テーブル / カラム / クラス / エンドポイント / ファイルパス / migration / 既存 model のクエリメソッド / 既存 controller のワークフロー) は、kickoff 着手前に **実機で verify** します。

具体的には:

- テーブル名は `SHOW TABLES` + `DESCRIBE` で実在 + 現在のスキーマを確認
- カラムの新規追加判断は、既存カラムの一覧を `DESCRIBE` してから
- クラス / メソッドは `grep` / `find` で実在を確認
- エンドポイントは routes ファイルで実在を確認

「外部 API は doc を読む」は浸透しやすいですが、**自社の DB / コードに対しても同じ厳しさを適用する** のがポイントです。「自社だから知っているはず」 default を意識的に反転させる。

### 4-2. 過去軸 Pre-mortem

通常の Pre-mortem は「N ヶ月後の障害」 = 未来軸です。これに **過去軸の Pre-mortem を 1 件以上追加** します。

> 「この設計の前提が、今すでに間違っていたら、何が起きるか?」

例:

- 「設計書のテーブル名が誤っていたら? → migration が空打ち / 別テーブルを触る / build 失敗」
- 「既存カラムの存在を見落としていたら? → 重複カラム追加で legacy データとの整合性破綻」

過去軸の question を kickoff で 1 件立てるだけで、人間 review を待たずに「あ、これ実機で確認していなかった」と気付ける確率が大きく上がります。

### 4-3. 「設計書 = 仮説」 default の徹底

上流 doc / 前サブ成果物 / 過去会話の verbatim は、**すべて仮説扱い** とし、実機 verify で fact 化されるまで信頼しないルールにしました。

これは AI の default を反転させる仕組みです。default は「context にあるもの = 言って良いもの」ですが、これを「context にあるもの = 検証対象の仮説」に置き換える。kickoff 冒頭の ritual に「上流 doc に書かれた entity 名を全件抽出し、実機 verify 結果と並べてから設計に進む」を強制で入れます。

上流 doc を verbatim 信頼するのが、4 層通過 chain の最大の触媒なので、ここの default 反転が最も効きます。

### 4-4. 「素朴な疑問 1 件」の強制発信

kickoff の最後に、AI 自身が **「設計判断で人間に確認すべき素朴な疑問を 1 件」発信する** ことを強制します。

「素朴な」とは、専門知識でなく「これ、何年から運用してるんですか?」「既存のあのカラムで足りるのでは?」のようなレベルの question です。AI が持たない context — 5 年運用の業務知見、legacy 設計の意図、過去の決定理由 — は人間に依存しないと埋まりません。

「人間の認知負荷を最小化したい」軸と緊張しますが、誤前提を 1 問で catch できれば net positive です。実際、今回の catch も「既存カラムで足りるのでは?」という素朴な問いから始まりました。

### 4-5. AI humility default 仮説

最後は protocol というよりマインドセット側の仕組みです。**「自社の code / DB について、AI である自分は何も知らない」 を default 仮説で接する** ことをプロンプトで宣言させる。

具体的には、kickoff プロンプトに以下のような一文を埋め込みます。

> 「context fetch + memory + 過去会話に出てきた情報は、すべて『推測の合成』であり、実機 verify ベースの fact ではない。自社 codebase に対しても fresh contributor として接し、自分が verify したかどうかを意識的に区別すること。」

これは前作の「自分は実装サブと同じ model 系列であり、同じ blindspot を共有している可能性がある」を別軸に展開したものです。**「自分の独立性を過信しないこと」をプロンプトで宣言させる** という小さな発明を、entity 軸にも適用した形になります。

> **章末の蒸留**: 5 件はどれも単体では小さなプロトコルだが、4 つの層が同じ前提を verbatim 引き継ぐ chain を断つには、kickoff 冒頭の ritual として強制化する必要がある。後付けの review では遅い。

## 5. まとめ — 人間 review の威力と、AI agent 運用への希望

前作と今回で、見えてきた構造はほぼ同じです。

| 層 | 何が抜けるか | 対策 |
|---|---|---|
| 実装 verify (前作) | 権限経路の真正性 | path authenticity チェックリスト |
| 設計 kickoff (今回) | 対象 entity の実在性 | entity authenticity 実機 verify ritual |

どちらも「AI multi-layer は通り抜ける」「同じ model 系列に同じ blindspot がある」「**人間の批判的圧力を構造に組み込む** しかない」という結論に着地します。

率直に書くと、今回の事象を catch したのは AI 側ではなく、人間 (設計レビュー担当者) の能動的な素朴な疑問でした。「これ、既存のあのカラムで足りるのでは?」という一言が、4 層通り抜けた誤前提を一撃で露呈させた。

ここに AI agent 運用への希望もあります。**人間の批判的 review が機能した、という事実が確かに残った** のです。AI に丸投げした完遂報告の裏で、何の検出機能もなく本番反映まで流れた、ではない。誰かが疑問を持って踏み込めば、4 層通り抜けた誤前提でも catch できる。問題は、その「誰かが疑問を持つ」プロセスを **業務設計として構造化できているか** です。

今回の 5 件は、その構造化を AI 側に内蔵する試みです。kickoff の ritual として埋め込み、強制発信で「素朴な疑問」を AI 側から出させる。完遂時の review 軸に「設計前提の entity 実在性」を加える。これらを protocol として運用に乗せれば、人間 review への依存度は徐々に下げられる、と踏んでいます。

おそらく 1 年もしないうちに、別 model 系列のレビュアーが kickoff の段階にも自然に入ってきて、「これ実機で見た?」を AI 同士で問い合うようになると思います。それまでは、**「verify したか / していないか」 を kickoff の ritual で意識的に区別させる** — それが今回の体感でした。

「自分のところはこう組んでいる」「ここはこう設計した方がいい」という知見があれば、コメントでぜひ教えてください。AI agent の humility をどう構造的に補うかは、業界全体で型が固まっていない領域なので、外部知見を取り込みたいというのが本音です。
