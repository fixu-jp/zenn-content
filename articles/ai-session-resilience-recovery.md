## はじめに

2026-05-29、Claude Opus 4.8 のリリースと Claude Desktop のアップデート直後に、AI サブセッションが意図せず終了する事象に複数回遭遇しました。最新版をいち早く採用している以上、リリース直後の不安定さは織り込むべきトレードオフです。原因はまだ切り分け中で、リリース影響なのか、それとも私自身がキーボード操作などで意図せず終了させたのか、断定できていません。

ところが、この一連の出来事を通じて **作業ロスはゼロ** でした。複数の AI サブセッションを並行運営して、あるバックエンドサービス群の開発を進めている最中の出来事だったにもかかわらず、です。

本記事は、この「なぜロスゼロで済んだのか」を、AI 駆動開発における **セッション消失への回復力 (resilience) 設計** という普遍的な学びとして整理したものです。一文で先に書いてしまうと、

> **個々の AI セッションは消えうる (ephemeral) と前提し、コードと思考を二重に外部永続化したうえで、親セッションが痕跡から仕掛かりを再構成できる設計にしておけば、消失の原因が未確定でも事業影響ゼロで復旧できる。**

想定読者は、Claude Code / Cursor / Cline などの AI エージェントを使った複数セッション運営に取り組んでいる開発者・エンジニアリングマネージャーです。題材の具体は伏せますが、回復力設計のパターン自体はツールを問わず転用できます。

---

## 1. 何が起きたか — 並行運営中に計3回の消失

その日、複数の AI サブセッションを並行で走らせ、あるバックエンドサービス群の開発を進めていました。親セッション (オーケストレーター役) が全体を統括し、子セッションがそれぞれの担当範囲を実装していく、という構成です。

この運営の最中に、**計 3 回、セッションが意図せず終了する事象** が発生しました。親で 1 回、子で複数回です。ちょうど Opus 4.8 と Claude Desktop のアップデート直後だったため、リリース直後の不安定さを疑いましたが、UI 操作で意図せず終了させた可能性も否定できず、原因は切り分け中です。

普通に考えれば、進行中のセッションが消えれば、そこで進めていた作業内容や思考の文脈が失われ、相応の手戻りが発生しそうなものです。ところが実際には、**毎回ロスゼロで復旧できました**。これは運が良かったのではなく、後述する 3 つの仕掛けが事前に効いていたからでした。

> 学び: セッション消失は「起こったら困る異常」ではなく「いつか起こる事象」として運営設計に織り込んでおくべき対象である。

---

## 2. 二重の永続化 — コードと思考を別々の外部に逃がす

回復力の土台は、**状態を外部に永続化しておくこと** です。ポイントは、永続化すべき状態が 2 種類あり、それぞれ別の置き場所に逃がす必要があるという点です。

**① コード = こまめな commit / push** — 各サブセッションは、節目 (プルリクエスト単位) ごとに commit して push します。これでコードの成果は GitHub という外部に保全されます。セッションが消えても、push 済みのコードは 1 行も失われません。これは AI 駆動開発に限らず当然の習慣ですが、セッションが消えうる前提に立つと「こまめさ」の重要度が一段上がります。

**② 思考・設計 = 作業ファイルへの永続化** — コードだけでは足りません。なぜその設計にしたのかという判断記録、タスク着手前の事前検討 (kickoff)、設計書、ドラフト段階のコード、検討中の選択肢といった **思考の成果** は、コミット可能な完成形になる前の段階ではコードに現れません。これらを作業ディレクトリのファイルとして書き出しておきます。

この二重化が肝心です。コードだけ永続化していると、消失時に「何が出来ているか」は復元できても「なぜそうしたか」「次に何をするはずだったか」が欠落します。思考だけ永続化していてもコードの実体がなければ復元できません。**両方が揃って初めて、復旧時に欠落がない状態** になります。

> 学び: 永続化すべき状態はコード (commit/push) と思考 (作業ファイル) の 2 種類。片方だけでは復旧時に必ず欠落が出る。

## 3. 親による痕跡からの再構成 — 「どこまで進んだか」は復元できる

二重に永続化されていても、消えたセッションが「どこまで進んでいたか」を誰かが把握し直さなければ復旧は始まりません。並行運営では、この役割を **親 (オーケストレーター) セッションが担います**。

子セッションが消えたとき、親は痕跡を突き合わせて仕掛かりを再構成します。具体的には、

- `git log` / `git status` で、どのコミットまで進み、どのファイルが未コミットで残っているかを確認する
- `gh pr` / `gh issue` で、プルリクエストやチケットの状態から進捗段階を読み取る
- 作業ディレクトリのファイル (kickoff・設計書・判断記録) から、思考がどこまで進んでいたかを把握する

これらを突き合わせれば、「コードはここまで、設計判断はここまで確定、残作業はこれ」という仕掛かり状況を、消えたセッション本人がいなくても外部から再構成できます。**痕跡が十分に残っていれば、進捗は復元可能な情報になる** ということです。

この「親が子の痕跡から復元する」構造こそが、並行運営における回復力の要です。個々の子セッションが消えても、親が生きていれば全体は止まりません。そして仮に親が消えても、親の作業ファイルと全体管理ページが残っていれば、新しい親セッションが同じ手順で全体を再構成できます。

> 学び: 進捗は「セッションの頭の中」ではなく「git・gh・作業ファイルの痕跡」に宿る。痕跡が十分なら、本人不在でも進捗は外部から復元できる。

---

## 4. 復旧プロンプトの構造化 — self-contained な4要素

痕跡から仕掛かりを再構成できたら、最後はそれを使って **新しいセッションを立ち上げ直す** 工程です。ここで効いたのが、復旧プロンプトを定型フォーマットで構造化しておくことでした。

親が生成する復旧プロンプトには、次の 4 要素を **そのプロンプト単体で完結する (self-contained)** 形で盛り込みます。

1. **仕掛かり状況** — どこまで進み、何が未完で残っているか
2. **再開手順** — 何から着手すれば作業を継続できるか
3. **必読資料** — 設計書・全体管理ページ・関連記事など、文脈把握に必要な参照先
4. **確定済みの設計判断** — すでに決まっていて蒸し返す必要のない判断事項

そして起動時は「役割の提示 + 全体管理ページ + 復旧プロンプトのパス」という定型で再起動します。新しいセッションは context ゼロから立ち上がりますが、この復旧プロンプトを読むだけで、消えたセッションが持っていた文脈を引き継いで作業を再開できます。

ここで重要なのは、復旧プロンプトが **self-contained であること** です。「前のセッションの会話を覚えている前提」で書くと、新しいセッションは何も覚えていないので機能しません。逆に、確定済みの判断まで含めて自己完結的に書いておけば、同じ設計判断を一からやり直す無駄も、蒸し返しによる手戻りも防げます。

> 学び: 復旧プロンプトは「仕掛かり状況 / 再開手順 / 必読 / 確定判断」を self-contained に書く。新セッションは何も覚えていない前提で、それ単体で再開できる粒度にする。

## 5. まとめ — 永続的なのは外部状態だけ

3 回のセッション消失をロスゼロで乗り切れたのは、特別な幸運ではなく、次の 3 つが事前に効いていたからでした。

1. **二重の永続化** — コードは commit/push で GitHub に、思考・設計は作業ファイルに
2. **親による痕跡からの再構成** — git・gh・作業ファイルから仕掛かりを復元
3. **復旧プロンプトの構造化** — self-contained な 4 要素で新セッションを再起動

これらを貫く前提は一つです。**個々の AI セッションは消えうる (ephemeral)。永続的なのは外部状態 (git / GitHub / ファイル) だけ** ということ。セッションを「消えない前提の作業場」とみなすと消失時に脆くなりますが、「いつでも作り直せる一時的な実行環境」とみなし、価値ある状態を片端から外部に逃がしておけば、消失は復旧可能な事象に変わります。

### 原因が未確定でも、結果は設計で吸収できる

ここで強調したいのは、今回の消失の **原因がまだ切り分け中** だということです。リリース直後の不安定さなのか、私の UI 操作起因なのか、断定できていません。

普通なら「原因が分からない」状態は不安で、調査が終わるまで作業を止めたくなります。ところが回復力設計があると、話が変わります。**原因が何であれ作業ロスはゼロ** なので、原因究明を慌てず並行で進められますし、Anthropic はこれまでも迅速に改善リリースを出してきた実績があるので、その改善を落ち着いて待つ余裕が生まれます。回復力設計の本質は、消失そのものを防ぐことではなく、**消失の原因という不確実性を、結果 (事業影響ゼロ) の側で吸収してしまう** ことにあります。

最新版をいち早く採用することと、リリース直後の不安定さを織り込んでおくことは両立します。むしろ、消えうる前提の設計があるからこそ、最新版を恐れず採用できる、とも言えます。

### 永続化は必要条件、運用が十分条件

最後に一つ補足を。「外部に永続化しておけば安心」とまでは言い切れません。姉妹記事 [AI時代の急がない勇気と旧世代発想のアンラーニング](https://zenn.dev/fixu/articles/ai-era-courage-not-to-rush) でも触れたとおり、**永続化は必要条件であって十分条件ではありません**。永続化された痕跡を親が能動的に読み返し、復旧プロンプトに組み立て直す運用がセットになって初めて回復力として機能します。痕跡を残すこと自体と、それを使って復元する運用は別物だ、という点は押さえておきたいところです。

なお、本記事を書くこと自体が、姉妹記事で提案した「クリティカルパスとは別レイヤーの活動 (知見共有)」の実践でもあります。並行運営で空いた余白を、こうした振り返りの言語化に振り向けるのは、回復力設計の知見を組織に残す投資でもあると考えています。
