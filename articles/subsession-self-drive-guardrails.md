## はじめに

少し前に [AIマルチセッション運営で気づいた7つの原則 — 3日間で270万行を消して見えた景色](https://zenn.dev/fixu/articles/ai-multi-session-7-principles) という記事を書きました。9リポジトリ横断で dead code を一気に整理したフェーズで気づいたことを、7つの原則に蒸留したものです。

あれから時間が経ち、また同じ9リポジトリを束ねる長期プロジェクト — Laravel 8→12 / PHP 8.1→8.3 / alpine 化という MW (ミドルウェア) アップグレード — を進めています。前回と外形は似ていますが、内側の運用は一段進化しました。

一番大きな変更は、**サブセッションが自分で完結できる作業の幅をかなり広げた**ことです。具体的には、Copilot レビューの依頼・結果の解釈・条件付きでのセルフマージ・後続フェーズへの自動進行までを、サブセッションが自走でやり切る運用に切り替えました。

結果として、親 (Code デスクトップ) と人間 (筆者) の往復は半分以下に減りました。一方で、それと交換に、これまで親側で吸収していた構造的なリスクが、サブセッション側に分散していくことも見えてきました。

ここで先に結論めいたことを書いてしまうと、AI 活用のオーケストレーションは、

> **雑に丸投げして業務を破綻させるのか、数手先を見越して細部に拘った業務設計をすることで効率的かつ安全な自走を達成するのか**

の分岐で、明暗が分かれます。任せる幅を広げる判断は方針として正しくても、それを破綻させずに走らせるためには、**任せられるための足場 — 委譲ルール、監視経路、編集動線、起動プロンプトの一文一文** に至るまで、無数の細部設計を積み上げる必要があります。

この記事は、自走化に踏み込んだ経緯、踏み込んだ結果として浮上した7類型のリスク、それを抑えるために親側に組み込んだ監視ガードレール、そしてもう一段抽象度を下げた事例として、並列編集される進捗管理表のフォーマット設計について、進行中のプロジェクトから書き起こしたものです。

## 1. 自走化に踏み込んだ経緯 — 7原則時代から1段進化

前回の3日間 (約270万行削除フェーズ) と、今回の MW アップグレードフェーズは、外形は似ていますが、構造が違います。

| 観点 | 前回 (270万行削除フェーズ) | 今回 (MW アップグレード) |
|---|---|---|
| 主作業 | 機械的な大量削除 (dead code 一掃) | Laravel/PHP/alpine の major アップグレード (BC break を含む) |
| 並列度 | ピーク 8〜9 | 定常 9 |
| マージ判断 | 各 PR は親判断必須 | サブの条件付きセルフマージ OK |
| Copilot レビュー | 親 / 人間が assign + 解釈 | サブがブラウザ拡張で trigger + 解釈 + 返信 |
| 人間負荷の性質 | コピペ同期で高 | 完遂報告まで低、ただし監視は必要 |

前回時点では「人間コピペは摩擦ではなく強制同期ポイント」という原則を採用していました (前記事の原則 7)。これはこれで機能した一方で、3日間でも認知疲労が大きく、5〜10日続く長期プロジェクトに同じ密度で人間を loop に入れ続けるのは現実的ではない、という肌感がありました。

そこで今回は、**Copilot レビューを起点とする一連の手続き — review 依頼の trigger / 結果の解釈 / 反映 / マージ — をサブセッションに権限委譲し、人間と親はマージ後の総括 (完遂報告のサンプリング監査) に役割をシフトさせる** という変更を試しました。

これは単に「人間負荷を減らす」というより、**人間に残す負荷を、より高価値な層 (監査と方針判断) に集約する** という設計変更です。

ただし — そして本記事のテーマはここからです — 委譲幅を広げる判断は方針として正しくても、**「任せる」と「丸投げ」は別物** です。任せられるためには、任せても走り抜けられるだけの細部設計を、事前にも、走りながらも、積み上げる必要があります。今回それをやらずに踏み込んだら、間違いなく途中で破綻していました。

## 2. 委譲と監視のバランス — 補完性原理の話

ここで少し抽象度を上げた話を挟ませてください。

AI を実務に組み込めば組み込むほど、「どこまで AI に任せ、どこから人間が握り続けるか」の線引きが、ほぼすべての設計判断に効いてきます。これはエンジニアリングというより、組織論や統治論に近い問題です。

社会学・政治学に **補完性原理 (subsidiarity)** という概念があります。EU の機能配分や、カトリック社会教説で参照される考え方で、ざっくり「決定は、その実行に最も近い小さな単位に委ねる。ただし上位はその責任を放棄しない」という原則です。

AI と人間の役割分担も、構造的にはこれと同じ問題に見えます。

- 委譲することで、現場 (= サブセッション) の局所最適を引き出し、速度と精度を稼ぐ
- ただし上位 (= 親 + 人間) は、局所最適の集合が大域最適から外れていないかを監督する責任を持ち続ける

完全に「投げっぱなし」にすると、各サブセッションが自分のリポジトリ視点で「軽微」と判定したものが、9リポジトリ横断で見ると重要な発見だった、というケースが必ず発生します。逆に、過剰に握り続けると、AI 実行のスループット差を活かしきれない。

ここで補完性原理が示唆するのは、**「任せる」と「責任を持ち続ける」は両立する、というより、両立しなければならない** という点です。「任せたから後は知らない」は補完性原理の半分しか守っていない。**上位が責任を持ち続けるための具体的な仕組みを業務設計に組み込んで、初めて成立する**。

つまり、自走化を成立させる本質は「権限を移譲した」という宣言ではなく、**「移譲した先で破綻が起きないよう、細部の業務設計を作り込んだ」という実装** にあります。今回の Day062-063 でやったことは、この実装を業務プロセスに落とし込む試みでした。

## 3. 自走化で浮上したリスク7類型

委譲の幅を広げた結果、それまで親側で吸収していたリスクがサブ側に分散しました。プロジェクトの進行中に観測したパターンを整理すると、概ね7つの類型に収まります。

これは「雑に丸投げした場合に、どんな形で業務が破綻しうるか」の分布図 でもあります。逆に言えば、**この 7 類型を 1 つずつ細部設計で抑え込めば、自走化は破綻しない** ということでもあります。

各類型は、特定のサブセッションを責めるための分類ではなく、自走化という構造に内在するリスクの分布図として読んでいただきたいです。

### A. 証跡関連

Copilot レビューへの返信を残さずセルフマージしてしまう、あるいは「対応しました」のみで根拠を書かない、という pattern。後追いの監査で「なぜこの指摘が scope-out になったのか」を再構成できなくなります。

抑え込みの方向性は単純で、**scope-out 判定は必ず Copilot コメントへの返信で根拠を明記する** ことを必須化します。返信投稿は将来の audit と同パターン再発時の参考データとして残るので、ここは省略させない。

### B. 判断品質関連

「3 ラウンドルール (3回目以降の hardening 系指摘はスキップ可)」を、まだ機能影響系の可能性が高い 1 ラウンド目で誤適用してしまう。あるいは、9リポジトリ横断で確立した統一基準の認識が古いまま、自分のリポジトリだけで判断してしまう、という pattern。

これは、起動プロンプトに最新の判断基準を都度織り込むこと、broadcast 配信で全サブの認識を同期し続けることで抑え込みます。

### C. エスカレーション漏れ

これがもっとも厄介です。サブセッション自身が「重大」と判定していないために親に上がってこない、というパターン。1 リポジトリ視点では軽微に見えるが、9リポジトリ横断で見ると重要な発見だった、というケースが起きます。

具体例 (抽象化):

- 特定パッケージのバージョン違いで露出している namespace の差を発見した。それを「自リポジトリ固有」と判断し、内部処理してしまう
- セキュリティアドバイザリ関連の発見を「軽微」と分類してしまう
- 既存 playbook と矛盾する状況に遭遇しても、矛盾と認識せずに自リポジトリの解釈を優先してしまう

抑え込みは、「重大発見の具体例リスト」を起動プロンプトに事前に列挙しておき、**該当しそうなら必ず親エスカレ** とすることです。判定の閾値をサブ側に持たせず、リスト照合だけで上げるべきか決められる形に倒します。

### D. 機械的判断関連

CI が green であれば機能影響なし、と短絡してしまう。マージ可能ステータスが CLEAN なら安全、と短絡してしまう。実際には CI のスコープ外で起きる影響 (たとえば本番デプロイ後にだけ表面化する依存関係の不一致) が抜けます。

抑え込みとして、image を変更するフェーズには **dev image rebuild + 主要クラスの存在確認スモークテスト** を事前必須化する、といった「last line of defense」を組み込みます。

### E. 自走運用そのものの副作用

「報告不要」を「親に隠していい」と誤解釈してしまう、あるいは Dunning-Kruger 効果的に、自走で得た成功体験から自信過剰になり、本来エスカレすべき判断を独断してしまう、という構造的リスクです。

これは技術的なガードレールでは抑えにくく、後述する「transparency 文化の明示」で抑え込みます。

### F. 経路依存性

Copilot review の trigger は、特定アカウントでブラウザログインしたサブセッションだけが実行できる、という外部条件に依存しています。ブラウザのセッション切れや、別アカウントへの切り替わりが起きると、サブが「trigger 完了」と思い込んだまま実は Request が登録されていない、という事故が起きます。

抑え込みは、**操作前にブラウザ接続状態とログインアカウントを必ず検証する** こと、**操作後も画面リロードして state 変化を確認する** こと。タスク結果の成功メッセージは信用しない、というのが原則です。

### G. 進捗管理の不可視化

サブがセルフマージした結果が、親側の集約ダッシュボードに反映されない、という pattern。完遂報告のタイミングまで親側の進捗把握ができない、中間状態が盲点になります。

これは集約ダッシュボードのフォーマット設計と編集動線の問題でもあるので、章 5 で具体例とともに掘り下げます。

---

これら 7 類型はそれぞれ独立したリスクではなく、自走化の幅を広げた瞬間に必ず潜在的に立ち上がる構造的副作用です。**1 つずつ細部設計で抑える** ことが自走化の前提条件であって、抑えずに踏み込めば破綻する、というのが今回の体感でした。

## 4. 親側に組み込んだ監視ガードレール

リスク 7 類型を抑えるために、親側に組み込んだ監視の仕組みは、大きく 3 層です。

### 4-1. 定期 sweep — 親が独立に状態を観測する

5〜10 分ごとに、親が `gh pr list` を全リポジトリ横断で実行し、各サブセッションが現在どのフェーズにいるか、どの PR が走っているか、どこで止まっているかを **サブの自己申告とは独立に** 観測します。

ここで重要なのは「サブの完遂報告と独立した観測経路を持つ」という点です。完遂報告だけを情報源にすると、E (自走運用の副作用) や G (進捗管理の不可視化) が観測されません。`gh pr list` は半 SoT (Source of Truth) として機能し、サブの自己申告と乖離があれば即座に分かります。

### 4-2. 完遂報告サンプリング監査 — 抜き打ちで品質をチェック

サブから完遂報告を受領した時点で、過去にマージされた PR を 2〜3 件抜き打ちで監査します。観点は以下:

- Copilot 指摘への返信投稿があるか / 内容が形式的でないか (リスク A)
- scope-out 判定が後追いで見ても妥当か / 価値ある指摘を見落としていないか (リスク B, C)
- 9 リポジトリ統一基準を遵守しているか (リスク B)

監査で問題が見つかったら、まずは個別に再対応を依頼し、横断影響がありそうなら全サブにブロードキャストで再周知 + プロジェクト memory 更新を行います。発見した知見はそのまま次の Day の起動プロンプトに織り込みます。

### 4-3. transparency 維持 — 「親に隠さない」を明示する

これは技術的というより文化的なガードレールです。サブセッションへの起動プロンプトで、「親に隠す権利はない」「迷ったら親エスカレ」「scope-out 判定は必ずコメント返信で根拠明記」を繰り返し明示します。

逆に、サブからの自発的な self-audit (完遂後に自分の判断を見直して改善計画を提示する) は積極的に評価し、起動プロンプトの初期化文に「broadcast 受領時に self-audit を奨励」と書き込みます。これによって、サブ自身が自走の限界を内省する習慣が定着し、親側の監視を一段補完してくれます。

### 3層をまとめた絵

```
  サブセッション (実行 + 一次判断)
        │
        ↓ 完遂報告 / scope-out 判定 / セルフマージ結果
        │
  親セッション (集約 + 監査)
        ├── 4-1 sweep ── 独立観測経路で乖離検知
        ├── 4-2 audit ── 完遂報告の品質を抜き打ち検証
        └── 4-3 transparency ── 隠さない文化の明示と self-audit 奨励
        │
        ↓ 方針判断 / 横断ブロードキャスト
        │
   人間 (筆者)
```

正直、この監視ガードレールは運用し始めたばかりで、まだまだ試行錯誤の段階です。3 層のうち sweep の頻度が荒いとリスク G を逃しやすいですし、audit の抜き打ち率が低いとリスク A〜C が定着してしまいます。実プロジェクトで回しながら、頻度と粒度を調整しているところです。

「自分はこういう仕組みでやっている」「もっとこう設計した方がいい」というアイデアやフィードバックがあれば、ぜひコメントで教えてもらえると嬉しいです。マルチセッション運営はまだ業界全体で型ができていない領域なので、外部知見を取り込みたいのが本音です。

## 5. 細部設計が運用の明暗を分ける一例 — 並列編集される進捗表のフォーマット

ここまでは大枠の話 (委譲ルール / 監視ガードレール) でしたが、本記事のテーマである **「細部の業務設計が明暗を分ける」** をもう少し肌で感じてもらえる事例として、進捗管理表のフォーマット設計の話を 1 本だけ紹介します。

これは Notion の表機能を使っていたときの体験で、ツール固有のクセも一部含みます。なので普遍的な処方箋というより、**「細部のフォーマット設計が雑だと、9 リポジトリの実作業がどれだけ綺麗でも、親側の状態把握がいきなり破綻する」** という事例として読んでください。同じ構造の問題は、GitHub Projects、Linear、スプレッドシート、Markdown 表など、**並列編集される 2 次元データ全般** で再現します。

### 失敗した最初の設計

最初は「Phase 行 × repo 列」で組みました。

```
            | repo1 | repo2 | repo3 | ... | repo9 |
Phase 1     |  ✅   |  ✅   |  🚧   | ... |  ⏸   |
Phase 2     |  ✅   |  🚧   |  ⏸   | ... |  ⏸   |
Phase 3     |  🚧   |  ⏸   |  ⏸   | ... |  ⏸   |
...
```

「Phase の進捗を上から下に追える」という親側の視点から見ると直感的で、最初はこれで良いと思っていました。ところが運用してみると、表面的な「見やすさ」の裏側で問題が連鎖していました。

### 実際に起きた事故 — セル更新の 1 列 shift 誤配置

Notion API は、表セルを更新する際に `old_str` (置換対象の文字列) を渡して `new_str` に置き換える方式を採ります。**`old_str` が一意でない場合、API はエラーではなく silent に意図しない位置に挿入される** という挙動があります。

今回の表は `⏸ × N` の連続同値セルが多く、サブが「自分の repo 列の自セルだけ」を更新しようとしても、`old_str` の周辺パターンが複数 Phase で同形になります。これが原因で、ある Phase の自セル (列 8 の `⏸`) を `✅ #15` に置換するつもりが、実際には隣の列 (列 9 の `⏸`) の **前に挿入** されてしまい、行全体が 1 列 shift しました。

実際に起きた誤配置 (匿名化):

```
意図した状態:
  列7: ✅ #21        ✅
  列8: ✅ #15        ← 自セル (今回更新)
  列9: ✅ #25 (前回) ✅
  列10: ⏸           ✅

実際に起きた状態:
  列7: ✅ #21              ✅
  列8: ⏸ (置換されず残る)  ❌
  列9: ✅ #15 (列8用が挿入) ❌
  列10: ✅ #25 (本来列9)    ❌
  列11: ⏸ (本来空セル)      ❌
```

サブが 1 セル更新したつもりが、4 セル分まとめて誤った状態に変わりました。

### 親と子のすれ違いを発見した瞬間

この 1 列 shift は、**サブ側からは「成功」に見えます**。書き込みは API 的に成功扱いを返してきますし、サブが直後に fetch しなければ気づかない。一方で **親側のマトリクス俯瞰では「該当 Phase が未了に見える」** という乖離が生じます。

実際のやりとりはこうでした (匿名化)。

> **親**: 親マトリクスでは「C 集約」が未了に見えます。更新漏れ?
>
> **サブ**: ご指摘その通りです。前回の update で挿入位置が誤り、自リポジトリ列ではなく余分セルとして列ズレしました。fetch して修正します。
>
> *(サブが fetch + 再 update)*
>
> **サブ**: ご指摘通り、前回 update で 1 列 shift していました。row 全体を再 align します。

サブの自己申告と、親の独立観測が乖離していなければ発見できなかった事象です。これは前章 (4-1 sweep) の存在意義を裏側から証明する事故でもありました。**親が独立に観測する経路を持っていなければ、誤配置は完遂報告タイミングまで気づかれず、9リポジトリ全体の状態認識がずっとズレ続けるところでした。**

### 反転後の設計

これらを踏まえて、後続の同種マトリクスは **「repo 行 × Phase 列」** に転置しました。

```
            | Phase 1 | Phase 2 | Phase 3 | ... | Phase N |
repo1       |   ✅    |   ✅    |   🚧    | ... |   ⏸    |
repo2       |   ✅    |   🚧    |   ⏸    | ... |   ⏸    |
repo3       |   🚧    |   ⏸    |   ⏸    | ... |   ⏸    |
...
```

これだけで以下が一気に解消しました。

- 各 repo の進捗が **1 行で読み取れる**: スクロールせずに状態把握できる
- サブセッションが触る対象が **自分の repo 行に局所化** される: 異なるサブが同じ行を触ることがほぼない、collision を構造的に誘発しなくなる
- Phase 追加 (列追加) は各 repo 行に列を 1 つ足すだけで済む: 追加コストが小さい

ポイントは「**サブセッションが編集する単位 = 行**」になるように設計することです。並列編集が前提のデータでは、各主体の編集動線が「行」または「列」のいずれか一方に統一されている必要があります。Phase × repo だと、サブの編集対象が「列」に散らばっていて、しかも Phase ごとに行を渡って更新が発生するので、構造的に collision を誘発していました。

### この事例から引き出せる一般原則

ここで強調したいのは、Notion 固有の話ではなく、**並列編集される 2 次元データ全般に共通する細部設計原則** です。

> **並列編集主体ごとに、編集対象が表の 1 軸 (行 or 列) に局所化される構造に組む**

この一般原則を満たさない表は、ツールが何であれ、必ずどこかで主体間の編集競合を引き起こします。Notion は silent failure として、Git は merge conflict として、スプレッドシートはセル上書きとして、形は違えど同じ構造の問題が表面化します。

### ここからの含意

後から考えれば当たり前です。並列編集が前提の表で、編集主体の動線が表の構造とズレていれば、いずれ衝突する。

それでも最初は「親が Phase 進捗を上から下に眺めたい」という親側の都合で組んでしまっていました。**サブセッション (= 実際に編集する主体) の動線を主軸に据える** べきだった、というのが反省です。

そしてこの一見些細な反省は、本記事の核心と地続きです。**「親が見やすい設計」と「サブが安全に並列編集できる設計」は、雑に作ると一致しない。だからこそ細部の業務設計に手を入れる**。

進捗表のフォーマットひとつ取っても、その細部設計が運用全体の明暗を分けます。同じ構造の判断が、起動プロンプトの一文、エスカレ条件のリスト、ガードレールの監視頻度、と無数の細部に散らばっていて、それぞれを丁寧に詰めるかどうかで、自走化が安全に走るか途中で破綻するかが決まる。**自走化の成否は、こうした細部の集積で決まる**、というのが今回の体感でした。

## 6. まとめ — 自走の明暗は細部設計の積み重ねで決まる

前回の7原則記事から数週間、AI による業務スケールアップで一番効いている変数は、相変わらず **マルチセッションのオーケストレーション設計** だと感じています。

ただし冒頭にも書いた通り、その「オーケストレーション設計」は、

> **雑に丸投げして業務を破綻させるのか、数手先を見越して細部に拘った業務設計をすることで効率的かつ安全な自走を達成するのか**

の分岐で、明暗が分かれます。今回の自走化への踏み込みも、突き詰めれば「この分岐を後者側に倒すために、無数の細部に手を入れる」という地味な作業の積み重ねでした。委譲ルールを定める、リスクを 7 類型に整理して個別に抑える、独立観測経路を組む、起動プロンプトに重大発見リストを書き込む、進捗表のフォーマットを並列編集主体の動線に合わせる — こうした細部のひとつひとつを「面倒だから雑でいいや」と放置していたら、間違いなくどこかで破綻していました。

おそらく 1 年もしないうちに、AI の精度はもう一段上がり、「統括役に雑に投げたら、よしなに全部マネジメントしてくれる」世界が来るはずです。それが一日でも早く訪れることを強く願っています。

ただ現時点では、まだ統括役 AI に丸投げできる段階ではない。だからこそ、**今の AI の実力値を正確に理解した上で、うまく使い倒すための細部の業務設計** に投資する価値があります。マルチセッション運営 — オーケストレーション — は、AI 活用による業務スケールアップのキモであり続けると思いますし、そのキモを支えるのは、派手な技術選定ではなく、**地味な細部設計の積み重ね** だと、強く感じています。

同じようにマルチセッション運営に取り組んでいる方の、次の一歩のヒントになれば嬉しいです。

そして冒頭にも書きましたが、自分の運用はまだ試行錯誤の段階です。「自分はこう組んでいる」「ここはこうした方がいい」という知見やフィードバックを、コメントでぜひ教えてください。
