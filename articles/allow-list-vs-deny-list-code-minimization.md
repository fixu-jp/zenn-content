## はじめに

fixU Reboot プロジェクトで多拠点機能 (親会社が複数の子会社・店舗を束ねる構造) を AI ネイティブな進め方で実装していた、ある日のことでした。

親管理者向けの管理画面サイドメニューを「許可された 15 項目だけ表示する」要件があり、AI サブセッションが書いた実装の動作確認を dev02 環境で進めていたところ、15 項目のうち **4 項目が 404 / 500 エラー** で開けないことが分かりました。許可リストに並べた path のうち 4 つが、Laravel route として存在していなかったり、依存データが空で落ちたりしていたのです。

ユーザー (筆者) からの指摘はこうでした。

> 今回は「15 項目だけ」を表示することが要件だが、実装上は **必要な 15 項目を作る** のではなく、**不要な項目を非表示にする** というアプローチが正しい。そうすれば誤ったリンク先を指定するなどという問題はそもそも起こらない。
>
> 要件が満たせるのであれば変更するコード量は少ないほど美しい。これは人間時代でもそうでしたが、AI 時代でも変わらないと私は考えます。アンラーニングすべきことと、踏襲すべきことの見極めが重要ですね。

この指摘は、本記事の核そのものです。一文で蒸留すると、こうなります。

> **要件が満たせるならコード変更は少ないほど美しい — これは人間時代から不変の原則だが、AI が「綺麗そうな新規実装」を量産しがちな時代だからこそ、より意識的に踏襲する必要がある。**

本記事は、「AI 時代のアンラーニング」シリーズの一本として、踏襲すべき古典的設計原則を多拠点機能の事例で再発見した記録です。姉妹記事との関係はこうなっています。

- [AI時代のアーキテクチャ意思決定 ― 実装工数は「tie-breaker」ではなくなった](https://zenn.dev/fixu/articles/ai-architecture-decision-beyond-effort) ― 「堅牢性 vs 工数」軸での意思決定
- 本記事 ― 「同じ堅牢性なら、コード変更量が少ない設計を選べ」軸での意思決定 (前者と直交)
- [AIは知っているのに使わない — 設計タスクの "task-kickoff" プロトコルで潜在能力を引き出す](https://zenn.dev/fixu/articles/task-kickoff-ai-design-protocol) ― AI に潜在能力を発揮させるための kickoff Phase 0-6
- [AI時代の急がない勇気と旧世代発想のアンラーニング](https://zenn.dev/fixu/articles/ai-era-courage-not-to-rush) ― アンラーニング系列の段取り編

想定読者は、AI エージェントを業務に組み込んでいるエンジニア・テックリード・アーキテクトです。特に、「AI に新規実装を任せていたら、いつの間にか既存資産との整合が取れなくなっていた」という経験がある方、あるいは AI 時代の設計レビューでチェックすべき軸を整理したい方に読んでほしい内容です。

## 1. 多拠点機能の要件と「許可リスト」approach 採用

具体例から入ります。

fixU の多拠点機能は、親会社 Company が複数の子 Company を束ねる構造を表現するもので、親 Company の管理者 (= 親管理者) は、自社が束ねる子 Company 全体を見渡せる管理画面を持ちます。

要件は以下の通りでした。

- 既存の Manager 画面のサイドメニュー (約 30 項目) は、子 Company の店舗オペレーション用に最適化されている
- 親管理者は、店舗オペレーションには直接関わらない (子 Company の管理者がやる)
- 親管理者用には、**親会社全体に跨る 15 項目のみ表示する**
- 件数 "15" は PdM 確定、項目名は別途用意された HTML mockup に視覚表現として存在

実装を担当したサブセッションは、HTML mockup を Source of Truth として読み込み、以下のような「許可リスト」approach を採用しました。

```php
// app/app/Support/ParentSidebarAllowList.php
final class ParentSidebarAllowList
{
    public const PATHS = [
        '/',
        '/space_management',
        '/account',
        '/employee',     // ← dev02 で 500 error
        '/holiday',
        '/news',
        '/setting',
        '/plan',
        '/plus/plan',
        '/payment',
        '/credit',
        '/invoice',      // ← dev02 で 404 (route 不在)
        '/cms_web',      // ← dev02 で 404 (route 不在)
        '/term',
        '/template',     // ← dev02 で 404 (route 不在)
    ];
}
```

```php
// app/app/Http/Middleware/EnforceParentAllowList.php
class EnforceParentAllowList
{
    public function handle($request, $next)
    {
        if ($this->is_parent_admin
            && !in_array($request->path(), ParentSidebarAllowList::PATHS, true)) {
            return redirect('/');
        }
        return $next($request);
    }
}
```

view 側の Blade テンプレートでも、同じ Constants を `in_array` で参照して 15 項目を組み立てます。さらに `app/Providers/AppServiceProvider.php` で middleware の alias 登録、ルーティング側で alias 適用、と関連変更が連鎖します。

設計思想を 1 文で書くなら、こうです。

> 親管理者用の「触ってよい 15 項目の世界」を新規定義し、それ以外を URL 直打ちレベルでブロックする。

一見、責務がはっきりしていて綺麗な設計に見えます。Constants で許可項目が一覧化され、middleware で防御層も用意されている。AI コードレビューでも「単一責任が明確」「拡張時の影響範囲が局所的」といった肯定的な評価が出やすい構造です。

しかし、この approach は dev02 環境のテストで本質的な問題を顕在化させました。

> **§ 1 蒸留**: 「許可リスト」approach は責務が明確で AI に好まれやすい構造を持つが、許可リストの中身が既存資産 (Laravel route) から派生していない場合、Source of Truth が二重化する潜在的な脆さを抱える。

## 2. dev02 で顕在化した 4 項目の 404 / 500

実装が dev02 環境にデプロイされ、ユーザー視点での E2E テストが走った結果はこうでした。

| path | 結果 | 原因 |
|---|---|---|
| `/` | OK | 既存 route 存在 |
| `/space_management` | OK | 既存 route 存在 |
| `/account` | OK | 既存 route 存在 |
| **`/employee`** | **500 error** | route は存在するが、依存データが dev02 で空で落ちた |
| `/holiday` | OK | 既存 route 存在 |
| `/news` | OK | 既存 route 存在 |
| `/setting` | OK | 既存 route 存在 |
| `/plan` | OK | 既存 route 存在 |
| `/plus/plan` | OK | 既存 route 存在 |
| `/payment` | OK | 既存 route 存在 |
| `/credit` | OK | 既存 route 存在 |
| **`/invoice`** | **404** | Laravel route 自体が **そもそも存在しなかった** |
| **`/cms_web`** | **404** | Laravel route 自体が **そもそも存在しなかった** |
| `/term` | OK | 既存 route 存在 |
| **`/template`** | **404** | Laravel route 自体が **そもそも存在しなかった** |

15 項目中 4 項目で問題発生。発生率にして 27%。これは「テストでぎりぎり拾った僅かな取りこぼし」というレベルではなく、**設計 approach そのものが構造的に問題を生んでいた** ことのシグナルです。

なぜこうなったかを掘ると、原因は単純でした。

- HTML mockup の中に、視覚デモ用の placeholder として「請求書 (`/invoice`)」「Web ページ (`/cms_web`)」「定型文 (`/template`)`」のメニュー項目が並んでいた
- これらはまだ Laravel route として実装されていない
- AI サブセッションは HTML mockup を「正の Source of Truth」として扱い、各 path が Laravel route として存在するか verify せずに Constants 化した
- `/employee` は route は存在するが、dev02 の seed データが空で 500 になった (これは別軸の問題で、本記事のスコープ外)

要するに、**Constants 化された許可リスト** と **既存 Laravel route** という、本来同じであるべき情報源が二重化していた、というのが根本原因です。

「許可リスト」approach は、許可リストを書いた瞬間に **「真実の写し」** を作ります。原本 (= 既存 route) と写しが同期しなくなった瞬間、写し側だけが破綻します。dev02 で 4 項目が壊れたのは、まさにその divergence が顕在化した結果でした。

> **§ 2 蒸留**: 既存資産 (route 一覧) を Source of Truth として使わず、独立した「許可リスト」を新規定義した瞬間、二重定義による divergence の risk が構造的に発生する。

## 3. ユーザー指摘 = 「拒否リスト」approach への転換

問題が顕在化した時点で、ユーザーから入った指摘がこうでした。

> 今回は「15 項目だけ」を表示することが要件だが、実装上は必要な 15 項目を作るのではなく、**不要な項目を非表示にする**、というアプローチが正しい。そうすれば誤ったリンク先を指定するなどという問題はそもそも起こらない。

これは設計 approach そのものの転換を要求する指摘です。「許可リスト」(allow list) ではなく **「拒否リスト」(deny list)** で実装すれば、上記の divergence は構造的に発生しないからです。

転換後の実装イメージはこうなります。

```blade
{{-- resources/views/manager/partials/sidebar.blade.php --}}
@php
    // 親管理者には不要な、店舗オペレーション系メニューを列挙
    $hide_for_parent = [
        '/check_in',
        '/reservation',
        '/door',
        '/camera',
        // ... 親管理者非表示の項目だけを列挙 ...
    ];
@endphp

@foreach($menu_items as $item)
    @if(!$is_parent_admin || !in_array($item->path, $hide_for_parent, true))
        <li><a href="{{ $item->path }}">{{ $item->label }}</a></li>
    @endif
@endforeach
```

middleware も最小実装になります。

```php
// 認可違反時の redirect だけ、許可リストの定義は持たない
class EnforceParentAccessScope
{
    public function handle($request, $next)
    {
        if ($this->is_parent_admin
            && in_array($request->path(), self::HIDDEN_FOR_PARENT, true)) {
            return redirect('/');
        }
        return $next($request);
    }
}
```

何が変わったのか、言語化するとこうです。

- **既存 Laravel route が、唯一の Source of Truth として残った**。サイドメニューはその一覧から「不要なものだけ削る」形で生成される
- 許可リストを別途定義する必要がない (= 二重定義が構造的に発生不能)
- 「`/invoice` は存在しないのに表示してしまう」という事故は **そもそも発生しない**。存在しない route はメニュー候補に挙がってこないからです
- 親管理者向けに新しい route が追加された場合、明示的に hide リストに入れない限り **自動的にメニューに追加される**

「許可リスト」と「拒否リスト」は表面的には対称な仕組みに見えますが、Source of Truth との関係性が本質的に異なります。

> **§ 3 蒸留**: 「拒否リスト」approach は、既存資産 (route 一覧) を Source of Truth として残したまま「不要なものを引き算する」設計。二重定義が構造的に発生しないため、divergence による事故が起きない。

## 4. 構造的比較 — 許可リスト vs 拒否リスト

ここまでを構造的に整理します。

### 4-1. 設計思想の比較

| 観点 | 許可リスト (allow list) | 拒否リスト (deny list) |
|---|---|---|
| 思想 | 「触ってよい 15 項目」を **新規定義** | 既存メニューから「親管理者には **不要な項目を引き算**」 |
| Source of Truth | Constants クラス + 既存 route の **二重** | 既存 route **のみ単一** |
| 既存資産との整合 | サブセッションが全項目の存在を verify する責務 → 漏れる | 既存 route そのものが SoT → 構造的に保証 |
| typo / 不在 route | 表面化しない、環境テストで初検出 | そもそも発生不可 (既存 route から派生) |
| 新規メニュー追加時 | Constants も同期更新必要 | 自動的にメニューに含まれる (hide list にない限り) |
| 保守性 | Constants が「既存 Manager の真実」と divergence する潜在性 | divergence 構造的に発生不能 |
| AI コードレビュー時の見え方 | 単一責任が明確 → **肯定評価が出やすい** | 既存依存で「責務分散」に見える → 冷静に評価する必要 |

注目したいのは最後の行です。「許可リスト」approach の方が **AI のコードレビューで肯定評価を得やすい** という事実は、AI 時代の設計判断において重要な意味を持ちます (これは § 6 で深掘りします)。

### 4-2. コード量の比較

| 項目 | 許可リスト | 拒否リスト |
|---|---|---|
| 新規 Constants クラス | ~25 行 | 0 行 |
| 新規 middleware (許可リスト参照) | ~30 行 | ~15 行 (最小実装) |
| middleware alias 登録 (Kernel.php) | ~3 行 | ~3 行 |
| ServiceProvider 登録 | ~10 行 | 0 行 |
| view 側 in_array チェック | ~5 行 | ~5 行 |
| ルーティング側 alias 適用 | ~10 行 | 0 行 |
| 隠す対象の hide list 定義 (view) | 0 行 | ~15 行 |
| **合計** | **~83 行** | **~38 行** |

実際の実装で関連した変更行数 (テスト含む) はこれよりさらに膨らみ、許可リスト approach は約 150 行、拒否リスト approach なら ~30 行で済む見積もりでした。**約 5 倍の差** です。

### 4-3. 保守性の長期コスト比較

「変更量最小化」の便益は、初期実装よりも **長期運用** に効きます。

許可リスト approach の場合:

- 親管理者向けに新メニューを 1 つ追加 → Constants に 1 行追加 + view 側修正 + 場合によっては middleware も
- 既存メニューの path を改名 → Constants も同期改名 (忘れると壊れる)
- そもそも親管理者にだけ見せる新機能を作った時 → 設計者が「Constants にも追加するんだったな」と思い出す必要がある

拒否リスト approach の場合:

- 親管理者向けに新メニューを 1 つ追加 → 既存 route に追加するだけ、自動的に表示される
- 既存メニューの path を改名 → Laravel の route 改名で自動追従
- 親管理者にだけ見せたい場合 → hide list に入れないだけ

**変更量が少ないほど、変更時に「同期忘れ」のような事故が起きる接点が少ない**。これは保守性の本質です。

> **§ 4 蒸留**: 許可リスト vs 拒否リストの差は単なるコード行数の差ではなく、Source of Truth が単一か二重か、divergence が構造的に発生不能か潜在的に発生するか、の差。長期運用で効いてくる。

## 5. AI 時代でも変わらない 3 つの設計原則

ここから記事の核に入ります。

ユーザー指摘の最も重要な部分はこの一節でした。

> 要件が満たせるのであれば変更するコード量は少ないほど美しい。これは人間時代でもそうでしたが、AI 時代でも変わらないと私は考えます。

「人間時代でもそうでした」という言い方が示唆的です。これらは AI 時代に新しく生まれた原則ではなく、人間時代から不変の古典的設計原則です。AI 時代でも踏襲すべき、踏襲してこそ価値がある原則を、3 つに分解して整理します。

### 5-1. 既存実装を活かす原則

> 要件 X を実現する際、既存実装に **追加** で対応する前に、既存実装から **減算** で実現できないかを必ず検討する。

今回の事例でいえば、「親管理者用に 15 項目のメニューを作る」という要件に対して、

- **追加思考**: 親管理者用のサイドメニューを新規実装する → 許可リスト
- **減算思考**: 既存サイドメニューから親管理者には不要なものを除く → 拒否リスト

両方を比較したうえで「減算で済むなら減算」と判断するのが、既存実装を活かす原則です。

この原則の根底にあるのは、**既存実装にはチームの暗黙知 + 環境との整合性 + テストされた品質が織り込まれている** という事実です。新規実装を起こすたびに、その暗黙知の一部を再構築する必要が出てきます。Constants 化された許可リストは、「このサイドメニューは何で構成されているか」という既存実装の暗黙知を、別の形で再表現することになります。原本と写しが乖離すれば、暗黙知のレイヤーで事故が起きます。

### 5-2. コード変更量最小化の原則

> 要件が満たせるなら、変更行数が少ないほど良い。

この原則は、保守性 / バグ混入 risk / コードレビュー cost / ロールバック容易性 / 認知負荷 など、複数の観点から効きます。

- **保守性**: 変更行数 N に対して、その変更を将来読み返す回数は M (M >> 1)。N が小さいほど M × N の総コストが小さい
- **バグ混入 risk**: 変更行 1 行あたりに統計的に X% のバグが混入する。N が小さいほど期待バグ数が少ない
- **コードレビュー cost**: レビューア (人間 / AI 両方) が読み取って判断する量が N に比例
- **ロールバック容易性**: revert の影響範囲が N に比例
- **認知負荷**: 「この変更で何が変わったのか」を理解するコストが N に比例

「実装工数を tie-breaker から外す」という [姉妹記事の主張](https://zenn.dev/fixu/articles/ai-architecture-decision-beyond-effort) と本原則は矛盾しません。あちらは「堅牢性 vs 工数」軸での話で、堅牢性が同じなら工数差は意思決定の決め手にならない、という主旨でした。本原則は **「同じ堅牢性が達成できるなら、コード変更量は少ない方が良い」** という、堅牢性が確保されたあとの第二軸での話です。

両方を組み合わせると、AI 時代の設計判断の優先順位はこうなります。

1. **第一軸**: 堅牢性 (ドメインモデルの正しさ・長期運用コスト・認知負荷)
2. **第二軸**: 同じ堅牢性なら、コード変更量が少ない方を選ぶ
3. **第三軸**: 同じ堅牢性かつ同じコード変更量なら、実装工数が少ない方を選ぶ (これは tie-breaker)

### 5-3. Source of Truth 単一化の原則

> 真実 (route の存在 / 設定値 / マスターデータなど) は 1 箇所で管理する。複数箇所で重複定義すると、必ず divergence する。

これは DRY 原則の派生形ですが、「コード上の重複」より広い概念で、**情報源の重複** を扱います。

今回の事例:

- 既存 Laravel route 一覧 ← これが既存の SoT
- HTML mockup の path 表記 ← これは PdM の意図表現
- ParentSidebarAllowList::PATHS ← これは AI が新規定義した「写し」

3 箇所の情報源が同期している必要がある状態は、本質的に脆い。1 箇所だけ更新が漏れると整合が崩れます。「拒否リスト」approach に切り替えると、Source of Truth は既存 Laravel route 一覧の 1 つに収束します。

> **§ 5 蒸留**: AI 時代でも踏襲すべき古典的設計原則は、(1) 既存実装を活かす、(2) コード変更量最小化、(3) Source of Truth 単一化 の 3 つ。これらは人間時代から不変であり、AI が「綺麗そうな新規実装」を量産しがちな時代だからこそ、より意識的に踏襲する必要がある。

## 6. AI 時代特有の罠 — 「綺麗そうな新規実装」を量産しがち

ここからが、AI 時代特有の論点です。

なぜ今回、サブセッションは「許可リスト」approach を選んだのか。後付けで分析すると、AI には以下のような構造的バイアスがあるように見えます。

### 6-1. AI は「既存読まずに新規生成」の誘惑に弱い

AI に「親管理者用のサイドメニューを実装して」と指示した場合、AI が取り得る approach は大きく 2 通りあります。

- (a) 既存 Manager のサイドメニュー実装 (`resources/views/manager/partials/sidebar.blade.php` 等) を熟読し、そこから「親管理者には不要な項目」を引き算するパッチを書く
- (b) 親管理者用に新しい構造 (Constants クラス + middleware + view 修正) を起こして、要件にある 15 項目を組み立てる

(a) の方が SoT を単一化できる優れた approach ですが、**AI にとって認知的なコストが高い** のです。理由は以下の通りです。

- (a) は既存実装を全面的に読み込む必要がある (~30 項目のサイドメニューロジック、メニュー描画の Blade 構造、関連 Controller など)
- (a) は既存実装の前提に依存するパッチになるため、汎用性が低い (= 学習データの中で「典型的な解法」として現れにくい)
- (b) は学習データに溢れる「綺麗な責務分離パターン」(Constants + middleware + ServiceProvider) のテンプレートに乗りやすい
- (b) はコードレビューでも肯定評価を得やすい (前述 § 4-1 参照)

つまり AI は、**「既存資産を読むコストを払って減算する」より「学習データのテンプレートに沿って新規定義する」方を選びがち** という構造的バイアスを持ちます。これは Claude や他の LLM の本質的な特性で、明示的に文脈を与えない限り、デフォルトでこの誘惑に流れます。

### 6-2. kickoff Phase 0-6 の Alternative Design に「既存活用 vs 新規定義」軸を必ず含める

[task-kickoff プロトコル](https://zenn.dev/fixu/articles/task-kickoff-ai-design-protocol) では、設計タスクの着手前に AI 自身に Alternative Design を 3 案以上列挙させる Phase 0-6 を設けています。今回の事例で振り返ると、AI が出した Alternative Design は「許可リスト approach」のバリエーション (Constants の置き場所、middleware の名前、ServiceProvider 登録の有無) に偏っており、**「拒否リスト approach」が選択肢として視野に入っていなかった** ことが分かります。

これは Phase 0-6 の運用に明示的なチェック項目を追加することで、構造的に防止できます。

> Phase 0-6 強制チェック (拡張案):
> - **既存資産活用 approach** (既存実装 + 引き算) を必ず Alternative Design の 1 つとして列挙する
> - **新規定義 approach** (Constants / 新規 middleware / 新規 class) を選んだ場合、**なぜ既存資産活用では実現できないか** を明示する
> - 両者のコード変更量を概算で比較する

このチェックを入れていれば、「許可リスト approach」を選ぶ前に「拒否リスト approach も検討した結果、こちらが優位」という意思決定の透明性が確保されます。実際には拒否リスト approach の方が優位だと気付くはずなので、最初からそちらを選べた可能性が高い。

### 6-3. テスト設計の DoD に「環境 verify」を必須化する

もう一つの構造的対策は、テスト設計担当のサブセッションの DoD (Definition of Done) に **「コードベース + 既存環境での挙動 verify」を必須化** することです。

今回の事例では、許可リストの 15 項目について「Laravel route として実在するか」を verify するステップが、テスト設計の DoD に明示的に含まれていませんでした。Unit テストでは、Constants の中身と middleware のロジックを検証することはできても、「Constants の中身が既存 Laravel route と整合しているか」までは catch できません。

AI 時代の利点は、**この verify が並列 grep + 環境 curl で安価に実施できる** ことです。

```bash
# 例: 許可リストの 15 path が dev02 で実在するか並列 verify
for path in / /space_management /account /employee /holiday /news \
            /setting /plan /plus/plan /payment /credit /invoice \
            /cms_web /term /template; do
    curl -sL -o /dev/null -w "%{http_code} $path\n" \
         "https://manage.dev02.example.com${path}"
done
```

人間がやれば手間ですが、AI なら 30 秒で終わります。AI 時代のテスト設計 DoD は、**人間時代より厚くできる**。むしろ厚くすべきです。

> **§ 6 蒸留**: AI には「既存読まずに新規生成」の構造的バイアスがある。kickoff Phase 0-6 の Alternative Design に「既存活用 vs 新規定義」軸を必ず含めること、テスト設計 DoD に「環境 verify」を必須化することで、構造的に対策できる。AI による検証コストの安さは、対策の実装可能性を高める方向に効く。

## 7. アンラーニングと踏襲の見極め

冒頭のユーザー指摘の最後の部分を再掲します。

> アンラーニングすべきことと、踏襲すべきことの見極めが重要ですね。

AI ネイティブ化の文脈で語られる「アンラーニング」は、しばしば **「古い前提を全部捨てよ」** というメッセージとして受け取られがちです。しかしユーザーの指摘は逆向きで、**「アンラーニングすべきものと、踏襲すべきものを見極めよ」** という、より精緻な姿勢を要求しています。

整理するとこうなります。

### 7-1. AI 時代でアンラーニングすべきもの

| アンラーニング対象 | 旧前提 | 新前提 |
|---|---|---|
| 実装工数の希少性 | 工数は希少資源 → 工数最小化が tie-breaker | AI で工数は圧縮される → 堅牢性で決める ([詳細](https://zenn.dev/fixu/articles/ai-architecture-decision-beyond-effort)) |
| 計測コストの高さ | 計測は半日仕事 → 推測で即決 | 計測は 10 秒 → まず計測 ([詳細](https://zenn.dev/fixu/articles/measure-dont-guess-ai-native)) |
| 並列度を上げれば速い | 人間工数稀少 → 並列度最大化 | デバッグ範囲最小化が新パラダイム → 並列度抑制 ([詳細](https://zenn.dev/fixu/articles/ai-era-courage-not-to-rush)) |
| AI に新規実装を任せれば cost ゼロ | 工数 cost が低い → 量を出して OK | AI ほど「綺麗そうな新規実装」の罠に陥りやすい → 既存活用を意識的に選ぶ (本記事) |

### 7-2. AI 時代でも踏襲すべきもの

| 踏襲対象 | 原則 | 不変な理由 |
|---|---|---|
| 既存実装を活かす | 追加より減算を先に検討 | 既存資産にはチームの暗黙知が織り込まれている |
| コード変更量最小化 | 要件が満たせるなら変更行数は少ない方が美しい | 保守性 / バグ risk / レビュー cost / 認知負荷 全てに効く |
| Source of Truth 単一化 | 真実は 1 箇所で管理 | 重複は必ず divergence する |
| ドメインモデルの正しさ | 実装工数より堅牢性 | AI で工数 cost が下がっても堅牢性の便益は変わらない |
| 認知負荷を意識する | 読むコストを見積もりに含める | コードは書くのは 1 回、読むのは N 回 |

両者を区別する判断軸はこうです。

- **アンラーニング対象**: AI によってコスト構造そのものが変わったもの (工数、計測、並列度、新規実装)
- **踏襲対象**: AI によってコスト構造が変わらない、あるいは変わってもなお価値が変わらないもの (堅牢性、SoT 単一化、認知負荷)

「AI が安くしたものに依存した経験則を、順番にアンラーニングしていく」というスタンスは正しい。同時に、「AI が安くしなかった (= 本質的価値を持つ) 古典的原則を、踏襲していく」スタンスも同じくらい重要です。両者をバランス良く運用することが、AI ネイティブ時代のエンジニアの新しい技能になりつつあると感じています。

> **§ 7 蒸留**: アンラーニングと踏襲は対立する概念ではなく、AI が変えた前提と変えていない前提を見極めるという、同じ姿勢の表裏。アンラーニングだけを推進すると、踏襲すべき古典的原則まで捨ててしまう。

## 8. 明日からの行動変容

抽象論で終わらせないために、具体的な行動に落とします。

### 8-1. 設計レビューに「既存活用 vs 新規定義」軸を加える

設計レビューで AI が提示した実装案を見たら、以下を問います。

- 「この実装は新規定義か、既存資産からの引き算か?」
- 「新規定義の場合、なぜ既存資産からの引き算では実現できないのか? その判断は明示的に行われたか?」
- 「Source of Truth は何か? 二重化していないか?」

AI のコードレビューが「単一責任が明確で良い」と返してきても、それだけでは不十分です。**「既存資産との整合」軸での評価** を、人間レビューアが意識的に重ねる必要があります。

### 8-2. kickoff Phase 0-6 の Alternative Design テンプレートを更新する

設計タスク着手時の kickoff (詳細は [task-kickoff プロトコル](https://zenn.dev/fixu/articles/task-kickoff-ai-design-protocol)) で、Alternative Design の列挙テンプレートに以下を追加します。

```
Alternative Design 必須軸:
- 案 X: 既存資産活用 approach (既存実装からの引き算で実現)
- 案 Y: 新規定義 approach (Constants / middleware / class 等を新規追加)
- 案 Z: ハイブリッド approach
評価軸:
- コード変更量の概算
- Source of Truth の単一性
- 既存資産との整合
```

このテンプレートを skill / プロトコルレベルで永続化することで、AI が「既存読まずに新規生成」のデフォルトに流れる構造的バイアスを、運用レベルで catch できます。

### 8-3. テスト設計 DoD に「環境 verify」を必須化する

テスト設計担当のサブセッションの DoD に、以下を必須項目として追加します。

- コードベース全体での grep verify (関連シンボルの存在 / 使用箇所)
- 既存環境 (dev / dev02 等) での挙動 verify (curl / API call / DB query)
- 上記が完了するまで、テストケースの設計は完了とみなさない

AI 時代の利点は、これらの verify が安価で並列に実施できることです。「人間時代より厚いテスト DoD」を設計するチャンスとして使うべきです。

### 8-4. 「コード変更量」を見積もりに含める

実装工数の見積もりに、**「変更行数」** を必ず含めます。同じ要件を満たす A 案と B 案で、変更行数が 5 倍違うなら、それは意思決定の重要なインプットです (堅牢性が同じ前提で)。

同時に、**「将来の変更量」** も見積もります。新規メニュー追加時、path 改名時、要件変更時に、A 案と B 案でそれぞれ何行の変更が必要かを想像する。今回の事例だと、許可リスト approach は新規メニュー追加で Constants + view + middleware の 3 箇所更新、拒否リスト approach は既存 route 追加のみ、の差です。

## まとめ

AI 時代に新しく学ぶことの量は確かに多いですが、それと同じくらい、人間時代から **踏襲すべき古典的設計原則** があります。

> **要件が満たせるならコード変更は少ないほど美しい。これは人間時代でもそうでしたが、AI 時代でも変わりません。**

AI が「綺麗そうな新規実装」を量産しがちな時代だからこそ、既存実装を活かす選択を意識的に取る必要があります。許可リスト vs 拒否リストの選択は、その本質を象徴する具体例でした。

| 観点 | 許可リスト | 拒否リスト |
|---|---|---|
| Source of Truth | 二重 (Constants + 既存 route) | 単一 (既存 route) |
| コード変更量 | ~150 行 | ~30 行 (約 5 倍少) |
| AI が選びがち | ✅ (テンプレート的に綺麗) | (既存読み込みが必要で認知 cost 高) |
| 環境 verify なし時の事故 risk | 高い (今回 4 項目で顕在化) | 構造的に低い |
| 長期保守性 | divergence 潜在 | divergence 構造的に発生不能 |

AI 時代のエンジニアは、AI が出してきた「綺麗そうな新規実装」を、**「もっと変更量を減らせないか」** という古典的な問いで受け止め直す技能を持つ必要があります。アンラーニングすべきことと踏襲すべきことの見極めが、その技能の核心です。

次にあなたが AI から実装案を受け取ったら、こう問いかけてみてください。

> **その実装、既存実装からの引き算では実現できませんか?**

その問いに即答できないなら、たぶん引き算 approach の方が正解です。
