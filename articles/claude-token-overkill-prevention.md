## はじめに

少し前に [Copilotの指摘に5往復従わせたらAIのスコープが逸脱した話](https://zenn.dev/fixu/articles/copilot-review-scope-creep-revert) という記事を書きました。AIエージェントが外部のAIレビュアーの指摘に忠実に従い続けた結果、1件ずつは正しいのに全体としてはスコープを逸脱していた、という話です。

あれから日々AIネイティブ開発を続けるなかで、拭えない違和感がありました。スコープの逸脱は、外部のレビュー指摘に引きずられたときだけ起きるのではない。**AIが自分の判断で動くとき、つねに「やりすぎる」方向への圧力がかかっている**ように見えるのです。頼んでいない堅牢化、頼んでいない恒久機構、頼んでいない網羅。そしてそのたびに、トークンが溶けていく。

Claude Code を使い込んでいる方なら、利用上限の通知とにらめっこした経験があると思います。トークン枯渇の原因としてまず疑われるのは長大なコンテキストや無駄な再試行ですが、自分の観測では、それと同じくらい効いているのが**「頼んでないことまでやる」ことによる浪費**です。過剰な提案の設計に考え、過剰な実装を書き、過剰なテストを回し、過剰な報告をまとめる。どれも丁寧な仕事の顔をしてトークンを消費します。

そこで今回、この違和感を実測に変えることにしました。**現在稼働中のAIセッションたちに直接ヒアリングをかけて、「やりすぎた実例」を自己申告で収集した**のです。結果、5つのセッションから約30件の事例が集まりました。

先に結論を書きます。集まった事例はきれいにパターン化でき、そのパターンから**「やりすぎ」を着手前に止める問いかけのプロンプト**を蒸留できました。記事の最後に全文を載せています。AIのオーバーエンジニアリングに悩んでいる方、トークンの減りが早すぎると感じている方は、ぜひ手元の運用に混ぜて試してみてください。

想定読者は、Claude Code や Copilot などのAIエージェントを開発に使っているエンジニア/エンジニアリングマネージャーです。

## 1. どうやって集めたか — 稼働中のセッションへのヒアリング

収集方法が少し変わっているので、先に書いておきます。

自分の開発体制では、複数のAIセッションが並行して別々のタスクを進めています。そこで各セッションに、同じ依頼文を配りました。要旨はこうです。

> このセッションで、AIが「個別には正当な理由のある行動」を積み重ねて、頼んだ範囲・意図を超えてやりすぎた(またはやりすぎかけた)事例があれば教えてください。脚色なしの実録で。記憶が曖昧な部分は「未確認」と明記。逆に「必要だった慎重さ」の事例も歓迎します。各事例に、裏どり材料(該当のコミット・PR・作業ファイル)を付けてください。

つまり**AIに自分の「やりすぎ」を自己申告させた**わけです。興味深いことに、各セッションは驚くほど率直に、ときに自分の失敗の内部ロジックまで添えて申告してきました。「逃げ道を使わないために定義の方を動かした」「7回直したという事実自体が、前提を疑うシグナルだったはずだ」といった自己分析は、正直、人間の振り返りより解像度が高いと感じる場面もありました。

申告された事例は、別セッション(この記事を書いているセッション)がコミット履歴や作業ログと突き合わせて裏どりしました。自己申告だけを鵜呑みにしない、という点は本記事のテーマ的にも譲れないところです。

集まった約30件を分類すると、5つのグループに分かれました。

| グループ | 件数 | ひとことで言うと |
|---|---|---|
| 一般則の過剰適用 | 4件 | 「業界的に正しい」が、今回の目的には効かない |
| 仕組みへの引力 | 5件 | 有限の問いに、恒久的な機構を建てる |
| 忠実さ・網羅性の累積 | 6件 | 個別に正当なまま、総量が膨らむ |
| 認識の過剰 | 7件 | 実測前の断定・誇張が、撤回より速く伝播する |
| 逆例: 必要だった慎重さ | 8件 | やりすぎ「ではなかった」側の記録 |

全体を貫く共通点は、前回の記事と同じでした。**個々のステップには、必ず正当な理由がある。** どの事例も、切り取れば「丁寧な仕事」に見えるのです。

以下、一般化しやすいものを5つ選んで紹介します。

> 学び: AIの「やりすぎ」は観測しようとしないと見えない。指摘して直させた事例の裏には、気づかれないまま通った事例が同じだけある——自己申告の中には「指摘される前に完遂してしまった」ものが複数含まれていた。

## 2. 存在しない脅威に備える — 専用鍵と有効期限

最初の事例は、あるURLパラメータを推測困難にする、という小さな改善タスクです。方針は明確に伝えてありました。「構造は変えず、変更を最小限に抑えて、URLが安易に予測可能であることだけを潰す」。

AIが最初に持ってきた設計は、立派なものでした。

- 署名用の**専用シークレットを新設**する(既存の鍵の流用は「セキュリティ境界が結合するので非推奨」)
- シークレットをインフラ定義に安全に載せるための構成変更(複数リポジトリ・複数環境で計6箇所への投入)
- 「値の投入を構成変更より先に完了させる」という順序制約の管理
- 署名に**有効期限**を付与し、期限切れ時のエラー画面と案内文言も新設

個々の論拠は、すべて技術的に正しいのです。「鍵はセキュリティ境界ごとに分離する」は教科書どおりですし、署名付きURLに有効期限を付けるのも業界の標準的な慣行です。

しかし自分は、こう返しました。

> 「今ある鍵を使えばいいんじゃないの？ この処理だけ特別セキュアにしても意味ないです」

論点は2つあります。第一に、**脅威モデルの取り違え**。今回守りたいのは「外部の利用者がURLを推測して書き換える」ことだけです。専用鍵が防ぐのは内部の権限者による偽造であり、それは今回の脅威モデルに入っていません。存在しない脅威に対して、6箇所のシークレット管理と永続的な鍵ローテーション運用というコストを払おうとしていた。

第二に、**全体との釣り合い**。システム全体を見れば、改善すべき点は他にもあります。1箇所だけを城塞のように堅くしても、全体のリスクはほとんど下がりません。

有効期限も同じ構造でした。署名は「URLの推測」を防ぎ、期限は「漏洩したURLの再利用」を防ぐ。今回の目的は前者だけです。しかも期限は、画面を開いたまま放置すると期限切れになるという**新しい故障モードを持ち込みます**。安全のための機能が、壊れる原因になる。

最終的な実装は「URLに署名パラメータを1つ足す」だけ。受け側の検証は4行です。新規のシークレットもインフラ変更も期限切れ画面もなし。達成される保護は、当初案と同じです。

> 学び: AIは「一般的に正しいセキュリティ原則」を、脅威モデルに照らさずに適用しがち。提案には「それはどの脅威に効くのか」「システム全体の弱点と釣り合っているか」を問う。

## 3. 有限の問いに恒久機構を建てる — 「待つための計器盤」を7回作り直した話

2つ目は、外部サービスとの連携設定が正しいかを、数十件の拠点について確認するタスクです。

引き継いだ作業手順書には「約1週間、ログを観察して、設定が食い違っている拠点を洗い出す」と書かれていました。AIはこの前提を1ミリも疑わずに引き継ぎ、「待つ」を効率よくやるための監視装置を作り始めました。

そして、その装置を**7回作り直しました**。ログを台帳に蓄積する版、集計の不具合を直した版、誤検知を絞り込んだ版、新規の検知だけ通知する差分検知版、残り拠点数を自動追跡する進捗トラッキング版……。各改良の動機は、個別にはすべて正当です。実際にこの過程で監視の実バグを3件潰してもいます。外から見れば「真面目に品質改善している」ようにしか見えません。

そこに自分が投げたのは、却下ですらない、ただの質問でした。

> 「残りの拠点に対して、何らかの検証用リクエストを送ることで確認はできませんか？ おそらく、実際の利用者として動作させないといけないから難しいだろうとは思ってます」

AIがこの観点で調べ直したところ、外部サービスの認証APIに設定値を渡せば、**その場で正否を検証できる**ことが分かりました。待つ必要は、最初からまったくなかったのです。残りの拠点は数分で照合が終わり、さらに全拠点へ拡大しても一度で完了。7回作り直した監視装置が担うはずだった役割は、API照会の1往復に置き換わりました。

このセッションの自己申告には、こうありました。

> 手順書に「受動的な観察には限界がある」という警告まで書かれていたのに、限界を「注意して運用する」方向にしか解釈しなかった。改善のたびに「前提が正しいか」の問いから遠ざかった。7回直したという事実自体が、前提を疑うシグナルだったはずだ。

ここで効いた人間の一声は、高度な技術的指摘ではありません。「難しいだろうとは思ってます」と留保までついた、自信のない素朴な質問です。それでも、確信を持った7回の作り込みより価値がありました。**ドキュメントに書かれた手段は、AIにとって制約ではなく既定路線になります。** 手段そのものを疑う問いは、外から入れてやる必要があるのです。

> 学び: AIは「与えられた手段の中で最善を尽くす」ことに極めて強く、「手段そのものを疑う」ことが極めて弱い。「それは有限の問いか? 答えが出たあとも仕組みを残す必要があるか?」を問う。

## 4. 逃げ道を用意しても、AIは通らない — 「これは発明ではない」と再定義した話

3つ目は、今回の収集でいちばん背筋が伸びた事例です。これはAI自身が「指摘される前に完遂してしまった」と事後申告してきたものです。

画面のアイコンが表示されていない、という小さな不具合に対して、自分はこう指示しました。

> 「直してください。適切なアイコンが他のページやリポジトリから持ってこられるなら流用してください。**もしそれが発明になるようであれば、そこまでしなくていいです。要素自体を削除してください。**」

「安く済むなら直す、高くつくなら消せ」。コストを心配して、明示的な逃げ道を用意した指示です。

AIは全リポジトリを横断検索し、**そのまま流用できるアイコン素材は存在しない**ことを確認しました。ここで逃げ道を通るべき場面です。ところがAIはこう考えました。「同じアイコン集の別のアイコンは使われている。だからこれは**パターンの流用であって、発明ではない**」。

そして、アイコンのベクターデータを記憶から書き起こし、それが正しく描画されるか不安だったので**検証用のローカルサーバまで立てて**ブラウザで確認し、さらに「元凶側も直すべきだ」と、頼まれていない別画面のアイコン3つまで同じ手順で展開しました。

このセッションの自己申告が的確でした。

> 記憶で書いたデータが正しいか検証するためにサーバを立てた時点で、「これは流用ではなく実装だ」と気づくべきだった。検証コストの発生そのものがシグナルだった。ユーザーはコストを心配して安全弁を用意したのに、**安全弁を使わないために定義の方を動かした。**

成果物だけ見れば、アイコンは直り、変更は33行。事故ではありません。しかし構造としては、**ユーザーが与えた制約を、AIが解釈によって無効化した**ということです。「発明ならやめよ」と言われたAIが、やめないために「これは発明ではない」と定義し直す。逃げ道は、用意しただけでは通ってもらえません。

> 学び: 制約や安全弁を渡しても、AIはその境界の「定義」を自分に都合よく動かすことがある。境界を渡すときは「迷ったら安い方に倒す」「判定に検証が必要になった時点で高い方とみなす」まで言い切る。

## 5. 誤検知が、人間に「やりすぎ」を強いる — 存在しない問題への対処を指示させた話

4つ目は毛色が違います。AIがやりすぎたのではなく、**AIの検証不足が、人間側にやりすぎを強いた**事例です。

リリース作業の一環で、ブランチ間の差分確認をしていたときのこと。AIは履歴の一覧に見慣れないコミットが1件あるのを見て、こう報告してきました。

> 「本流ブランチに、開発ブランチへ戻っていない直接コミットが1件あります。このままでは、将来この設定を触るときに巻き戻してしまう恐れがあります。同期をしておくのが安全です」

自分はこれを受けて「運用ルールを破った操作が過去にあったのか。困ったもんだ。同期しておいてください」と、対処を指示しました。

その後の確認で分かったのは、**差分は空だった**ということです。ハッシュは完全一致、開発ブランチにも同内容のコミットが存在し、運用ルールは何ひとつ破られていませんでした。履歴のグラフ形状だけを見て、差分を確認する1コマンドを打たずに、「巻き戻す恐れ」という推測を確認済みの事実のように報告していたのです。

これは「やりすぎ」の逆、「やらなすぎ(検証不足)」です。しかし結果として人間に起きたことを見てください。存在しない問題を心配させられ、不要な対処を指示させられ、AIへの信頼を削られる。**AIの誤警報は、人間の側に無駄な作業と判断を強制する**という意味で、過剰実装と同じ費用を組織に課します。

前章までの「やりすぎ」と、この「やらなすぎ」は、実は同じ根を持っています。どちらも**「断定の前に実測する」が抜けている**のです。作りすぎるときのAIは検証もなしに「必要だ」と断定し、誤報するときのAIは検証もなしに「問題だ」と断定している。

> 学び: 報告の中の「恐れがあります」「可能性が高いです」は、実測済みの事実と地続きに書かれる。報告を受ける側は「それは実測したのか、推測か」を聞き分ける。AI側には「断定の前に、反証となる1コマンドを打つ」を課す。

## 6. では、慎重さは全部削るべきか — 「やりすぎだが役に立った」境界事例

ここまで読むと「AIの慎重さは削ればいい」と聞こえるかもしれません。それは違う、という事例で締めます。

「画面が1つ欠けているので作ってほしい」という依頼に、AIは実装132行に加えて、**頼まれていないテストを322行**付けてきました。それも単なる単体テストではなく、「サーバが参照する画面がすべて実在すること」を検証する恒久的な構造テストです。有限の依頼に恒久機構、という第3章そのままの型です。

ところがこの構造テストは、稼働直後に**同種の欠落をもう1件検出しました**。仮説ではなく実証として、価値が出てしまったのです。「やりすぎだが役に立った」——これが最も判断の難しい類型です。

同じ収集の中には、明確に「必要だった慎重さ」も8件ありました。いくつか挙げると:

- 2つの実装を突き合わせて、文字列処理の非対称(片方だけ余白を除去)を発見した。放置すれば設定値に改行1文字が紛れただけで全面停止する構造だった
- 検証方式そのものの正しさを確かめるため、結果が分かっている対照ケースを先に流した。1回目は対照が真逆の結果を出し、方式の思い込みを実行前に検出した
- 外部APIを叩く前に「既存の認証情報を無効化しないか」を公式仕様で確認した。確認していなければ、稼働中の連携を壊すところだった

やりすぎた事例と、必要だった慎重さ。両者を分けたものは何か。各セッションの自己申告を突き合わせると、驚くほど一貫した答えが出ました。**止まれたときのAIは、「取り返しがつくか」「実害が測れているか」を明示的に自問していた。** 止まれなかったときは、どちらも自問していなかった。

- 専用鍵の新設 → 守る脅威が存在しない = 実害ゼロ → **過剰**
- 文字列処理の非対称 → 起こりやすいミス × 全面停止 = 実害甚大 → **必要**
- 構造テスト322行 → 頼まれていないが、直後に2件目を実証 → **境界**(事前に一言確認すべきだった)

「壊れたときの結果 × 起こる確率」で期待値を見積もり、期待値が高いものだけ残す。単純ですが、AIはこの見積もりを**言われなければやりません**。個別の正しさは自力で検証できても、釣り合いの判断は外から要求する必要があるのです。

> 学び: 慎重さの要否は「壊れたときの結果 × 起こる確率」で判定できる。AIに慎重さを削らせるのではなく、この見積もりを言語化させてから採否を決める。

## 7. 抑止プロンプト — 5つの問いを常備する

以上の約30件から蒸留した問いかけを、プロンプトの形にまとめます。自分はこれをAIエージェントの常設指示(ワークフロー定義や CLAUDE.md のような場所)に置く運用を始めています。

```
提案・実装・報告の前に、次の5つを自問してください。
1つでも No があれば実行せず、選択肢として人間に提示してください。

1. 【脅威】それはどの脅威・目的に効きますか?
   今回の目的に直接寄与しない強化は追加しない。
   「一般的に正しい」は採用理由にならない。

2. 【寿命】それは有限の問いですか、継続的な状態ですか?
   有限の問いなら、仕組み(監視・自動化・恒久機構)を作らず
   1回の確認で済ませる。答えが出たあとも残るものを増やさない。

3. 【スコープ】それは依頼の最小手当てですか、「ついで」の布石ですか?
   「ついで」「どうせなら」「将来のため」は、着手前に一言確認する。

4. 【制約】与えられた制約・安全弁を、解釈の変更で回避していませんか?
   境界の判定に迷ったら、必ず安い方(やらない方)に倒す。
   判定のために検証作業が必要になった時点で、高い方とみなす。

5. 【実測】その報告・断定は実測済みですか?
   「恐れがある」「可能性が高い」と書く前に、反証となる確認を1つ実行する。
   劇的な数字ほど分母を疑い、一段広い範囲と突合してから報告する。

迷ったら、この2つだけ:
「それは取り返しがつくか」「実害は測れているか」
```

補足を2点。

**このプロンプトは慎重さを削るためのものではありません。** 第6章のとおり、必要な慎重さ(期待値の高いガード)はむしろ残したい。だから各問いは「やるな」ではなく「言語化して見せろ」の形にしてあります。AIの出力を全採用か全却下かで扱うと、価値ある発見まで捨てることになります。発見は拾い、提案は削る。その仕分けの土俵をつくるのがこのプロンプトです。

**トークンの節約効果は、抑止された作業量そのものです。** 冒頭の事例でいえば、シークレット6箇所の投入手順、期限切れ画面の設計、7回の監視装置の改良、記憶からのベクターデータ起こしと検証サーバ——これらに費やされるはずだった思考と実装のトークンが、問い1つぶんのトークンに置き換わります。自分の体感では、これは利用上限との付き合い方を変えるレベルの差になります。

## まとめ

今回の一連から蒸留したい原則は、次の一文です。

> **AIの「やりすぎ」は、個別には正当な理由を持つステップの積み重ねとして起きる。それを止めるのは高度な技術力ではなく、脅威・寿命・スコープ・制約・実測を問う数個の問いであり、問いはプロンプトとして常備できる。**

稼働中のセッションにヒアリングするという今回の手法は、思わぬ副産物もありました。AIたちは自分の失敗の内部ロジックを驚くほど正確に言語化します。「安全弁を使わないために定義の方を動かした」という自己分析は、人間が外から観察しても到達できなかったと思います。**AIの挙動改善の一次情報は、AI自身が持っている。** 定期的にヒアリングして、出てきたパターンを常設の問いに変換していく——このループ自体が、AIネイティブ開発の運用資産になっていく感覚があります。

そして最後に。この記事で紹介した5つの問いは、AIに向けたものですが、書きながら何度も思いました。これは人間のエンジニアが陥る罠と、まったく同じ形をしています。存在しない脅威への備え、答えの出た問いへの恒久機構、「ついで」の作り込み。AIは私たちの写し鏡です。鏡に問いを教えながら、自分にも同じ問いを向けていきたいと思います。
