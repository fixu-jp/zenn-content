## はじめに

少し前に [AIへの丸投げと細部の業務設計 — サブセッション自走化で見えた明暗の分岐](https://zenn.dev/fixu/articles/subsession-self-drive-guardrails) という記事を書きました。Laravel 8→12、PHP 8.1→8.3、alpine への切り替えというミドルウェアの更新を、9 つのリポジトリで横断して進めたときの話です。サブセッションに自走させるときに見えてきた 7 種類のリスクと、親セッションに組み込んだ監視の仕組みをまとめました。

あれから 2 週間ほどで、同じ 9 リポジトリは次の段階に進みました。キャッシュ・ログ・キュー・ファイルアップロードをコンテナの外に出す、ステートレス化です。前作で整理した 7 種類のリスクは、起動プロンプトの調整と、全サブセッションへの一斉通知で、実務上はかなり抑えられるようになっていました。

ところが、その先で **複数の AI を重ねた体制（実装サブ・親・第三者の監査サブ・Copilot レビュー）の全層をすり抜けた、重大インシデント未遂** が起きました。見つかったのは、人間（筆者）があとから「もっと踏み込んだ回帰テストはできそう？」と追加で頼んだからです。頼んでいなければ、9 リポジトリすべてに「✅ 完遂」と表示されたまま本番に反映され、お客さまの側で問題が表に出るところでした。

さらに前の記事 [AI開発でユーザーの判断軸が効いた1日 — Claude × Copilot と作るインフラの現実](https://zenn.dev/fixu/articles/day051-ai-human-collaboration) では、「人間の判断軸 × AI の実行速度 × 複数の視点によるレビュー」の三層で品質が決まる、と書きました。あのときの人間の役割は、Claude の暴走をその場で正すことでした。今回は構造が一段違います。**複数の AI と Copilot レビューが日常の運用になっても、AI の全層が通してしまうケースは残る。** そこに、人間が批判的に問い直す最終層を組み込まないと、業務設計として閉じない。そういう体験でした。

この記事に書くのは、次の 4 点です。

- 複数の AI と Copilot レビューで、コードの面の体制はかなりできてきたこと（実測値つき）
- それでも見つけられなかった構造的な盲点が、「確認がどの経路を通ったか」の層にあったこと
- AI の多層防御が、なぜ全層で通してしまったのかの構造の分析
- ここを「コードと同じ手触り」で塞ぐテスト・監査・QA のやり方はまだ手探りで、知見を求めていること

先に結論めいたことを書くと、こうなります。

> **複数の AI を重ねても見つけられない、気づいていないこと（unknown unknowns）はある。人間の役割は「実行」から「批判的に問い直す + 無いものを疑う」へ移る。**

これが今回いちばん強く残った手触りです。

## 1. 前作からの差分 — 7 種類のリスクは抑えた、その先に何があったか

前作の続編なので、まず構造の違いを表にします。

| 観点 | 前作（ミドルウェアの更新） | 今回（ステートレス化） |
|---|---|---|
| 主作業 | Laravel・PHP・alpine の大きな版上げ | キャッシュ・ログ・キュー・ファイルアップロードを ECS Fargate 前提で外に出す |
| AI の構成 | 実装サブ + 親 + Copilot レビュー | 実装サブ + 親 + **第三者の監査サブ** + Copilot レビュー |
| 抑える対象 | 自走運用の構造リスク 7 種類（証跡・判断の質・エスカレーション漏れ・機械的な判断・自走の副作用・経路への依存・進捗管理） | **確認の経路が本物か** — 前作で整理しきれていなかった層 |
| 人間の主な役割 | 自走運用の監視（巡回・監査・可視化） | **AI の多層防御のあとの最終的な問い直し（「無いもの」を疑う）** |
| 主な発見 | 細部の設計の積み重ねが明暗を分ける | 多層防御は「同じモデル由来」だと独立性が稼げない |

前作の 7 種類は、起動プロンプトの調整と一斉通知で、実務上はかなり抑えられました。サブセッションは、対象外と判断したときに必ず Copilot へ返信するようになり、9 リポジトリ共通の基準は一斉通知でそろいます。証跡は残り、エスカレーションも回ります。

ただ、「これで自走運用は安全に閉じた」と思った瞬間に、別の層の盲点が立ち上がりました。**その確認は、本当に実際の利用者が通る経路で行われたのか**、という問いです。これは 7 種類のどれにも当てはまらない、確認の設計に固有の問題でした。

> **前作との差分**: 前作はサブの「行動」を律する話、本作はサブの「確認の設計」を律する話。

## 2. コードの面では体制ができてきた — Copilot レビュー平均 1.5 ラウンドの実測

まず、対策側の今の状態を率直に書きます。

コードの変更については、Claude（実装サブ）が PR を作り、GitHub Copilot のコードレビューをかける、という体制がかなり機能するようになりました。Copilot は Claude とは別の系列の AI レビュアーです。AI 同士でも、モデルの系列が違えば、ある程度は独立した視点を持ち込めます。

実測値も取りました。Day062 以降の約 12 日間に、9 リポジトリでマージされた PR を集計すると、次のとおりです（執筆時点）。

| 指標 | 値 |
|---|---:|
| 期間 | Day062〜（約 12 日間） |
| 集計対象 PR | 247 件（マージ済み） |
| Copilot レビューが付いた PR | 195 件（79%） |
| **Copilot レビューの平均ラウンド数** | **1.5 ラウンド** |
| 1 ラウンドで収束した割合 | 73% |
| 2 ラウンド以上（往復が発生） | 27%（53 件） |

「ラウンド」は、Copilot のレビューが PR に投稿された回数です。1 回目で指摘なし、または軽い指摘だけですぐマージできた PR が 7 割。1 回目で指摘 → 対応 → 2 回目で収束、という往復があったものが 2 割強。重い議論で 4〜6 ラウンドまで行った PR も 5% ありました。

体感としては、「コードのレビューの観点では、おおむね体制として機能している」と言えます。Claude が一人で書いて一人でマージする状況に比べれば、視点の独立性は確実に一段増えました。前々作で書いた三層のうち、**複数の視点によるレビューの軸は、コードの側ではかなり整った。** これは確かな進歩でした。

ところが、この記事の核はここからです。**この体制は、テスト・監査・QA の観点には届いていなかった。** それが今回の発見でした。

## 3. それでも全層をすり抜けた事例 — 確認の経路は本物か

具体的に何が起きたかを書きます。

ステートレス化の先行リポジトリで、ファイルアップロードの保存先を、ECS Fargate 前提の S3 に切り替える作業をしていました。実装サブが移行を終え、続いて基本の確認（baseline）の設計に進みました。基本の確認は 6 つの項目でできていて、そのうちの 1 つが「**S3 へのアクセス** — ECS のタスクから S3 バケットの画像の一覧を取れるか」でした。

実装サブは、次のように確認しました（抽象化して書きます）。

```bash
# サブセッション自身の AWS の認証情報で
aws s3 ls s3://<bucket>/<prefix>/ --region <region>
# → 1099 件のファイルが返る
```

「1099 件の一覧が取れた → ✅ S3 アクセス OK」と判定し、6 項目すべて ✅ で完遂と報告してきました。

親（筆者側の Claude）はこれを承認しました。別に立ち上げた第三者の監査サブに、一斉通知の前の「進めてよいか」の判定を独立にかけました。監査サブは 10 項目を確認し、7 つが ✅、3 つが 🟡（見た目だけの指摘）で、🟢 進めてよい、の判定でした。Copilot レビューも、該当の PR では 1 回目で軽い指摘だけで、マージ済みでした。

ここまでで、AI の多層防御 4 層（実装サブ・親・監査サブ・Copilot）を全層通過しています。

ところが — この記事の主題はここからです — 筆者（人間）が「基本の確認は了解。**もっと踏み込んだ回帰テストはできそう？**」と追加で頼みました。実装サブは 3 ケースを追加で設計し、そのうちの 1 つで初めて、次の確認が行われました。

```bash
# ECS Exec で実際のコンテナに入り、実際のアプリのエンドポイントを、利用者と同じ経路で叩く
curl -i http://<container>/image/<filename>
# → HTTP 404
```

**HTTP 404 が返りました。**

つまり、実装サブが「✅ S3 アクセス OK」とした `aws s3 ls` の経路では一覧が取れていたのに、**実際のアプリの HTTP の経路では、画像が 1 件も返ってこない** 状態でした。ここで人間の追加の依頼がなければ、9 リポジトリすべてに「✅ 完遂」と表示されたまま本番に反映され、お客さまの側で画像が表示されない問題が表に出るところでした。重大インシデント未遂です。

### 真因（簡略）

技術的には、次の連鎖でした。

1. Laravel 標準の環境変数名（`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`）がデプロイ先の環境変数に入っておらず、過去の独自の名前だけが存在していた
2. Laravel の設定は標準の名前を参照するので空になり、AWS SDK は ECS のタスクロールへ流れた
3. ECS のタスクロールには、対象バケットへのアクセス権限が付いておらず、AccessDenied になった
4. アプリ層の例外処理が AccessDenied を握りつぶし、ローカルのストレージへ切り替えた
5. ECS Fargate のローカル領域は当然 0 件 → 一覧は 0 件 → 個別のファイルは 404

これらが直列につながり、**実装サブの `aws s3 ls` はサブ自身の広い権限で通っていた一方、実際のアプリは狭いタスクロールの経路で、まったく通っていなかった** という構造でした。

### 何が問題だったか

この不具合そのものは、設定 1 行で直る軽いものです。本番に反映する前に見つかっているので、実害もありません。問題はそこではなく、**「AI の多層防御 4 層をすり抜けた」という構造のほう** にあります。

## 4. 多層防御はなぜ通したのか — 構造の分析

各層がなぜ通したのかを、層ごとに分けます。

| 層 | 何を見ていたか | 結果 | 通した理由 |
|---|---|---|---|
| 1. 実装サブ | 基本の確認 6 項目の自己確認 | ✅ 合格と判定 | サブ自身の認証情報で一覧が取れた → 「S3 アクセス OK」と判定。**確認がどの経路を通ったかは、観点に入っていなかった** |
| 2. 親（Claude） | 基本の確認の設計の承認 + 完遂の判定 | ✅ 完遂 | 5 番目の項目が ✅ だという報告を信じた。「その確認は、広い権限で迂回していないか？」を問わなかった |
| 3. 第三者の監査サブ | 一斉通知の前の「進めてよいか」の判定 | 🟢 進めてよい | 監査のプロンプトが「6 項目を達成したかの確認」だった。**基本の確認の設計そのものが十分かは、観点の外** |
| 4. Copilot レビュー | 該当 PR のコードレビュー | 軽い指摘だけでマージ | コードの差分のレビューであって、確認の設計のレビューではない |
| **5. 人間（筆者）** | **追加の回帰テストの依頼** | **検出** | **「もっと踏み込んだ確認はできそう？」の問い直しで初めて、コンテナの中から curl で確かめる確認が組まれ、404 が露わになった** |

### 同じ系列のモデルの AI は、同じ盲点を持つ

複数の AI を組めば、原理的には独立性が稼げるはずです。実装サブと監査サブは独立したセッションで、互いの文脈を参照しません。「複数の AI が独立に見れば、盲点は消える」。直感的にはそう思いがちです。

ところが今回はっきりしたのは、**AI のセッションが独立していても、モデルの系列が同じなら、系統的な盲点は共有される** ということでした。

実装サブも監査サブも、同じ Claude 系列のモデルでした。どちらも、「確認は項目の達成チェックリストの形で組む」「✅ 合格と書いてあれば達成とみなす」という、形式的な確認への傾きを共有していました。これはセッションを分けても消えない癖です。**学習データに由来する系統的な傾向は、セッションの独立性では拭えない。**

Copilot レビューを受けるのは実装サブだけですが、Copilot は **コードの差分** を見るレビュアーで、**確認の設計が十分か** を見る役には置かれていません。つまり、確認の設計の観点には、独立した外の視点（= 同じ系列ではないレビュアー）が組み込まれていなかった。これが今回の構造的な気づきです。

## 5. 引き出した原則 — 確認の経路は本物か、人間の問い直し

今回得た原則は 2 つです。

### 原則 5-1: 確認の経路は本物か（確認経路の真正性）

確認は「✅ 合格」を返すだけでは足りません。**どの権限の経路で通したかを、必ず問う** 必要があります。チェックリストにしました。

- **権限の経路**: サブ自身・管理者の認証情報・サブの広い権限を使っていないか？（使っていれば、誤って合格にしているおそれがある）
- **利用者の経路**: 実際の利用者が通る、最小の権限の経路で確かめているか？
- **アプリ層の通過**: 実際のコンテナ・実際のアプリのプロセスを通して確かめているか？（サブの手元から直接 CLI や SQL を叩くのは不可）
- **異常系も確かめる**: 権限がない・リソースがない、という異常系も、利用者の経路で確かめる

この 4 点を、起動プロンプトと監査プロンプトの両方に「**必須の観点**」として書き込み、確認を設計するときにサブが自分から点検する形にしました。

### 原則 5-2: 人間の問い直しを構造に組み込む

AI 主導の確認の設計は、プロンプトで明示しない限り、形式的な確認（項目の達成チェックリスト型）に流れます。これは AI を責める話ではなく、構造として認識しておく性質です。

人間（筆者・レビュアー）は、AI から確認の設計の提案を受け取ったとき、次の問いを必ず加えるルールにしました。

- 「その確認は、管理者の認証情報やサブ自身の広い権限で迂回していないか？」
- 「実際の利用者が同じ経路を通ったら、同じ結果になるか？」
- 「サブの権限が広すぎて、アプリ層の権限不足を隠していないか？」

これは前々作の [Day051 の記事](https://zenn.dev/fixu/articles/day051-ai-human-collaboration) に書いた「人間の判断軸」と地続きですが、当てる層が深くなりました。Day051 の時点では、「Claude がローリングアップデートを提案 → 人間が本番を見越して却下」のような、**コードの設計の層** での判断軸でした。今回は、**確認の設計の層** に同じ形の判断軸が必要になった、ということです。

### 監査サブのプロンプトの改修

第三者の監査サブを起動するとき、プロンプトに次を必須の観点として渡すようにしました。

- 基本の確認・回帰テストの設計**そのもの**が十分かを、厳しく評価する
- 確認の経路は本物か（管理者やサブの権限で迂回していないか）
- 複数の AI が同じ盲点を持つリスクの自覚（「自分は実装サブと同じ系列のモデルで、同じ盲点を共有している可能性がある」）

最後の項目を入れたのが、今回の小さな発明でした。**「自分の独立性を過信しない」と、プロンプトで宣言させる。**

## 6. それでもテスト・監査・QA のやり方は確立していない — コメント募集

ここまで対策を書いてきましたが、率直に書くと、**コードの面で Claude × Copilot の体制ができているのと同じ手触りでは、テスト・監査・QA の観点のレビューはまだ組めていません。**

整理するとこうです。

| 観点 | コードの面 | テスト・監査・QA の面 |
|---|---|---|
| Claude が一次の成果物を作る | ✅ 確立 | ✅ できる（テストの設計・監査の観点の設計） |
| 別の系列のモデルのレビュアーで、複数の視点から確かめる | ✅ Copilot レビュー（平均 1.5 ラウンド） | ❌ **未確立** |
| 数値で運用できる | ✅ ラウンド数・指摘の件数で管理できる | ❌ 「観点の網羅度」をどう測るか分からない |
| 参照できる定石 | レビュー文化の蓄積がある | 手探り |

理由を考えると、コードレビューは「差分を見る」という範囲がはっきりしていて、Copilot のような自動レビュアーが入り込む設計が、業界全体で蓄積されています。一方、テスト・監査・QA は「**何を見るかを設計する作業が妥当か**」を問うので、レビューの対象が平らな差分ではなく、観点の網の目になります。これに別のモデルで確かめる仕組みを組むのは、考え方としては可能でも、実装は手探りです。

今の時点で組み込めているのは、次のくらいです。

- 監査サブのプロンプトに、「基本の確認・回帰テストの設計そのものが十分か」を厳しく見る観点として明記する
- 起動プロンプトに、確認の経路のチェックリスト 4 点を埋め込む
- 「同じ系列のモデルを重ねた多層防御に、独立性を期待しない」という前提を、全プロンプトで共有する
- 人間の追加の依頼を **構造的な手順として組み込む**（AI の完遂報告のあとに、必ず人間が「もっと踏み込んだ確認はできそう？」と聞く）

これは **対症療法に近い** と自覚しています。

### 知見を求めています

同じ問題に取り組んでいる方に、ぜひ伺いたい点があります。

1. **テスト・監査・QA の層で、別の系列のモデルの AI レビュアーをどう組み込んでいますか？** Copilot に相当する自動レビュアーが、テストの設計にも入り込む仕組みを作れているケースはありますか？
2. **「観点の網羅度」を数値で測る運用** をしている例はありますか？ コードレビューのラウンド数のような、運用できる指標が、テスト・監査の側にも欲しいです
3. **AI 同士の多層防御で、「同じモデル由来の系統的な盲点」を構造的に潰す** やり方はありますか？ 私たちは今のところ、「人間の問い直しを最終層に組み込む」ことしかできていません

「自分のところはこう組んでいる」「ここはこう設計したほうがいい」という知見を、コメントで教えていただけるとうれしいです。AI を業務に組み込む型は、まだ業界全体で固まっていない領域なので、外の知見を取り込みたいというのが本音です。

## 7. まとめ — 人間の役割は「実行」から「問い直し + 無いものを疑う」へ

前作からの 2 週間でいちばん大きかった発見は、**複数の AI と Copilot レビューの体制がコードの面で確立しても、テスト・監査・QA の層には届いていない盲点が残る** ということでした。

そして、その盲点は AI を何層重ねても抜けません。同じ系列のモデルの AI には同じ系統的な盲点があり、セッションを分けても拭えない。**独立性は「セッションの分割」ではなく、「モデルの系列・観点・経路」の独立で稼ぐ必要がある。** これが構造の原則として残ります。

この前提に立つと、人間の役割は、前々作の [Day051 の記事](https://zenn.dev/fixu/articles/day051-ai-human-collaboration) で書いた「AI の暴走をその場で正す、判断軸の持ち主」から、もう一段抽象度が上がります。

> **AI の多層防御のあとの最終層 — 「無いもの」を疑い、「その確認は広い権限の経路で迂回していないか？」を構造的に問う役**

「実行」を AI に明け渡すこと自体は、前作までで成立しています。今回見えてきたのは、**「実行を明け渡したあとの確認を、AI 任せにしない」というもう 1 段** の業務設計です。確認は「✅ 合格」が返った瞬間に終わる作業ではなく、その合格が **どの経路で通ったか** を問うことで、初めて閉じる作業です。

おそらく 1 年もしないうちに、別の系列のモデルのレビュアーが、テスト・監査・QA の層にも自然に入ってきて、人間の問い直しを構造的に補ってくれるようになると思います。それまでは、**人間の問い直しを業務設計に組み込み続けるしかない。** それが今回の体感でした。

「自分のところはこう組んでいる」「ここはこう設計したほうがいい」という知見を、コメントでぜひ教えてください。手探りの段階を共有しつつ、業界として型を作っていけたらうれしいです。
