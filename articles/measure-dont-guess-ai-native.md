## はじめに

「月10,000アクセスくらいだと思います」
「実測は月20件でした」

この2つの数字、**500倍離れています**。でも本記事で伝えたいのは「私の推測が雑だった」という話ではありません。**推測と計測は、そもそも用途が違う道具だった**、という配置の話です。

fixU Reboot プロジェクト（Laravel モノリシックを9マイクロサービスに分割する取り組み）のなかで、私はこの2つを同じ箱に放り込んでいました。AIネイティブ時代は、その2つを別の棚に並べ直す絶好の機会だ、というのが今回の気づきです。

## 「推測で即決」が合理的だった時代

これまで、エンジニアや事業責任者は「数値感覚を磨き、推測の精度を上げることで、計測のステップを省略し、意思決定のスピードを上げる」という戦い方を基本としてきました。

- 計測はコストが高い（SSHログイン、ログ整形、集計、グラフ化…）
- 意思決定は早いほうがビジネス的に有利
- したがって、経験則で即決できる人材ほど価値が高い

これは合理的でした。1件の意思決定のために半日ログを掘るコストと、推測で即決して外したコストを比べると、多くのケースで推測のほうが安かった。数値感覚を磨くことはエンジニアの重要なスキルだったわけです。

## 転換点 ― AIネイティブ時代に計測コストが激減した

ところがAIエージェント（Claude Codeなど）を業務に組み込むと、状況が反転します。

たとえば「この機能、本番でどれだけ使われてるんだっけ？」という問いに対して、従来なら：

1. 本番サーバにSSH
2. nginx access.log の場所を思い出す
3. `grep` と `awk` でパスごとに集計
4. アプリケーションログもついでに確認
5. スプレッドシートに貼って可視化

で30分〜1時間。

AIネイティブ時代ではこれが、**自然言語で1行投げて10秒**になります。

```
「本番の nginx access.log から過去14日間の /door* 系のアクセス数を集計して」
```

計測コストの桁が変わった、というのがポイントです。「推測で省略する」ことを支えていた前提が崩れました。

## 実例 ― Share機能の「月10,000 vs 月20」

fixU Reboot プロジェクトで、こんな議論が起きました。

- 旧fixUをマイクロサービスに分割するにあたり、Share機能（ドア共有URL、スマートロック連携）の「受け皿」がどの repo にもない
- 選択肢は2つ
  - A: ユーザー向けの既存 repo (`fixu-user-app`) に統合する
  - B: 新しく `fixu-share` repo を新設する

私は数値感覚をフル稼働させて、こう答えました。

> 「Share機能の利用量は月10,000アクセス程度と想定します。施設数100+、MAU 40k+、将来の10倍スケールへの safety margin を考えると、独立 repo にしておくほうが安全です」

これ自体は教科書どおりです。キャパシティプランニングでは**悲観的に多めに見積もって safety margin を掛ける**のが基本で、数値感覚としてはむしろ「正しい作法」で出した数字でした。

一方、並行して AI に計測を投げました。

- nginx access.log の `/door*` 系アクセス: **14日間で実質0件**
- アプリログの `views/share` 参照: 月 **~20件**
- share_url 発行ログ: 月 **~150件**（発行のうち約13%しか使われていない）
- ついでに `Undefined variable $space_data` エラーが放置されていることも検出

**推測 月10,000 vs 実測 月20 = 500倍の差。**

ついでに、ほぼ使われていない機能で PHP エラーが出続けていたことも可視化されました。

## 推測と計測は、別の道具である

大事なのは、ここで**推測側を責めないこと**です。数値感覚で出した「月10,000」はキャパプラ向けの道具として正しく機能していて、これを使ってインフラサイジングしていたら問題なかったはずです。

ズレを生んだのは、**推測という道具を、方針判断という別の現場に持ち込んだ**ことでした。道具の精度の問題ではなく、**道具の配置**の問題です。

| 用途 | 使うべき手法 | 性質 |
|------|------------|------|
| キャパシティプランニング（インフラサイジング等） | **推測**（pessimistic × safety margin） | 外しても過剰投資で済む |
| 方針決定（機能継続、repo分割等） | **計測**（現状把握 + トレンド） | 外すと見当違いの意思決定になる |
| 戦略（M&A、5年構想） | **推測と直感** | そもそも計測できない未来 |

これを私は「3層思考フレーム」と呼んでいます。

- **戦略層**: 未来は計測できない。推測と直感でよい
- **方針層**: 現在と潜在は計測できる。まず計測すべき
- **容量層**: 外したときの損失が「過剰投資」で済むなら推測でよい

Share機能のケースは、**容量層の道具（悲観的推測）を、方針層に置いてしまった**ときに起きる典型例でした。「pessimistic × safety margin」はインフラサイジングでは頼りになる道具ですが、「この機能を存続させるか」「どの repo に置くか」という方針層では、そもそも欲しい情報（現状はどうか）を返してくれない道具なのです。

道具が悪いのではなく、棚が間違っていた。そう捉えると、これまで蓄積してきた数値感覚も、AIによる計測も、両方とも資産のまま活かせます。

## 結論、どうしたか

Share機能の最終方針はこうなりました。

- **機能は維持**（スマートロック連携は戦略上の重要度が高いため）
- ただし配置は、`fixu-user-app` 統合ではなく **独立 `fixu-share` repo 新設**
- 利用量の少なさは「機能廃止」の材料にはしない（戦略層の判断が優先）
- 放置されていた PHP エラーは別チケットで修正

ここで重要なのは、**計測したからといって、結論が計測値ベタ付けで決まるわけではない**ことです。計測は方針層にインプットを与えますが、最終意思決定は戦略層で行われます。「利用量が月20件だから廃止」にはなりませんでした。

興味深いのは、**推測だけでも計測だけでも、どちらも片手落ちになる**という点です。

- 推測だけ → 「月10,000の大事な機能」として過剰なインフラ投資をしていた可能性
- 計測だけ → 「月20件しか使われていないから廃止」と、戦略を無視した結論に倒れていた可能性

結局は、**道具を適切な層に配置して、両方を使う**しかない。推測 vs 計測ではなく、推測 × 計測です。

## 道具の配置ルール

AIネイティブ時代における道具の置き場所として、私が意識しているのはこの4点です。

1. **方針層にはまず計測を置く**。推測を先に出してから計測で補強するのではなく、**計測してから推測で補完する**。順番を入れ替えるだけで、議論の解像度が変わります
2. **AIに「実測で」と指示できる環境を整える**。従来は「計測コストが高いから推測で」と逆の指示をしていました。道具の値段が変わったら、指示も変える
3. **推測はキャパプラと戦略に温存する**。長年磨いてきた数値感覚は、引き続き有効な道具です。片付ける棚を変えるだけで十分
4. **「今どの層の話をしているか」を議論の最初に宣言する**。方針の話なのか容量の話なのかが曖昧なままだと、再び道具の取り違えが起きます

## おわりに

「推測で即決できるエンジニア」は、計測コストが高い時代の強力な人材像でした。その強みをそのまま引き継いで、AIネイティブ時代の人材像は「**計測を即座に投げ、推測を適切な層に配置できるエンジニア**」にアップデートできるはずです。

今回、道具の配置を教えてくれたのは、14日間分の access.log を10秒でサマリしてくれた AI でした。次に「だいたい月◯◯くらいですかね」と言いそうになったら、ひと呼吸置いて、**これは方針の話か、容量の話か** を自分に確認するようにしています。
