## はじめに

前回の記事「[AIネイティブ開発でQCDはどう変わったか](https://zenn.dev/fixu/articles/ai-native-qcd-measured-evaluation)」で、「基盤の全体像は後日別記事で」と予告しました。本記事がその全体像編です。

弊社はこの約100営業日で、12年もののレガシーシステムを「AIが自走し、人間が方針判断とレビューを担う」体制で再生してきました。個々の技術トピック（マルチセッション運営、リポジトリ分割、計測文化など）は過去記事で扱ってきたので、本記事は**全体を俯瞰する総集編**です。何が課題で、どんな状態を目指し、どの順序で取り組み、最終的にどうなったのか——判断の理由と代償も含めて、一本の物語としてまとめます。

> AIネイティブ化とは、開発ツールを導入することではありませんでした。デューデリジェンス → 意思決定 → テストという安全網 → 基盤の再構築 → 段階的リリース、という**順序立った再生プロジェクト**であり、その順序の一つひとつに理由と、ときに代償がありました。

---

## 1. なにが課題だったのか

### 12年分の堆積

対象は、12年運用してきたコワーキングスペース/シェアスペース管理のSaaSです。会員登録・チェックイン/アウト・決済・スマートロック連携・LINE連携までを一気通貫で扱う、事業の中核システムです。デューデリジェンスをAIで実施したところ、次の姿が定量的に見えてきました。

- **テストがほぼ存在しない**: 12年分・450本超のDBマイグレーションと約300のコントローラーに対し、自動テストは実質ゼロ。CI/CDもなし
- **EOL（サポート終了）の堆積**: フレームワーク・言語・ランタイムが軒並みサポート切れバージョン
- **性能課題**: 5秒を超えるスロークエリが1日約1,800件。索引が未整備の巨大テーブル、N+1クエリの多発。監視はCPU使用率の通知のみで、アプリケーションの中身は見えない
- **セキュリティ課題**: 出力エスケープ漏れの残存、権限の共有アカウント運用など、確認すべき論点が多数
- **個社カスタマイズの堆積**: 特定顧客向けの分岐やハードコードがコードベース全体に散在し、変更影響の見積もりを困難にしていた
- **デプロイはシェルスクリプトの手動実行**: サーバーへ順次配布し、プロセス再起動の瞬断が発生する方式。24時間営業の店舗を多数抱えるサービスとしては心臓に悪い構造

### リニューアルの停滞と、経営判断

実はこのシステムには並行して、フルリニューアル版の開発プロジェクトが走っていました。しかし品質と移行リスクを実測評価した結果（後述のE2Eテストがここで効きました）、**リニューアル版への移行を中止し、現行システムを再生する**という経営判断をしました。

この判断を支えたのが、AIによるデューデリジェンスです。現行コードベースを複数の観点（性能・セキュリティ・個社仕様・構成）で並列調査し、「DB負荷改善」「フレームワーク更新」「テスト導入」「大型新機能」といった主要な改修系統ごとに工数を見積もったところ、**AI体制なら現行システムの維持・改善は現実的**という数字が出ました。従来なら「触りたくない」の一言で終わっていたレガシーが、AIの登場で「再生できる資産」に変わった——ここがすべての出発点です。

> **章末の蒸留**: レガシー再生か作り直しかの判断は、感覚ではなく実測で下せる。AIはコードを書く前に、まず「意思決定の材料を揃える道具」として効いた。

## 2. どんな状態を目指したのか

再構築計画では、目的を5つ立てました。

1. セキュリティ・パフォーマンス問題の解消
2. **AIネイティブ開発の基盤づくり**
3. 追加機能開発の加速
4. デプロイ事故の抑止と影響範囲の限定
5. 個社向け機能や新しい提供形態への対応

注目していただきたいのは2番です。単に古い部分を直すのではなく、「**AIが安全に自走できる構造**」をゴールに据えました。AIの生産性は、コードベースの見通しの良さ・検証の自動化・環境の再現性に強く依存します。つまりレガシー解消とAIネイティブ化は別々の取り組みではなく、同じ一つの投資です。

進め方のモットーは「**小さく早く段階的に、安全措置を取りながら**」。現行環境には手を加えず運用を続け、並行して新環境を構築して段階的に移行する方針にしました。

設計面で特徴的な割り切りが、モノリスの**ハードフォーク分割**です。1つのモノレポを、提供チャネルごとに約10のリポジトリへ「全部コピーしてから不要部分を削る」方式で分割しました。コードの重複を許容する、いわゆるDRY原則に反するやり方ですが、AI時代は「リポジトリごとに文脈が閉じていること」の価値が重複管理のコストを上回る、という判断です（この設計思想は[別記事](https://zenn.dev/fixu/articles/subsidiarity-scs-end-to-end-ai-native)で詳しく書きました）。

> **章末の蒸留**: 目指したのは「綺麗なシステム」ではなく「AIが安全に自走できるシステム」。ゴールをそう定義すると、DRYのような従来原則にも見直しの余地が生まれる。

## 3. どの順序で取り組んだのか

ここが本記事の中心です。約100営業日の取り組みを、施策の繋がりで整理すると次の順序になります（読みやすさを優先し、実際には並行・前後した部分も一直線に再構成しています）。

### 3-1. デューデリジェンスと意思決定（最初の1か月）

前章までの通り、まず現行システムの棚卸しと改修ロードマップの立案、そしてリニューアル移行中止の意思決定です。意思決定は1回の会議ではなく、約2週間で「戻れる道を残す」→「移行を止める」→「詳細比較」→「現行一本化」と段階的に収束させました。大きな方針転換ほど、一度に決めずに撤退可能な小さな決定を重ねる方が合意形成が速い、というのは発見でした。

### 3-2. 現行仕様の把握とE2Eテストの整備

次に着手したのは、コードの修正ではなく**テスト**です。仕様書がない12年もののシステムでは、「いま何が正しい挙動か」の定義から始める必要があります。AIに画面を実際に操作させながら仕様を文書化し、ブラウザ操作を含むE2Eテストケース群を整備して、機能テストを繰り返し実行できる状態を作りました。

これが以降のすべての工程の**安全網**になります。この後に続くコード削除もバージョンアップも構造変更も、「E2Eテストが通り続けること」を回帰の判定基準にできたからこそ、AIに大胆な変更を任せられました。

なお、このE2Eテスト実行とコード調査には膨大な時間とAIトークンを消費しました。専用のMacBookを1台AIに割り当て、最上位プランのサブスクリプションを契約し、外出先からはスマホで進捗を監視・指示する体制です。基盤投資としては安くありませんが、この安全網なしに後続の工程は成立しなかったので、真っ先に投資してよかったと考えています。

### 3-3. リポジトリ分割と不要コードの削除

安全網ができたところで、ハードフォーク分割を実行しました。全リポジトリにモノレポ全体をコピーし、各リポジトリの責務を定義した上で、不要なコードを「ルート定義→コントローラー→サービス→モデル→依存パッケージ」と外側から内側へ削っていきます。入口であるルートとコントローラーを削るだけで、コードベースの6〜7割が削減できる見込みが立ち、実際に累計で数百万行を削除しました（このときのAIマルチセッション運営は[過去記事](https://zenn.dev/fixu/articles/ai-multi-session-7-principles)で詳しく書いています）。

順序のポイントは、**バージョンアップの前に削除を済ませた**ことです。コードが6割減れば、バージョンアップで面倒を見る対象も6割減ります。

### 3-4. バージョンアップ — EOLからの脱却

続いて言語・フレームワーク・ライブラリのバージョンアップです。まず最も小さなリポジトリ1つをパイロットとして最新化の手順を確立し、その手順を残りのリポジトリへ横展開しました。テストという安全網と、削除で身軽になったコードベースのおかげで、フレームワークのメジャーバージョンを複数段跳ねる更新を全リポジトリで完了できました。

### 3-5. デプロイパイプラインとIaC — 土台の整備

インフラは、既存環境をいじるのではなくゼロから作り直しました。Terraformで全環境をコード管理（IaC）し、GitHub ActionsでCI/CDを構築。環境名・ドメイン名・ネットワークの命名規則もこの時点で整理し、「開発→ステージング→本番」の3環境を同じコードから生成できる構造にしました。

IaCを選んだ理由の半分はAIとの親和性です。インフラがコードなら、AIが差分をレビューでき、変更計画を実行前に明示できる。人間がコンソールを手で触る運用は、AIから見ると「観測できないブラックボックス」になってしまいます。初期構築はモジュール設計込みで実質1日。以降、検証用環境の使い捨て構築([実例](https://zenn.dev/fixu/articles/lazy-load-verify-sleep-not-implemented))のような配当も生まれました。

### 3-6. コンテナ化とステートレス化

アプリケーションはEC2上の常駐プロセスから、ECS Fargate上のコンテナへ移行しました。前提として必要なのがステートレス化です。

- セッション情報: サーバーローカル → Redis
- 画像・CSVなどのファイル: ローカルディスク → S3
- ログ: ローカルファイル → CloudWatch Logs
- 定期実行ジョブ: サーバー上のcron → スケジュール起動のコンテナタスク

これによりオートスケーリングとBlue/Greenデプロイが適用でき、「デプロイのたびに瞬断する」構造から「無停止で切り替え、問題があれば即座に旧版へ戻せる」構造になりました。ログのCloudWatch集約は、のちの[監視・問い合わせ調査のAI化](https://zenn.dev/fixu/articles/liff-front-crash-observability-cw-logs)の土台にもなっています。

### 3-7. DBとデータ管理・権限の整備

DBスキーマの変更をマイグレーションとして整備し直し、DB操作専用のコンテナを構築しました。検証環境には本番を模した**マスク済みデータ**を投入し、本番相当のデータ量・形状でテストできるようにしています。あわせてDBアカウントとIAM権限を役割ごとに整理し、「誰が(どのAIセッションが)何をしたか」を追跡できるようにしました。

ステートレス化(3-6)とこの権限整理は、実はもう一つの布石でもあります。ログと権限が整理されていれば、**市場トラブルの一次調査をエンジニア以外(あるいはAI)に開放できる**。実際にその後、CSメンバーの問い合わせ調査をAIが支援する体制([過去記事](https://zenn.dev/fixu/articles/cs-engineer-boundary-dissolving))へ繋がりました。

### 3-8. セキュリティ強化 — そして代償

出力エスケープの徹底、認証・認可まわりの厳密化、秘密情報の管理方法の是正など、デューデリジェンスで挙がったセキュリティ課題のリファクタリングを進めました。

正直に書くと、ここでは代償も払いました。処理を厳密化した結果、これまで「緩さ」の上で動いていた一部の機能が動かなくなったり、エラー時の挙動が変わってUXが悪化したりして、**リリース後の緊急修正に追われる時期がありました**。セキュリティとコストとUXはトレードオフの三角形で、「厳密にすれば安全」ではない。厳密化するなら、その挙動変化を検知できるテストと、ユーザーが行き止まりにならない復帰導線をセットで用意すべきでした。これは前回のQCD記事で書いた対策(fail-close時の復帰導線の設計基準化)に繋がる教訓です。

### 3-9. 大規模新機能 — 多拠点管理の実装

基盤整備と並行して、複数拠点を一元管理する大型の新機能を実装しました。

ここにも判断の分岐があります。原則論で言えば、インフラ刷新と新機能追加を同じリリースに載せる「ビッグバンリリース」は避けるべきです。インフラだけ先に切り替えて安定させ、機能追加は後から載せるのが正着でしょう。ただしその場合、リリース前のテストとリリース後の安定化に取られる期間のぶん、**新機能の提供が数週間遅れます**。当時、リニューアル移行の中止によってこの機能の提供をお待たせしているお客様が複数いらっしゃったため、今回は最短で届く道、つまり基盤刷新と新機能を近接させて出す道を選びました。教科書的な正解と事業の要請がぶつかったとき、どちらの代償を払うかを**自覚的に**選ぶ——それができれば、原則から外れること自体は悪ではないと考えています。

### 3-10. 段階的リリース — 約3週間の切り替え

本番切り替えは一斉ではなく、ドメイン(サービス)単位の段階的な切り替えにしました。影響の大きいサービスはロードバランサーの重み付けを使った**カナリアリリース**で、新環境へのトラフィック比率を少しずつ上げながら移行しています。

リリース後はAIが定期巡回でログ・メトリクスを監視し、問題を検知したら「ロールバックか、最速のhotfixか」を都度判断。発生と解消のペースを見ながらリリース計画そのものを調整し続け、全サービスの切り替え完了までに**約3週間**かけました。

この期間は、正直に言えば苦しい時期でした。切り替えに伴って大小の不具合が顕在化し、お客様にご迷惑をおかけする場面が続きました。矢面に立つのはエンジニアだけではありません。問い合わせを受け止めるCS、お客様との関係を預かるPdMにも、物理的にも精神的にも負荷のかかる3週間でした。段階的リリースは「事故を小さくする」手法であって「事故をゼロにする」手法ではない——切り替え計画には、技術の計画と同じ解像度で**チームの負荷の計画**を含めるべきだったというのが、いちばん重い反省です。

### 3-11. 運用の定常化 — 監視強化とコスト最適化

切り替え完了後は、運用の定常化フェーズです。フロントエンドのクラッシュをサーバー側で捕捉するテレメトリの新設、リリース後の定量監視の標準化といった観測性の強化。計測に基づくパフォーマンスチューニング(45秒→2.7秒、7秒→0.5秒といった画面高速化)。そして新旧環境の並行稼働で膨らんだAWSコストの最適化(不要リソースの削除、DBインスタンスの適正化などで月額20%超を削減)です。この定常運用の実態が、前回の[QCD記事](https://zenn.dev/fixu/articles/ai-native-qcd-measured-evaluation)で評価した「直近2週間」にあたります。

> **章末の蒸留**: 順序の背骨は「安全網(テスト)を最初に張り、土台(IaC/CI/CD)を作り、荷物を減らして(削除)から家を建て替える(コンテナ化)」。そして原則から外れる判断をするときは、何の代償を払うのかを自覚して選ぶ。

## 4. 最終的にどうなったのか

100営業日を経た現在地です。

| 観点 | Before | After |
|---|---|---|
| 構成 | モノリス1リポジトリ | 責務別の約10リポジトリ(マイクロサービス) |
| テスト | 実質ゼロ | E2E+ユニットテストが回帰の安全網として常時稼働 |
| インフラ | 手作業構築のEC2 | Terraform管理のECS Fargate、3環境をコードから生成 |
| デプロイ | 手動スクリプト・瞬断あり | CI/CD+Blue/Green+カナリア、無停止・即ロールバック可 |
| 監視 | CPU通知のみ | ログ集約+テレメトリ+リリース後定量監視の三層 |
| ランタイム | EOL堆積 | 全リポジトリで最新系へ更新済み |
| 開発体制 | 人間が書き、属人化 | AIが自走し、人間が方針判断とレビュー |

そしてこの基盤の上で何が起きているかは、前回のQCD記事で書いた通りです。週あたり人間換算約80人日のアウトプットが、変更失敗率を業界水準以下に保ったまま出ている。これは「AIが優秀だから」だけでは説明できません。**テストの安全網・環境の再現性・観測性という基盤があって初めて、AIの生産性は品質と両立する**——100日の投資は、そのための土台づくりだったのだと、いまは整理しています。

## おわりに

振り返れば、100日の大半はコードを書く時間ではなく、「AIが安全に働ける環境」を作る時間でした。テストがあるから大胆に削れる。IaCだから環境を使い捨てられる。ログが集約されているから問い合わせ前に問題を検知できる。どれも地味ですが、AIネイティブ開発の生産性はこの地味な基盤の総和で決まる、というのが100日やった実感です。

今後も計測と改善のフィードバックループを回し続けます。基盤は整いましたが、ここからが本番です。いまは小規模な改善タスクが中心なので、この体制が数週間規模の大規模な機能開発でどうスケールするのか——次の挑戦として、また結果を報告します。
