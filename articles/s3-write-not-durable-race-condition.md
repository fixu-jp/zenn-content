## はじめに

Amazon Linux 2 のサポート終了(2026年6月30日)を機に、私たちはEC2上のLaravelモノリスをAmazon Linux 2023へそのまま移行するのではなく、ECS Fargateへの移行を選びました。B/Gデプロイやオートスケーリングを前提にすると、複数のコンテナが入れ替わり立ち替わり動くことになります。そうなると、どのコンテナが処理を受けても同じ結果になる「ステートレス化」が前提条件になります。

その一環として、画像アップロード機能をローカルディスクへの書き込みからS3への直接アップロードに切り替えました。ローカルディスクに書くと、そのコンテナが次のデプロイで消えた瞬間にデータも消えてしまいます。S3に直接書けば、どのコンテナが処理しても同じ場所に永続化される。設計としては素直で、実装もLaravelの`Storage`ファサードを使えばものの数行です。

ところがリリース後、実運用を模した確認(いわゆるドッグフーディング)を続けている中で、奇妙な事象に気づきました。アップロードした画像が、**稀に0バイトの空ファイルになっている**のです。

先に手触りを書いてしまうと、

> **「書き込みが成功した」という戻り値は、「データが永続化された」ことを保証しない。ステートレス化でローカルディスクという緩衝地帯を失うと、この差分がそのままユーザーに届く事故になる。**

この記事では、この稀な0バイト事象をどう追い詰め、どう対策したかを振り返ります。

---

## 1. 症状 — 「登録完了しました」の裏で起きていたこと

管理画面から店舗のロゴ画像をアップロードすると、画面には「登録完了しました」と表示されます。ユーザー体験としては何の問題もありません。ところが実際にその画像を開こうとすると、表示されるべき画像が出てこない。S3上の実体を確認すると、ファイルは**確かに存在するのに中身が0バイト**という状態でした。

Laravel側のコードは、素朴に書けばこういう形です(抽象化しています)。

```php
$result = Storage::put($path, $decodedImageData);

if (!$result) {
    // エラー処理
}
// $result が true なので、ここには来ない
```

`Storage::put()`は正常に`true`を返し、例外も投げていません。戻り値だけを見て正常終了と判断する、ごく普通のコードです。しかしこの「普通の書き方」が、今回の事故を捕まえにくくしていました。

> 学び: 「ファイルが存在する」ことは「正しいデータが書き込まれた」ことの証明にならない。空ファイルも立派に「存在」する。

---

## 2. なぜ捕まえにくいのか

通常のエラーハンドリングは、「戻り値が`false`」「例外が飛ぶ」「HTTPステータスがエラーになる」といった、何らかの**否定的なシグナル**を前提に設計されています。しかし今回の事象は、そのどれも発生させませんでした。

- アプリケーションのログにはエラーが一切残らない
- HTTPレスポンスは200で返る
- ユーザーには成功メッセージが表示される
- S3のオブジェクトも(空とはいえ)ちゃんと存在する

つまり**「失敗した」というシグナルがどこにも存在しない**まま、ユーザーが実際に見る結果だけが壊れているという、検出の起点がない不具合でした。

> 学び: エラーハンドリングは「失敗を通知してくれるシステム」を前提に設計されがちだが、外部ストレージの書き込みは「成功したふりをして実は壊れている」というモードを取りうる。

---

## 3. 環境差の壁 — 開発環境では再現しない

原因を絞り込もうにも、まず開発環境で再現させようとしたのですが、何度アップロードを繰り返しても発生しませんでした。発生するのは本番環境だけです。

S3のバケット設定やECSタスクの構成に、開発環境と本番環境で意図した差異はありません。考えられる違いは、日常的に処理されるファイル数の桁違いの差、WAFのフィルタリング挙動、あるいは単純にインスタンスのスペック差くらいですが、どれも決め手には至りませんでした。

「本番でしか起きない」という事実は、原因の絞り込みという意味では厄介です。本番環境で気軽に再現実験を繰り返すわけにはいかないからです。ここから先の調査は、本番環境という制約の中でどう安全に切り分けるか、という問題になりました。

> 学び: 「本番でしか再現しない」は、原因を推測で埋めたくなる誘惑が最も強くなる場面。ここで推測に頼らず、経路を一つずつ実測で潰していく規律が効いてくる。

---

## 4. 消去法による切り分け

処理の流れを、ブラウザ→ロードバランサー→アプリケーションサーバー→S3という経路に分解し、それぞれの区間でデータが正しいかを一段ずつ確認していきました。

1. **クライアント側の送信データを直接確認する**
   ブラウザの開発者ツールで、送信直前の画像データ(base64エンコード済み)の文字数を直接確認したところ、正しい長さのデータが生成されていました。クライアント側の生成ロジックは無罪です。

2. **ロードバランサーのアクセスログを確認する**
   AWSのALBアクセスログには、リクエストごとの受信バイト数(`received_bytes`)が記録されています。これを確認したところ、送信されたデータが**完全な形でロードバランサーまで届いている**ことが確認できました。ネットワーク経路も無罪です。

3. **HTTPリクエストを経由せず、アプリケーションサーバー内部から直接書き込む**
   コンテナに直接入り、HTTPリクエストの経路を一切経由せずに、同じ`Storage::put()`をその場で実行してみました。すると、何度実行しても正しいサイズでS3に書き込まれます。PHPの実行環境・IAM権限・S3への書き込み自体も無罪です。

ここまでで無罪が確定した箇所を消していくと、残るのは一つだけでした。**「ブラウザ→ロードバランサー→アプリケーションサーバーというHTTPリクエストの経路を実際に通ったときだけ」**、何かが起きているということです。

> 学び: 「どこがおかしいか」がわからないときは、経路を要素に分解し、各要素を単独で無罪にしていく。ALBの受信バイト数のように、アプリケーションの外側にある一次記録を使うと、アプリケーションのログを疑わずに済む区間を作れる。

## 5. 本番環境への一時的なデバッグ計装

経路上の疑わしい区間は絞れたものの、この先はアプリケーションコードの内部で何が起きているかを直接見るしかありません。開発環境では再現しないため、本番環境で稼働中のコンテナに、影響範囲を明示した上で一時的なデバッグログを直接仕込むという手段を取りました。

具体的には、受信したデータの文字数、デコード後のデータ長、そして`Storage::put()`の戻り値をログに出力するようにしました。実際にログを確認すると、次のような記録が残っていました。

```
受信データ長: 785418
デコード後データ長: 589045
put()の戻り値: true
```

すべて正常な値です。しかし、このログが出力された**直後にS3の実オブジェクトを確認すると、0バイトになっているケース**が実際に再現しました。アプリケーションが認識している内部状態は完全に正常で、それでもS3上の実体は壊れている。ここに来て、問題の所在がようやく一段深いところにあることが見えてきました。

このデバッグ計装は稼働中の本番コンテナに対する一時的なコード変更であり、検証終了後は必ず元の状態に復元することを徹底しました。影響範囲を明示し、承認を得た上で実施する、リスクの高い調査手法です。

> 学び: アプリケーションが「正常」と報告している値は、あくまでアプリケーションの認識でしかない。外部システムの実際の状態とは、別に確認しないと一致しているとは限らない。

## 6. 核心 — 「成功」は「永続化確定」を意味しない

ここで一つの仮説が出ました。「`Storage::put()`の直後に、S3へ確認の呼び出しを挟んだら直るのではないか」というものです。実際に`Storage::exists()`や`Storage::size()`で書き込み直後のオブジェクトを確認する処理を挟んでみると、**その回以降は連続して正常に書き込まれる**ようになりました。

さらに、確認呼び出しの代わりに単純に1〜2秒待機する処理を挟んでも、同様に成功することが確認できました。これは、S3への追加のAPI呼び出し自体に意味があるのではなく、**単純に時間的な要因が絡んだレースコンディション**であることを示していました。

つまりこういうことです。

> `Storage::put()`が`true`を返した時点で、実際の書き込みが完全に確定しているとは限らない。そのまま処理を完了させてレスポンスを返すと、稀に、直後の状態確認では書き込みが反映されていない(0バイトになる)瞬間が存在する。

発生頻度は、意図的に繰り返しテストすると数回に1回程度で再現する、稀ではあっても無視できない水準でした。ローカルディスクへの同期的な書き込みに慣れていると、「書き込み関数がtrueを返した=データはそこにある」という前提を無意識に持ってしまいます。しかし外部ストレージへの書き込みは、その前提が常に成り立つとは限りません。

> 学び: 戻り値が「true」であることと、その効果が外部から観測可能になっていることの間には、時間的なギャップがありうる。単純な戻り値チェックでは、このギャップは検出できない。

## 7. 対策設計 — 検証・リトライ・原子的な確定

恒久対応として、書き込み処理そのものをラップする仕組みを実装しました。設計の骨子は次の3点です。

1. **書き込み後に必ず検証する** — `Storage::put()`実行後、実際に書き込まれたサイズを元データの長さと比較する
2. **検証に失敗したら短い間隔でリトライする** — 数回まで、漸増するバックオフを挟みながら再試行する
3. **全リトライ失敗時は例外を投げず、失敗として扱う** — 呼び出し元がデータベースの更新をスキップし、ユーザーには改めてエラーを返せるようにする

```php
function putVerified(string $path, string $data, int $maxAttempts = 3): bool
{
    for ($attempt = 1; $attempt <= $maxAttempts; $attempt++) {
        $stagingPath = "{$path}.tmp-" . bin2hex(random_bytes(8));
        Storage::put($stagingPath, $data);

        if (Storage::size($stagingPath) === strlen($data)) {
            Storage::move($stagingPath, $path);
            return true;
        }

        Storage::delete($stagingPath);
        usleep(200_000 * $attempt); // 漸増バックオフ
    }

    return false;
}
```

一時的なステージング用のキーに書き込んで検証し、検証が通った場合のみ本来のパスへ昇格させる、という流れです。最終的な移動が成功して初めて「書き込み完了」とみなすため、検証途中の不完全なデータが本来の場所に見えてしまうことを避けられます。

> 学び: 「書いて確認する」だけでなく、「確認できたものだけを本来の場所に昇格させる」という一段階を挟むと、検証と確定の間の隙間が塞がる。

## 8. AIコードレビューによる段階的な堅牢化

この実装は、AIによるコードレビューを何ラウンドか経て収束させました。指摘の推移が、堅牢化のプロセスとして興味深いものでした。

- **第1ラウンド**: 「クライアント側のデータ自体が空だった場合、0バイトの書き込みを正常な検証成功として扱ってしまう」という設計の穴が指摘されました。さらに、**「全リトライが失敗した場合、既存の正常なファイルを空データで上書きしてしまうリスクがある」**という最重要の指摘がありました。壊れたデータを検出する仕組みのはずが、そのままでは新たな破壊経路になりうる、という皮肉な状態です。ステージングキーを経由して検証してから昇格させる、という上記の設計は、この指摘を踏まえたものです。
- **第2ラウンド**: 検証呼び出し自体は例外処理でカバーされていたものの、実際の書き込み呼び出しそのものが例外を投げた場合の処理が漏れていました。加えて、ステージングキーの拡張子の位置によってはコンテンツタイプの推測に影響しうる、という実務的で気づきにくい指摘もありました。
- **第3ラウンド**: ランダムなトークン生成自体が例外を投げうる、リトライのバックオフ処理がテストしにくい構造になっている、「原子的な移動」という表現がS3の実装(コピー後に削除)として正確でない、といった、より軽微な品質・表現面の指摘でした。
- **第4ラウンド**: 指摘なし。ここで収束しました。

単純な「書いて確認する」という最初の実装が、複数ラウンドの指摘を経て、ステージング→検証→原子的な昇格という、より堅牢な設計に磨かれていきました。特に「壊れたファイルを直す仕組みが、新たな破壊経路になっていた」という第1ラウンドの指摘は、対策そのものにも検証が必要だということを思い出させてくれました。

> 学び: 対策コードは、対策であるがゆえにレビューが甘くなりがちな箇所でもある。「この対策自体が新しい失敗モードを持ち込んでいないか」を、レビューの一観点として明示的に置く価値がある。

## 9. 横展開と機微データの安全境界

開発環境で複数回のアップロードテストを行い、対策後は毎回1回目の試行で正常に成功することを確認した上で、標準的な段階的デプロイ(開発→ステージング→本番)の流れで展開しました。

同種の「外部ストレージへの書き込み成功を無条件に信じている」パターンは、この管理画面の機能だけでなく、他の複数の画面・サービスにも共通して存在していました。同じ検証・リトライの仕組みを横展開する際、一点だけ強く意識したことがあります。

**本人確認情報など、公開してはならない機微なデータを扱う画面については、書き込み先の可視性(非公開設定)は絶対に変更してはいけない**という点です。今回のロゴ画像のような公開データの不具合修正パターンをそのまま機械的に適用してしまうと、書き込み先の設定まで一緒に変えてしまい、機微なデータが公開範囲に晒される重大な事故になりかねません。横展開のタスクを起票する際は、この注意点を明記した上で、検証・リトライという「堅牢性の追加」と、書き込み先の可視性という「データの扱い」を明確に切り分けて依頼しました。

> 学び: 同じ症状に見える不具合を横展開するときほど、「この修正のうちどの部分が共通で、どの部分がその画面固有の文脈に依存しているか」を切り分ける必要がある。機械的な横展開は、文脈を無視した瞬間に別の重大な事故を生む。

## まとめ

今回の根本原因は、突き詰めれば「S3への書き込みが`true`を返した時点で、その効果が外部から観測可能になっているとは限らない」という、地味だけれど本質的な事実でした。

> **「操作が成功を返した」ことと「実際に永続化された」ことは別物である。外部ストレージへの書き込みは、常に検証してから確定として扱うべきで、単純な戻り値チェックはこの差分を検出できない。**

これはS3やLaravelに限った話ではありません。ローカルディスクへの同期的な書き込みという「緩衝地帯」を手放し、ステートレスなクラウドネイティブ構成に移行すると、こうした確率的な整合性の揺らぎがそのままユーザーに届く形で顕在化します。B/Gデプロイやオートスケーリングのために手に入れたステートレス化は、同時にこの種の罠と向き合う覚悟も要求してくるのだと感じた経験でした。

外部ストレージへの書き込みを伴う機能を持つ方の参考になれば幸いです。
