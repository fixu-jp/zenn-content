## はじめに

以前「[AIネイティブ開発の基盤ができるまで](https://zenn.dev/fixu/articles/ai-native-platform-rebuild-story)」という総集編を書きました。長年運用してきた Laravel モノリスを複数のマイクロサービスに分割し、EC2 から ECS Fargate へ移行するまでの物語です。その記事の終盤に「新旧環境の並行稼働と監視強化で膨らんだクラウド費用を月額20%超削減した」と一段落だけ書きました。本記事はその一段落を、費用という軸で一本に引き伸ばした姉妹編です。

先に断っておくと、金額そのものは出しません。代わりに、移行前の1〜3月の月平均を **100pt** として、各月の請求額がその何割だったかで話を進めます。数字はすべて AWS の Cost Explorer の実績（9月は見込み、10月は計画）を丸めたものです。

結論を一枚にすると、こうなります。

```
 1月 ██████████████████████████████ 100
 2月 ██████████████████████████████ 100
 3月 ██████████████████████████████ 100  ← 移行前のベースライン
 4月 ████████████████████████████████████ 120
 5月 ██████████████████████████████████████████ 140
 6月 ████████████████████████████████████████████████ 160  ← 新旧並行・増強のピーク
 7月 ████████████████████████████████████████████████ 160
 8月 █████████████████████████████████ 110  ← 第1次最適化（5日間）
 9月 ████████████████████████ 80  ← 第2次最適化（4日間）※見込み
10月 ██████████████████ 60  ← Aurora の Provisioned 化 ※計画
```

サーバの数は増えています。移行前は役割ごとに分けた EC2 が十台前後でモノリスを動かしていましたが、いまは本番・ステージング・開発の3環境で常時50前後のコンテナが走っています。マイクロサービス化とは、そういうことです。それでも費用は移行前を下回りました。

この記事で持ち帰っていただきたい核を、一文で書いておきます。

> クラウド費用を決めるのは「一般的に良いとされる構成」ではなく「自分のサービスの実態に合っているか」である。そして、実態に合わせて最適化し続ける作業は、AIが調査から実行までを数日に圧縮したことで、はじめて人件費に見合う仕事になった。

---

## 1. 移行前 — 100pt の中身

まず、ベースラインの構成を振り返ります。EC2 上で Laravel モノリスが動き、DB は Aurora MySQL（Serverless v2）、セッションとキャッシュは ElastiCache（Redis）、前段に ALB という、構築当時としてはごく一般的な構成です。

費用の内訳を見ると、DB が全体の4割強、ロードバランサーが約16%、EC2 が約1割、Redis が約7%、パブリック IPv4 アドレスが約6%でした。

ここで目を引くのはロードバランサーの 16% です。1つのサービスでこの比率は高い。理由は、ドメインや用途が増えるたびに ALB を1本ずつ立ててきた歴史でした。過去に提供していたサービス、実験的に作った窓口、特定のお客様向けの入口——それぞれに ALB とパブリック IP が付き、役目を終えたあとも構成の一部として残っている。一本一本は小さいのですが、積み上がると DB の次に大きい費目になっていました。

もう一つは監視です。CloudWatch の費用はほぼゼロでした。これは「安く済んでいる」のではなく「アプリケーションの中を見る手段が限られていた」ことの裏返しで、[総集編](https://zenn.dev/fixu/articles/ai-native-platform-rebuild-story)に書いたとおり、監視はサーバーの CPU 使用率といったインフラ層に留まっていました。

> **章末の蒸留**: 「構築当時の一般的な構成」は当時の正解であって、いまの正解ではない。一般解と実態のズレは費用の内訳に静かに積み上がり、しかも内訳を見ない限り気づけない。

## 2. 4〜6月 — 120→160、意図して増やした時期

4月から6月にかけて、費用は 100 から 160 へ 1.6 倍になりました。増分 60pt の内訳は、DB が約22、コンテナ実行（Fargate）が約20、NAT ゲートウェイとストレージが約9、監視（CloudWatch）が約8です。これは事故ではなく、二つの意図の結果でした。

### 2-1. 性能問題をマシンパワーで殴る

移行を進める間も、既存サービスの性能課題は待ってくれません。重い画面が数十秒かかる、集計処理が本番の書き込みを待たせる。根本対策には索引の整備やロックの見直しが必要ですが、それには調査と検証の時間がかかる。そこでまず、Aurora にリーダーインスタンスを追加して読み取り負荷を分散し、Serverless v2 の上限 ACU にも余裕を持たせ、コンテナのタスクサイズも大きめに取りました。いわゆる「マシンパワーで殴る」対処です。

これは正しい順序だったと思っています。お客様の体感を先に守り、根本対策は並行して進める。ただし、殴った分の費用は「根本対策が終わったら戻す」前提で積んだものです。この前提を忘れると、増強は恒久化します。

### 2-2. 新環境を建てる

同時に、移行先の環境を構築しました。開発・ステージング・本番の3環境に加え、検証用の4つ目の環境。それぞれに VPC、NAT ゲートウェイ、ALB、ECS クラスタ、Redis。さらに移行期は旧環境も動いているので、コンピュートとネットワークが二重になります。

監視も強化しました。全クラスタで Container Insights を有効化し、アプリケーションログを CloudWatch Logs に集約。移行期の問題を早く見つけるための投資で、監視費用は移行前の数十倍になりました。

> **章末の蒸留**: 移行期の二重費用と暫定増強は投資であり、増えること自体は問題ではない。問題になるのは「戻す日」を決めずに増やしたときで、戻す日は増やす日に決めておく。

## 3. 7〜8月 — 160→110、第1次最適化

7月に本番の段階的切替（重み付きカナリアで約3週間）が進み、旧環境の役目が順に終わっていきました。そして7月下旬、5日間で第1次の最適化を実施しました。結果、8月の請求は 110 まで下がりました。

### 3-1. リーダーインスタンスの廃止 — 品質改善と費用削減は同根

一番大きかったのは Aurora のリーダー廃止です。これができたのは、並行して進めていたアプリケーション側の根本対策が効いていたからでした。集計処理のロック問題の解消（「[集計バッチが本番の書き込みを止めていた](https://zenn.dev/fixu/articles/insert-select-lock-read-committed)」）、索引の整備、重い画面の事前集計化。スロークエリが減り、ライターだけで読み取りを引き受けても p90 応答時間は維持できました。

正直に書くと、削減幅は当初見込みより小さかったです。リーダーを消しても読み取り負荷そのものは消えないので、ライターの ACU がその分上がります。正味の削減はリーダー単体の費用の4割ほどでした。「消せば全部浮く」は推測で、計測すると4割だった——という典型例です。

### 3-2. 実測で「増強したまま」を戻す

コンテナの実測 CPU 使用率を並べると、大半のサービスが 1% 未満でした。ワーカー系のタスクサイズを一律に半分以下へ、暫定増強していたフロント系のタスクも元のサイズへ。メモリの実使用率が一桁%だったので、性能上のリスクはほとんどありませんでした。

ここで一つ、計測しなければ見えなかった発見がありました。オートスケーリングのターゲット追跡ポリシーが、Blue/Green デプロイのあとに旧ターゲットグループ（トラフィックがゼロになった側）を監視し続ける構成になっていたのです。負荷が低いのになぜタスク数が張り付いているのか——を追って判明しました。ポリシーを CPU 使用率ベースに切り替えて、この構造を解消しました。

### 3-3. 役目を終えたものを消す

退役済みの ALB を十数本、停止済みの EC2 を5台、非本番環境の Container Insights、そして Redis を2ノードから1ノードの小さいサイズへ。どれも「本当に使われていないか」を DNS の参照とアクセスログで確認してから削除しました。

> **章末の蒸留**: 増強は一瞬で、縮退には根拠がいる。根拠を作るのは計測であり、計測すると「増やしたまま」になっていたものと、増やした理由が既に消えているものが見えてくる。

## 4. 9月 — 110→80、第2次最適化

9月頭、今度は4日間で第2次の最適化を行いました。8月の 110 は移行前と同水準ですが、内訳を見ると移行前とは別物になっています。DB 45%、コンテナ 18%、NAT とストレージ 13%。この内訳に沿って「なぜ高いのか」を一つずつ計測しました。

### 4-1. NAT の費用の正体

NAT ゲートウェイのデータ処理料が移行前の3倍になっていました。ユーザートラフィックが3倍になったわけではありません。転送量を環境ごと・時間帯ごとに並べると、毎時きれいなバーストが出ています。正体は、キューワーカーが1時間ごとに自分を再起動する設定（`queue:work --max-time=3600`）でした。再起動のたびに ECS がタスクを作り直し、ECR からコンテナイメージ約 250MB を NAT 経由で取得する。ワーカー数×環境数×24時間で、月に数 TB です。

ECR のイメージレイヤの実体は S3 なので、**無料の S3 ゲートウェイエンドポイント**を各 VPC に1本ずつ足すだけで、この転送は NAT を通らなくなります。導入後、NAT の流入は毎時 1〜3GB から 5分あたり数 MB になりました。

### 4-2. 使わない時間は止める

開発環境とステージング環境を、平日 9時に起動、23時に停止するスケジュール運用にしました。Application Auto Scaling のスケジュールアクションで全サービスの最小・最大タスク数を 0 にする方式です。

設計で迷ったのは「厳密なアイドル検知（実利用がなくなったら止める）」にするかどうかでした。実測すると、固定時刻方式との差は月に 1pt 未満。しかもステージングの早朝・週末トラフィックの大半は検索エンジンのクローラで、アイドル検知には除外ロジックが必要になります。1pt 未満のために複雑さを買う理由はなく、固定時刻を採用しました。

一つだけ、運用上の落とし穴がありました。AI の開発セッションは夜間もデプロイします。停止中の環境にデプロイが走ると失敗するので、デプロイパイプラインの先頭に「環境が停止中なら起こす」処理を入れました。

### 4-3. その他

- 14日間利用のなかった検証環境を、定義ごと破棄
- 本番の Container Insights を無効化（依存していたアラームは役割を終えていたため廃止）
- 利用率の低い Redis ノードを集約（ElastiCache の RBAC でユーザーとキー空間を環境別に分離したうえで）
- 旧環境に残っていた ALB・停止中 EC2・古い AMI とスナップショットの整理。切替後の旧ロードバランサーは、転送先サーバのアクセスログを送信元で経路分けし、実利用ゼロを確認してから削除

合計で、8月時点の月額の約 24% を削りました。9月の見込みは 80。移行前を下回ります。

> **章末の蒸留**: 費目が高い理由は、たいてい構成の前提の中にある。「ワーカーは毎時再起動する」「監視は全環境で厳密に」——それ自体は妥当な前提でも、費用という別の面から見ると答えが変わる。

## 5. 10月 — 60（計画）、Aurora Serverless v2 からの脱却

ここからは計画です。残る最大の費目は DB で、全体の半分近くを占めます。

Aurora Serverless v2 は、負荷に応じて ACU（2GiB メモリ相当の単位）が伸縮し、使った ACU 時間で課金されます。負荷が読めないサービスには理想的です。ところが実測すると、こうなっていました。

- ACU は時間平均で 16、夜間でも一桁台後半を下回らない
- 一方、CPU の実効需要は平均 0.7、ピークで 1.5 vCPU 相当
- バッファキャッシュのヒット率は 100%（時間内最小でも 99.5%）

つまり ACU の「床」を支えているのは CPU ではなく、バッファプール——メモリです。Serverless v2 はメモリ需要に合わせて ACU を維持するので、CPU が暇でもメモリ分の課金が続く。データサイズが安定していてヒット率が飽和しているワークロードでは、この構造は割高です。

固定サイズの Provisioned インスタンス（db.r6g.xlarge、32GiB）なら、いまの平均割当メモリと同等をオンデマンドで持って現状の 4 分の 1 強、1年リザーブドなら 6 分の 1 程度になります。手順は「同一クラスタに Provisioned インスタンスを追加 → 深夜にフェイルオーバーでライターを切替 → Serverless インスタンスを削除」で、データ移行はなく、切替は数十秒、可逆です。

もっとも、ここは慎重に進めます。月に数時間ある ACU 64 級のピークを固定サイズでは自動吸収できないため、切替後2週間は CPU・空きメモリ・ヒット率・ピーク時間帯の p90 を観察し、余裕があれば一段小さいサイズへの縮退も検討します。リザーブドインスタンスの購入はサイズが確定してから。Savings Plans も同じで、コンソールの推奨値は「変更前の使用量」を根拠にしているので、いまの実績が溜まってから再算定します。

> **章末の蒸留**: 「一般に良い」構成でも、自分の負荷特性に合わなければ高い。Serverless が悪いのではなく、メモリ主導で床が固まる負荷には向いていなかった、というだけの話。

## 6. なぜ、いまこれができるのか

ここまでの施策は、どれも特別な技術ではありません。S3 ゲートウェイエンドポイントも、スケジュールによる停止も、Provisioned への切替も、AWS の資料に書いてある定番です。「知らなかった」のではなく「やらなかった」——なぜか。

人間の専門家がやると、費用の内訳分析、各費目の原因調査、代替構成の試算、IaC の変更、告知、実施、事後監視まで、SRE が片手間ではなく数週間から数か月かける仕事になります。そしてその人件費は、削減額と見合わないことが多い。月額の 20〜30% の削減のために専門家を数か月張り付けるなら、放っておくほうが安い。だからクラウド費用の最適化は、多くの組織で「いつかやる」に分類されてきました。

今回、第1次は5日、第2次は4日でした。AI（Claude Code）が Cost Explorer と CloudWatch を読んで内訳を分解し、ログを集計して原因を特定し、Pricing API で代替案を試算し、Terraform を書いて変更し、リリース後の指標を監視する。人間がやったのは、方針の確定（触ってよい領域と触らない領域の線引き）、各施策の GO/NO-GO、本番影響のある変更の告知、そして「その推測は計測したか」という問いかけです。

これは「[推測から計測へ](https://zenn.dev/fixu/articles/measure-dont-guess-ai-native)」と「[実装工数はもう tie-breaker ではない](https://zenn.dev/fixu/articles/ai-architecture-decision-beyond-effort)」で書いた変化の、インフラ費用版です。計測の費用が下がると、推測で放置していた費目を一つずつ検証できる。実行の費用が下がると、「見合わない」と判断されていた最適化が見合うようになる。費用最適化はもう年に一度の棚卸しではなく、構成が変わるたびに回す定常作業になりました。

> **章末の蒸留**: 最適化の技術は昔からあった。変わったのは技術ではなく、最適化の採算である。

## まとめ

| 時期 | pt | 何が起きたか |
|---|---|---|
| 1〜3月 | 100 | 構築当時の一般的構成。DB 4割強、ロードバランサー 16% |
| 4〜6月 | 120→160 | 性能対策の増強＋新環境構築＋監視強化。意図した増加 |
| 7〜8月 | 160→110 | 段階的切替、第1次最適化（5日）。リーダー廃止、適正サイズ化、退役資産の削除 |
| 9月 | 80（見込） | 第2次最適化（4日）。S3 ゲートウェイエンドポイント、非本番の停止スケジュール、検証環境破棄 |
| 10月 | 60（計画） | Aurora を Provisioned へ。実績が溜まったら RI / Savings Plans |

サーバの数は増え、監視は厳密になり、環境は3つになり、それでも費用は移行前を下回りました。決め手は高価な構成でも安価な構成でもなく、実態を計測し、実態に合わせて構成を変え続けたことです。そしてその作業を「見合う」ものにしたのが AI でした。

10月の Aurora 切替が終わったら、実績値でこの記事を更新します。
