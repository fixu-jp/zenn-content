## はじめに

マイクロサービス構成のシステムを運営していると、複数のリポジトリに「同じパターン」の変更を入れるケースが頻繁に発生します。

筆者のチームでは現在、9つのマイクロサービスリポジトリを共通パターンで整備するプロジェクトを進めています。1つのリポジトリで確立したパターンを、残り8つに横展開するのが主な作業です。

ある日、1リポジトリで検証済みの変更を8リポジトリに一気に並列展開しました。各PRにGitHub Copilotをレビュアーに追加したところ、**同一の変更にもかかわらずレビューの指摘内容にばらつきが生じている**ことに気づきました。

最初はノイズに見えたこの「ばらつき」が、実は品質保証の強力なシグナルになることを発見しました。この記事はその経験と、そこから導いた運用プロトコルをまとめたものです。

## 観測された現象

8つの PR は、いずれも同じパターンから機械的に生成された変更でした。しかし Copilot のレビューコメントを並べてみると、指摘内容が PR ごとに微妙に異なります。

- ある PR では「Makefile の grep パターンが対象フレームワークの出力形式に合っていない」と指摘される
- 別の PR では同じ問題に加えて「README の状態確認メッセージが実態と不一致」も指摘される
- また別の PR では両方ともスルーされる

「同じ変更なのに、なぜ同じ指摘が全 PR に来ないのか？」

### 仮説：LLM の確率的挙動

LLM は temperature > 0 で動作するため、同一の入力でも出力が確率的に変動します。加えて：

- **文脈差異** — リポジトリごとにモジュール名・コメント・隣接コードが微妙に異なる
- **タイミング差** — PR を出すタイミングが数分ずれるだけでモデルの状態が変わりうる

これは LLM の「弱点」として知られています。しかし、**並列運用においては全く別の見方ができます。**

## 従来のアプローチの限界

通常、PR は独立してレビュー・対応されます。

```text
PR #1 → Copilot レビュー A → 開発者が個別対応
PR #2 → Copilot レビュー B → 開発者が個別対応
...（8本が独立並列）
```

このアプローチには3つの問題があります。

**1. 指摘の部分集合しか捕捉できない**

各 PR が受け取るのは確率的なサンプルであり、重要な指摘が偶然スルーされる可能性があります。

**2. パターン展開なのに修正がドリフトする**

同じ変更から派生しているのに、PR ごとに対応内容が異なり、最終的な実装が乖離します。「全リポジトリで統一されたパターン」という前提が崩れます。

**3. 誤指摘と正指摘の切り分けが困難**

1 PR で見ると、Copilot のコメントが的外れなのか重要な指摘なのか判断が難しい。結果として、重要な指摘を見落としたり、逆に不要な対応をしてしまうことがあります。

## 発見した原則：「パターン複製のレビューは、パターンレベルで扱う」

N リポジトリにパターン複製するとき、**レビューも N 件まとめてパターンレベルでトリアージする**という原則です。

```text
PR #1〜#8 → Copilot レビュー 8件 → 【集約・トリアージ】
                                          ↓
                                    確定 fix → 8 PR に並列適用
```

ここで重要なのは副次効果です：

- **N 件中 k 件で同じ指摘が出る** → それは noise ではなく signal（k が大きいほど確実性が高い）
- **1 件だけに出る指摘** → 文脈固有の問題か、または LLM のハルシネーション候補

LLM の確率的ばらつきが、**自然なアンサンブル投票**として機能するわけです。

## 実際のクロスリファレンス表（匿名化済み）

実際の作業で 8 PR の Copilot レビューを集約した結果です。

| # | 指摘トピック | 出現数 | 判定 |
|---|---|---|---|
| A | Makefile の `grep` コマンドがフレームワークの出力形式に合っていない | 7/8 | universal fix |
| B | README の状態確認メッセージが実態と不一致 | 5/8 | universal fix |
| C | `.env` の URL 設定にポート番号漏れ | 4/8 | local fix |
| D | `docker compose exec` に `-T` フラグが必要 | 2/8 | universal fix |
| E | 証明書セットアップ（`mkcert -install`）が毎回実行される | 2/8 | universal fix |
| F | `/etc/hosts` にローカルドメインの漏れ | 2/8 | local fix |
| I | 設定レイヤー間で URL 不整合 | 2/8 | universal fix |
| G | HTTPS 検証がリダイレクト先まで確認されていない | 1/8 | I と合わせて対応 |
| H | `.PHONY` 宣言がない | 1/8 | universal fix |
| J | ポート一覧表にドメイン漏れ | 1/8 | local fix |
| K | DB 未起動時の事前チェックがない | 1/8 | universal fix |
| L | `make clean` の説明が不正確 | 1/8 | local fix |
| M | DB ホストがコンテナ名依存になっている | 1/8 | ignore（設計変更を伴うため別対応） |

### この表から読み取れること

**出現頻度 = 信頼スコア**として機能しています。

- **A（7/8）** は圧倒的な確実性。全リポジトリで修正すべき明確な signal。
- **B〜I（2〜5/8）** も統計的に有意。universal または local fix が妥当。
- **H（1/8）** が興味深い。出現数は1件だが、Makefile に `.PHONY` 宣言がないのは共通パターンとして明らかに直すべき問題です。「出現頻度だけでなく、パターンの本質的な正しさも判定基準に入れる」のがポイントで、**1件でも全リポジトリに universal 適用**と判断しました。
- **M（1/8）** も1件ですが、対応には設計変更を伴うため ignore。別の機会に改めて議論します。

H と M はどちらも 1/8 ですが、判定が分かれます。これがトリアージの核心部分です。

## 実装プロトコル（Phase 1〜4）

### Phase 1: 集約

全 PR の Copilot レビューコメントを1か所に集めます。スプレッドシートでも、AI に処理させる形でも構いません。

重要なのは、**PR 横断で同じ指摘を名寄せ**することです。「Makefile の grep」「grep コマンドの修正」「grep -c が動かない」は同じ指摘として集約します。

### Phase 2: トリアージ

各指摘を3分類します：

| 分類 | 条件 | 対応 |
|------|------|------|
| **universal** | N 件中複数で出現、または出現数が少なくともパターンとして正当 | 全リポジトリに適用 |
| **local** | 特定リポジトリ固有の文脈による正当な指摘 | 該当リポジトリのみ適用 |
| **ignore** | ハルシネーション・誤指摘・対応コストが不相応に大きい | 対応しない（メモして保留） |

### Phase 3: 並列適用

確定した fix を N リポジトリに一括適用します。このフェーズは AI エージェントが得意とする作業です。

```bash
# 概念的な実装例
fixes=(
  "Makefile: grep コマンドをフレームワーク出力形式に合わせる"
  "docker-compose: exec に -T フラグを追加"
  "Makefile: .PHONY 宣言を追加"
  "Makefile: DB 未起動時の事前チェックを追加"
)

repos=(repo1 repo2 repo3 repo4 repo5 repo6 repo7 repo8)

for repo in "${repos[@]}"; do
  for fix in "${fixes[@]}"; do
    apply_fix "$repo" "$fix"
  done
done
```

実際には Claude Code などの AI エージェントに fix 仕様を渡して並列実行するのが効率的です。

### Phase 4: 再レビュー

修正後の PR を再度レビューします。理想的には指摘が収束（重複コメントが消える）していきます。収束しない場合は Phase 2 のトリアージ判断を見直します。

## 適用範囲の広がり

このプロトコルは「同じ変更を N 箇所に適用する」あらゆる場面に一般化できます：

| シナリオ | 内容 |
|----------|------|
| **横展開** | 1リポジトリで確立したパターンを N リポジトリに適用 |
| **依存アップデート** | 共通ライブラリ・フレームワークのアップデートを N サービスに適用 |
| **廃止コード削除** | 廃止 API や Feature Flag を N リポジトリから一括削除 |
| **リファクタ** | コード規約変更・命名統一を N リポジトリに横断適用 |

N が大きいほど、LLM レビューのアンサンブル効果が強くなります。

## おわりに

LLM の確率的挙動は、しばしば「信頼できない理由」として挙げられます。確かに、1回のレビューに全面依存するのは危険です。

しかし、**N 個の並列コンテキストで同じ LLM を動かす**と、その確率的ばらつきが品質シグナルとして機能し始めます。出現頻度が信頼スコアになるのです。

今回の経験から感じた、AI ネイティブな開発における重要な姿勢：

> **「LLM をそのまま信頼しない。構造で信頼性を作る。」**

LLM の弱点を補うのは、別の LLM ではなく、**運用の設計**です。並列パターン展開という文脈が、偶然にも LLM レビューのアンサンブルを生み出しました。これを意図して設計できれば、さらに強力な品質保証の仕組みになるはずです。

マイクロサービスを横断したパターン整備や、大規模リファクタリングに取り組む方の参考になれば幸いです。
