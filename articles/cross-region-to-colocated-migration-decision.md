## はじめに

大阪リージョンに新しいマイクロサービス環境を構築しました。compute は大阪、DB は東京。9つのサービスをデプロイし、ステージング環境も整備し、本番切替の準備を進めていました。

結論から言うと、この大阪環境を全て破棄し、東京リージョンに作り直しました。

大阪の環境が使えなかったわけではありません。チューニングすれば本番運用は可能でした。それでも東京に戻したのは、「**移行先の選定基準はコストでもレイテンシでもなく、リリース安全性で決まる**」という判断に至ったからです。

本記事では、クロスリージョン構成を選んだ経緯と、それをやめて同一リージョン集約に切り替えた意思決定の過程を振り返ります。想定読者は、マイクロサービスの移行やリージョン選定を検討しているインフラエンジニア・SRE です。

## 1. 当初の計画：クロスリージョン構成

私たちのサービスは、東京リージョンの EC2 上で Laravel モノリスとして稼働していました。これを9つのマイクロサービスに分割し、ECS Fargate へ移行するプロジェクトを進めていました。

移行先として大阪リージョンを選んだ理由は、**既存環境との「クリーンな分離」** です。

- 東京リージョンには旧環境の EC2、ALB、各種リソースが稼働中
- 同じリージョンに新環境を構築すると、命名の衝突やリソースの混在が起きやすい
- 大阪リージョンなら、完全にクリーンな状態から始められる

ただし、Aurora（RDS）は移行コストが大きいため東京に据え置きました。結果として、以下のクロスリージョン構成になりました。

| コンポーネント | リージョン | 備考 |
|---|---|---|
| Compute（ECS Fargate） | 大阪 | 新規構築 |
| Aurora（MySQL） | 東京 | 既存を共有 |
| Redis（ElastiCache） | 大阪 | 新規構築 |
| 接続経路 | VPC Peering | 大阪↔東京クロスリージョン |

この構成は機能的には動きます。VPC Peering でリージョン間を接続し、大阪の compute から東京の Aurora へクエリを投げる。設計としてはシンプルです。

> 学び：「クリーンな分離」は正当な動機だが、それを実現する手段はリージョン分離だけではない。同一リージョン内の別 VPC でも同じ分離は達成できる。

## 2. クロスリージョンの構造的コスト

構成が動くことと、本番運用に耐えることは別です。リリースの段取りを詳細に詰めていく過程で、クロスリージョン構成には当初の想定を超える構造的なコストがあることが見えてきました。

### DB 往復レイテンシの積算

ステージング環境で、1クエリあたりの純粋な往復時間（RTT）を実測しました。

| 環境 | 経路 | 純 RTT（1往復） |
|---|---|---|
| 東京 同一リージョン配置 | 同一リージョン Peering | **0.2ms** |
| 大阪 クロスリージョン | 大阪↔東京 Peering | **8.4ms** |
| 差 | — | **約40倍** |

1クエリ 8ms の差は、一見すると小さく感じます。しかし、Laravel の `DB::select` は内部的に prepare + execute の2往復を行うため、実効的には **1クエリあたり約16ms** のペナルティになります。

1リクエストで13〜14のクエリを発行する画面では、クロスリージョンだけで **+200ms 以上** の遅延が積み重なります。実測でも、同一リクエストの応答時間は東京で約11ms、大阪で約71ms と **約6倍の差** が出ました。

### デプロイ手段の制約

もう一つの構造的コストは、**リリース手段が DNS 全切替に限定される**ことでした。

大阪の compute に切り替えるには、Route53 の DNS レコードを東京の ALB から大阪の ALB に一括で向け直す必要があります。これは「全か無か」の切替です。

- トラフィックの100%が一瞬で新環境に流れる
- 問題時のロールバックは DNS の TTL に依存する（即時ではない）
- 段階的なトラフィック移行（10%→50%→100%）ができない

この制約は、クロスリージョン構成に固有のものです。ALB のリスナールールで weighted forward（重み付きルーティング）を使うには、ターゲットが同一リージョンの IP アドレスでなければなりません。**リージョンをまたいだ時点で、段階リリースという選択肢が構造的に失われます。**

> 学び：クロスリージョンの隠れたコストはレイテンシだけではない。デプロイ手段の選択肢を狭めるという、リリース戦略レベルの制約がある。

## 3. 東京集約が優れる理由

クロスリージョンの構造的制約を認識したうえで、代替案を検討しました。compute を東京リージョンの別 VPC に置く構成なら、クロスリージョンの2つの問題が両方解消します。

### レイテンシの構造的改善

| 指標 | 大阪（クロスリージョン） | 東京（同一リージョン配置） | 改善 |
|---|---|---|---|
| DB 純 RTT | 8.4ms | 0.2ms | 40倍 |
| `DB::select` 実効 | ~16ms/query | ~0.4ms/query | 40倍 |
| 代表的リクエスト応答 | ~71ms | ~11ms | 6倍 |

東京内の VPC Peering（同一リージョン）の遅延は約0.07ms で、実質ゼロです。「Peering を経由するから遅くなるのでは」という懸念は、実測で否定されました。

### カナリアリリースによるリリース安全性

東京集約の最大のメリットは、**weighted canary（重み付きカナリアリリース）** が可能になることです。

既存の ALB（東京リージョン）に、新環境のターゲットグループを ip-target で追加できます。同一リージョンの Peered VPC 内の RFC1918 アドレスは ALB のターゲットとして登録可能（AWS 公式仕様）だからです。

これにより、

- **段階的なトラフィック移行**：weight 10% → 50% → 90% → 100% で段階リリース
- **即時ロールバック**：weight を 100:0 に戻すだけ。DNS の TTL に依存しない、秒単位の切り戻し
- **影響範囲の限定**：問題が起きても、影響を受けるのは当該 weight 分のトラフィックだけ

DNS 全切替と比較すると、リスクの構造が根本的に異なります。

| 項目 | DNS 全切替（クロスリージョン） | weighted canary（同一リージョン） |
|---|---|---|
| 切替の粒度 | 100% 一括 | 10% → 50% → 100% 段階 |
| ロールバック速度 | DNS TTL 依存（分〜時間） | weight 変更（秒） |
| 影響範囲（問題時） | 全トラフィック | weight 配分のトラフィックのみ |
| 前提条件 | compute と ALB が別リージョン | compute と ALB が同一リージョン |

### 最終形のクリーンさ

移行期だけ既存 ALB を使い、安定後は新 ALB（IaC 管理）に一本化する計画です。

- **移行期**：既存 ALB で旧ターゲットと新ターゲットを weighted forward で共存
- **恒久**：新 ALB（新 VPC と同一、Peering 不要）に一本化
- **VPC Peering** の役割は Aurora 接続専用に純化

当初の動機だった「クリーンな分離」は、東京の別 VPC でも同じように達成でき、最終的にはより素直なアーキテクチャに収束します。

> 学び：移行先の選定基準は「コスト」「レイテンシ」の先にある。「どうやって安全にリリースするか」が移行先を規定し得る。

## 4. 方針転換で追加で払ったコスト

方針転換には当然コストが伴います。ここは隠さずに書きます。

### 大阪環境の全面破棄

すでに3環境（dev / stg / prod）× 9サービスをデプロイ済みでした。これを全て破棄しました。

- ECS サービス・タスク定義・ターゲットグループ
- Redis（ElastiCache）
- ECR リポジトリ（大阪側）
- VPC Peering（クロスリージョン経路）
- Secrets Manager / SSM パラメータ
- CloudWatch アラーム / Observability 設定

技術的には Terraform destroy とリソース削除ですが、心理的には「動いているものを壊す」重さがありました。

### 東京環境の新規構築

大阪と同等の環境を東京に一から作り直しました。

| 作業 | 規模 |
|---|---|
| インフラ基盤（VPC / ALB / ECS cluster / Redis / Peering / Route53） | Terraform apply 72リソース |
| デプロイパイプライン（deploy.yml + infra） | 9リポジトリ × 3環境 |
| Secrets / SSM パラメータ投入 | laravel_env 27件 + DB credentials + SSM 各種 |
| IAM 権限整備 | CI ロールの trust policy、Secrets 読み取り権限 |
| GitHub Environment 作成 | 全9リポ × 本番環境 |

延べ2日程度を東京環境の構築に費やしました。大阪環境の構築にかけた時間と合わせると、環境構築に二重のコストを払ったことになります。

### スケジュールの後ろ倒し

大阪環境で進めていた本番切替の計画は白紙に戻りました。東京環境の構築・検証を経て再開するため、リリーススケジュールが数日後ろにずれました。

### やり直しの心理的コスト

「すでに動いている環境を捨てて作り直す」判断には、サンクコストの重さがあります。大阪環境のステージングで負荷試験を回し、パラメータを調整し、その過程で得た知見は東京環境にも活きますが、成果物そのものは破棄です。

> 学び：方針転換のコストは「新しく作る工数」だけではない。「すでに作ったものを捨てる」心理的コストと、スケジュールの後ろ倒しが合算される。サンクコストを認識したうえで、それでも転換すべきかを判断する必要がある。

## 5. それでも東京集約を選んだ理由

追加コストを払ってでも東京集約を選んだ理由は、**リリース安全性は一度のコストではなく、今後の全リリースに効く構造的な投資** だからです。

### 短期コスト vs 長期の構造便益

| 観点 | 大阪を続ける場合 | 東京に作り直す場合 |
|---|---|---|
| 環境構築の追加コスト | なし | 約2日の再構築 |
| 今後のリリース手段 | DNS 全切替（毎回） | weighted canary（毎回） |
| ロールバック速度 | TTL 依存（毎回） | 秒単位（毎回） |
| DB レイテンシ | +200ms/リクエスト（恒久） | 構造的に解消（恒久） |
| 単一障害点 | 旧 EC2 と同じ SPOF 構造 | multi-AZ ECS で解消 |

2日の追加工数は一度きりのコストです。一方、weighted canary のメリットは今後のすべてのリリースに適用されます。DNS 全切替のリスクを毎回背負い続けるのか、一度作り直して構造的に安全な手段を手に入れるのか。時間軸を伸ばせば、答えは明白でした。

### 「大阪である必然」がなかった

方針転換を後押ししたのは、「そもそもなぜ大阪を選んだのか」を改めて問い直したことでした。

大阪を選んだ理由は「既存環境とのクリーンな分離」です。しかし、この分離は東京リージョン内の別 VPC でも同じように達成できます。大阪でなければならない戦略的理由——たとえば DR（災害復旧）要件や、リージョン固有の規制要件——はありませんでした。

**手段（リージョン分離）と目的（クリーンな分離）を混同していた**、というのが振り返りでの気づきです。目的に立ち返れば、大阪を選ぶ理由は最初からなかった。

> 学び：「すでに作ったから続ける」はサンクコストの罠。移行先の選定は、「当初なぜそこを選んだか」に立ち返り、その理由が今も有効かを検証することで、正しい判断に近づく。

## まとめ

本記事の要点を整理します。

| 判断のステップ | 内容 |
|---|---|
| 当初の選定理由 | 「既存環境とのクリーン分離」→ 大阪リージョン |
| 見落としていたコスト | DB レイテンシ40倍 + リリース手段が DNS 全切替に限定 |
| 転換の決め手 | weighted canary は同一リージョンでのみ実現可能 |
| 追加で払ったコスト | 大阪破棄 + 東京再構築（2日）+ スケジュール後ろ倒し |
| 最終判断 | 短期コストより長期のリリース安全性を優先 |

一般化すると、インフラ移行先の選定で見落としやすいのは「**その構成で、どうやって安全にリリースするか**」という問いです。

コストやレイテンシは見積もりやすく、比較表にも載りやすい。しかし、リリース手段の選択肢——段階的なトラフィック移行ができるか、即時ロールバックが可能か——は、構成を決めた後で初めて顕在化する制約であり、事前の見積もりに含まれにくい。

次にリージョンや移行先を選ぶとき、コストとレイテンシの比較表を作ったら、もう一行追加してみてください。**「この構成で、段階リリースと即時ロールバックはできるか」** と。その一行が、移行先の選定を変えるかもしれません。
