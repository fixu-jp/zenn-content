## はじめに

木曜の朝、AWS Health から1通の通知が届きました。「[要対応] Amazon Aurora MySQL バージョン 3.08 と 3.09 が 2026 年 8 月 31 日に EoS に到達」。本番データベースが該当します。

この通知、後半にさらっと重要なことが書いてあります。

> Amazon RDS は、マイナーバージョン 3.08 または 3.09 を実行している Amazon Aurora MySQL データベース（中略）を、2026 年 8 月 31 日以降に予定されているメンテナンス期間中に Amazon Aurora MySQL 3.10.3 以降のバージョンに自動的にアップグレードします。

つまり放置すると、**日時を選べない強制アップグレード**に変わります。「これは必須のエンジンバージョンアップグレードであり、ダウンタイムが必要です」とも明記されています。

先に持ち帰ってほしいことを書きます。

> **EoS 通知への対応の本質は「アップグレードするかどうか」ではなく、「日時を自分で選べるうちに、リスクを検証済みの状態で実施する」こと。クローン2面でのリハーサルと本番 SQL の全量キャプチャ&リプレイまで AI エージェントに任せれば、通知当日に検証全グリーン、2日後の深夜に接続断ゼロで本番完了まで持っていける。**

実際に今回は、木曜朝に通知を受け、その日のうちに検証を全て終え、土曜未明の3分弱で本番アップグレードを完了しました（切断されたコネクションはゼロ）。本記事はその手順を Aurora MySQL 共通のガイドとして一般化してまとめたものです。最後に、一連の作業を AI に実行させるためのプロンプトも載せます。

## 1. EoS 通知を読み解く — 3つの期限

通知文には期限が3つ埋まっています。

| 期限 | 内容 | 実務上の意味 |
|---|---|---|
| 2026/8/1 | 3.08 / 3.09 での新規インスタンス作成がコンソール・CLI から不可に | **検証用クローンも作れなくなる（これが一番怖い）** |
| 2026/8/31 | 標準サポート終了（EoS） | パッチ提供が止まる |
| 8/31 以降 | メンテナンスウィンドウで 3.10.3 以降へ自動アップグレード | 日時を選べない・ダウンタイムあり |

見落としがちなのが1つ目です。EoS の1ヶ月前から旧バージョンでの新規作成がブロックされるため、「旧バージョンのクローンを作って検証する」という選択肢自体が消えます。スナップショットからの復元には猶予がありますが、確実なのは**通知を読んだ日のうちにクローンを確保してしまう**ことです。

> 学び: EoS 通知は「8/31 が期限」と読むと1ヶ月読み違える。検証環境を確保できる実質の期限は「新規作成ブロック開始日」の方。

## 2. 影響範囲の棚卸し — 制約が方式を決める

まず読み取り専用の調査から始めます。

```bash
# クラスタとバージョンの確認
aws rds describe-db-clusters \
  --query 'DBClusters[].{id:DBClusterIdentifier,ver:EngineVersion,status:Status}'

# 現行バージョンから直接上げられるバージョンの一覧
aws rds describe-db-engine-versions --engine aurora-mysql \
  --engine-version 8.0.mysql_aurora.3.08.2 \
  --query 'DBEngineVersions[0].ValidUpgradeTarget[].[EngineVersion,AutoUpgrade]'
```

今回の環境で判明した構成と制約は3つでした。

1. **全環境が単一クラスタに同居** — 開発・ステージング・本番のスキーマが同じクラスタに載っている構成だったため、「開発環境で先に実績を作ってから本番へ」という定石が同一クラスタ内では使えない。リハーサルにはクローンが必要
2. **`binlog_format=OFF`** — Blue/Green Deployments はバイナリログのレプリケーションが前提のため使えない。binlog の有効化自体に再起動が要るので本末転倒。よって**インプレース（in-place）アップグレード一択**
3. **アップグレード先は 3.10.5 を選定** — 強制適用先が「3.10.3 以降」なので、同系列の最新パッチが最も保守的な選択

なお、エンジンバージョンはクラスタ単位の属性なので「reader インスタンスだけ先に上げて試す」こともできません（writer / reader は常に同一バージョンで、マイナーアップグレードは全インスタンス同時適用です）。制約を並べると、取れる手は「クローンでリハーサル → 本番はインプレース」に自然に絞り込まれます。

ここで救いになるのが **ゼロダウンタイムパッチ（ZDP: Zero-Downtime Patching）** です。Aurora MySQL のマイナーバージョンアップグレードは、条件が揃うと再起動なしで適用され、既存の接続が維持されます。ただし長時間トランザクションの実行中などは通常再起動（数分の停止）にフォールバックします。この「ZDP が効く条件を整える」が、後の実施日時の設計に効いてきます。

> 学び: アップグレード方式は好みではなく制約から逆算する。binlog・クラスタ構成・環境同居の3点を先に棚卸しすると、選択肢は自然に絞れる。

## 3. 事前検証① — クローン2面でリハーサル

Aurora のコピーオンライト（copy-on-write）方式のクローンで検証環境を2面作ります。ストレージは差分課金なので、本番サイズのデータでも作成は数分・費用は小さく済みます。

```bash
# クローン作成（A面 / B面の2回実行）
aws rds restore-db-cluster-to-point-in-time \
  --source-db-cluster-identifier <本番クラスタ> \
  --db-cluster-identifier upgrade-verify-a \
  --restore-type copy-on-write \
  --use-latest-restorable-time \
  --db-subnet-group-name <本番と同じ> \
  --vpc-security-group-ids <本番と同じ>
```

2面作るのがポイントです。

| 面 | バージョン | 役割 |
|---|---|---|
| クローンA | 3.08.2 のまま据え置き | 比較のベースライン（旧版の挙動・性能の対照群） |
| クローンB | 3.10.5 へアップグレード | リハーサル本体 + 新版の挙動・性能 |

クローンB へのアップグレード操作が、そのまま「本番で行う操作のリハーサル1回目」になります。RDS イベントを見ると所要時間の内訳まで取れます。実測では、オンラインのプリチェックが数秒、全体で約2分15秒。そしてイベントログに、

```
Attempting to upgrade the database with zero downtime.
... 0 connections preserved, 0 connections dropped.
```

ZDP が適用されました。この実測値が「本番のダウンタイム見込み」を語る根拠になります。

> 学び: リハーサルは「動くか」だけでなく「何分かかるか」「ZDP が効くか」の実測値を取る場。ここで取った数字が本番当日の判断基準になる。

## 4. 事前検証② — 本番 SQL の全量キャプチャ&リプレイ

「クローンB で普通に動く」だけでは、本番で流れている多様なクエリが新バージョンでも同じ結果を返すかまでは分かりません。そこで本番の SQL を全量キャプチャして両クローンにリプレイし、結果を突合します。Aurora MySQL にマネージドなキャプチャ&リプレイ機能はないため、スロークエリログを使います。

**キャプチャ**: `long_query_time` を 0 にすると全クエリがスロークエリログに記録されます。動的パラメータなので再起動は不要です。

- 罠: DB インスタンス側のパラメータグループは、クラスタ側の同名パラメータを**上書き**します。クラスタ側だけ変えて「あれ、効かない」となりがちなので、実際にどちらが効いているかを先に確認します
- ログ量は跳ねますが、課金はバイト量ベースです。実測では全クエリ化しても数 MB/分、30分の窓で約 80MB（ログ取り込み費用は数十円）でした。件数の見た目に驚いてコストを過大に見積もる必要はありません
- 時間を区切って必ず元に戻します（今回は30分。戻し忘れ防止に、有効化と同時に自動復帰のタイマーまで仕込んでおくのが安全です）

**整形**: 30分で約21万エントリ、本番アプリ由来に絞って約6万クエリ。リテラル（数値・文字列）を正規化してフィンガープリント化すると **610 形状**まで圧縮できました。リプレイはこの形状単位で代表クエリを流します。

**リプレイと突合**:

- SELECT 378 形状 — クローンA / B に同一実行し、**行数 + 結果チェックサム + 実行時間**を突合
- 書き込み系 106 形状 — 実行はせず `EXPLAIN` の受理可否を両面で比較（構文・実行計画レベルの互換性確認）

結果は、完全一致 373。差分 1 件は `SELECT VERSION()`（当然の差分で、むしろリプレイの配線が正しい証拠）。残り 4 件は旧バージョンでも失敗する元々不正なクエリで、両面同一挙動でした。性能も総実行時間比 0.97 で劣化なし。書き込み側の EXPLAIN 差分もゼロ。ここまで揃って初めて「アップグレードのアプリ互換リスクはほぼない」と実測で言い切れます。

余談ですが、この全量キャプチャは思わぬ副産物を生みます。普段は閾値以下で見えないクエリが全部見えるので、性能改善のヒントの宝庫です。実際、このとき取ったログの分析から集計バッチのロック競合を発見して、別記事になりました: [集計バッチが本番の書き込みを止めていた — INSERT...SELECT と分離レベルの意外な関係](https://zenn.dev/fixu/articles/insert-select-lock-read-committed)

実務メモをひとつ。リプレイのような長時間処理は、実行環境が途中で失われても再開できる作りにしておくと安全です（処理済みの結果を定期的に外部ストレージへ退避し、再実行時は処理済み分を読み飛ばす）。今回も一度実行環境の都合で処理が中断しましたが、この作りにしていたおかげで数分で再開できました。

> 学び: 「本番で流れている SQL」以上に信頼できるテストケースはない。キャプチャ（30分）→ 形状圧縮 → 2面リプレイ → チェックサム突合で、互換性の議論を実測に変えられる。

## 5. 本番実行 — 切断ゼロの3分間

検証が全グリーンでも、実施日時の設計は人間の仕事です。考慮したのは2点。

1. **月末月初を避ける** — 課金・集計系のバッチが集中する期間は、長時間トランザクションによって ZDP が通常再起動へフォールバックするリスクが上がり、万一の際の業務影響も最大になる
2. **深夜の低負荷帯を選ぶ** — キャプチャの解析で数十秒級の重量クエリが日中に定期実行されていると分かっていたため、その非実行帯に寄せる

当日の手順はこうなります。

```bash
# 1. 実行中の長時間クエリがないことを確認（SQL）
SELECT COUNT(*) FROM information_schema.processlist
WHERE command <> 'Sleep' AND time > 5;

# 2. 手動スナップショット（ロールバック保険）
aws rds create-db-cluster-snapshot \
  --db-cluster-identifier <本番クラスタ> \
  --db-cluster-snapshot-identifier pre-3105-YYYYMMDD

# 3. アップグレード実行
aws rds modify-db-cluster \
  --db-cluster-identifier <本番クラスタ> \
  --engine-version 8.0.mysql_aurora.3.10.5 \
  --apply-immediately
```

実測タイムライン（RDS イベントより）:

```
00:24:38 アップグレード開始（クラスタはオンライン維持）
00:25:13 オンラインプリチェック開始 → 2秒で完了
00:26:34 ZDP 適用開始
00:27:05 ZDP 完了 — 0 connections dropped
00:27:14 全体完了（所要 2分36秒）
```

リハーサルどおり ZDP が効き、切断されたコネクションはゼロでした。面白いのはアクセスログ側で、ZDP 実行中に到達したリクエストが**約10秒待たされた後に 200 で成功**していました。接続を切るのではなく、待たせて通す——これが ZDP の挙動です。

事後確認は、DB バージョン・接続性の確認に加えて、全サービスの 5xx とアプリケーションログの DB 系エラーを横断チェックします。問題なしを確認したら、事前告知していた Slack スレッドに完了報告を投げて終了。検証用のクローン2面と作業用の一時権限は撤収し、スナップショットだけ保険として残します。

> 学び: 検証で「リスクほぼゼロ」でも、実施日時の設計（バッチ回避・低負荷帯）だけは省略しない。ZDP は万能ではなく「効く条件を人間が整える」機能。

## 6. 一連の作業を AI に実行させるプロンプト

ここまでの作業——調査、クローン構築、キャプチャ&リプレイ基盤の自作、本番実行、事後確認——は、ほぼ全てを AI エージェント（Claude Code）が実行しました。人間がやったのは方針の決定と各段階の GO 判断です。使ったプロンプトを汎用化して載せます。

ポイントは**1つの巨大プロンプトにしない**ことです。「準備」と「実行」を分離し、本番に触る操作は段階ごとに承認を挟みます。

**① 初動 — 通知を渡す（実行はさせない）**

```
以下の対応準備を進めてください。まだ実行はしないで！

[AWS Health 通知の全文を貼る]

- 影響を受けるリソースの棚卸し（読み取り専用の調査のみ）
- 対応計画の立案と、管理チケットの起票案の作成
```

「まだ実行はしないで」の一言で、AI は調査・計画立案・起票案までで止まります。ここで単一クラスタ同居や binlog 制約のような「方式を決める事実」が出揃います。

**② 検証の設計を出させて、順に GO**

```
検証に必要な手順は？本番実行されている SQL をキャプチャ&リプレイできる？
```

提案（クローン2面・キャプチャ手段・リプレイ方式・コスト見積もり）を確認したら、操作単位で承認します。

```
OK、クローン2面の作成をお願いします
```

```
キャプチャ GO。ただし本番パラメータ変更は時間限定で、自動復帰まで仕込むこと
```

途中で方針を変えるのも会話一往復です。今回はキャプチャ中に「ログ件数がすごいがコストは大丈夫か」と聞き、実測レート（数 MB/分）を出させた上で窓を60分から30分に縮めました。

**③ 本番実行 — 検証全グリーンを確認してから**

```
リリースを実行してください。
手順: Slack 事前告知 → 実行中の長時間クエリ確認 → 手動スナップショット
→ アップグレード実行 → 全サービスヘルスチェック → 完了報告 → 検証リソース撤収
```

実行後のヘルスチェックで想定外の兆候（今回は特定パスの 5xx）が見えたときも、AI がアクセスログを遡って「アップグレード前から存在する既存挙動」とエビデンス付きで切り分けてくれました。「異常っぽいものが出たら、まず時系列でアップグレード起因かを切り分ける」ことを事後確認の手順に含めておくのがおすすめです。

**人間が握るべき判断は3つ**でした。

1. **実施日時の決定** — バッチや業務カレンダーとの兼ね合いは AI に決めさせない
2. **本番状態を変える操作の GO** — キャプチャのパラメータ変更・アップグレード実行は都度承認
3. **費用対効果の判断** — コスト実測値を出させた上での窓の短縮判断など、「どこまでやるか」は人間が決める

逆に、クローン構築・リプレイ基盤の自作・数百クエリの突合・イベントログの解釈といった「手数が多く正確性が要る作業」は AI の独壇場です。通知当日に検証まで終わる速度は、人手では出せませんでした。

> 学び: AI に任せるのは「手数と正確性」、人間が握るのは「日時・GO・費用対効果」。準備と実行をプロンプトで分離すると、この役割分担が自然に固定される。

## まとめ

Aurora MySQL の EoS 通知対応を、実測ベースの手順に落とすとこうなります。

1. **通知当日にクローンを確保する**（新規作成ブロック開始日が実質の期限）
2. **制約の棚卸しで方式を決める**（binlog OFF → Blue/Green 不可 → インプレース + ZDP）
3. **クローン2面**（据置 / 新版）でリハーサルし、所要時間と ZDP 適用可否を実測する
4. **本番 SQL を30分だけ全量キャプチャ**し、形状圧縮 → 2面リプレイ → チェックサム突合で互換性を実測に変える
5. **深夜低負荷帯にインプレース実行**（長時間クエリ確認 → スナップショット → 実行 → 横断ヘルスチェック）
6. 一連を AI に任せ、人間は**日時・GO・費用対効果**だけを判断する

結果、通知から2日後（木曜通知 → 土曜未明）、切断ゼロ・所要2分36秒で本番アップグレードが完了しました。8/31 に日時を選べない形で来るはずだったダウンタイムを、自分たちで選んだ深夜の3分間に変換できたこと——それがこの対応の価値だと思っています。

EoS 通知が届いたら、まず「検証環境を確保できる期限」を確認するところから始めてみてください。
