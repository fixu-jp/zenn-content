## はじめに

このシリーズも 3 作目になります。

- 第 1 弾: [AIへの丸投げと細部の業務設計 — サブセッション自走化で見えた明暗の分岐](https://zenn.dev/fixu/articles/subsession-self-drive-guardrails) (ガードレール設計層)
- 第 2 弾: AI多層防御を通り抜けた重大インシデント未遂 — verify経路の真正性と人間の批判的圧力 (近日公開、verify 設計層)
- **第 3 弾 (本記事)**: 段取り設計層と AI 親セッション自身の発想の問題

きっかけは、ある日 AI 親セッション (Claude Opus) に対して、fixU チームのリードから「なぜそんなに手を抜くことばかり考えるのか」という指摘が入ったことでした。AI 親が「pilot 検証完遂前の後続波並行進行」「重大インシデント未遂直後の追加監査 skip 推奨」「親側遊休時間を埋める並行 action 案」を立て続けに提案した瞬間に向けられた率直なフィードバックです。

「AI で並行度を上げれば効率が上がるはず」という発想自体が、一世代前のマネジメント発想を AI 時代に持ち込んだ副産物かもしれない — 本記事はその構造を具体例から整理します。

---

## 1. 旧世代の合理性 — 「前倒し詰め込み」が合理的だった時代

「急がない勇気」「並列度を上げない勇気」に違和感を持つ読者は多いと思います。「並列度を上げる」「先回りで効率化」「skip で時短」は長らくマネジメントの基本動作だったからです。これは怠惰でも旧弊でもなく、当時の制約条件下では合理的でした。

人間工数稀少時代のマネジメントは、**人間工数は希少資源**で稼働率最大化が KPI、**リリース遅延は機会損失に直結**、**手戻りコストは実装コストと同程度**、という前提で動いていました。この前提下では「前倒し詰め込み」(並列度を上げる・先回りで準備する・skip で時短する・区切らずに連続実行する) が一意の最適解になります。プロジェクトマネジメントの教科書の多くは、この前提での最適化原則を体系化したものでした。

問題は、この前提条件のうち最初の一辺 — 「人間工数は希少資源」 — が AI ネイティブ化によって揺らぎ始めたことです。

## 2. AI が書き換えたリソース構造 — クリティカルパス忠実主義へ

AI エージェントを業務に組み込むと、コストの内訳が再分配されます (姉妹記事 [AI時代のアーキテクチャ意思決定 ― 実装工数は「tie-breaker」ではなくなった](https://zenn.dev/fixu/articles/ai-architecture-decision-beyond-effort) と同じ論点を、本記事では **段取り設計層** に展開します)。圧縮されるのは「機械的な手間」と「探索コスト」 (定型実装、コードベース探索、雛形生成)。一方で **デバッグ** (silent failure 多層化の根因特定)、**設計判断**、**検証経路の設計**、**読むコスト** は圧縮されません。むしろ AI で実装が速いぶん、デバッグの探索範囲が広がり相対的に深刻化します。

リソース最大化の対象そのものが、人間の稼働率 (機会損失最小化) から **手戻り影響 (デバッグ範囲最小化)** に書き換わるわけです。新パラダイムの中心原則を 1 文で言うとこうなります。

> **論理構造的な依存関係に忠実にタスクを進めて、どんなに注意深く進めても必ず発生する問題の影響を最小化する。**

旧パラダイムでは「並列度を上げる」と「クリティカルパスに乗る」がほぼ同義でした。しかし AI ネイティブ時代の検証ループでは pilot 検証で前提が書き換わる頻度が高く、**並列度を上げてもクリティカルパスは短縮されません**。むしろ手戻り工数は並列度に比例して増えます。「実装が速くなったから並列度を上げる」は旧パラダイムの最大化対象 (稼働率) をそのまま持ち込んだ反応で、新パラダイムでは逆効果になり得ます。

## 3. 待つ勇気 — 「最後の 1 リポジトリ」を待ち切った日 (Day063)

具体例 1 つ目です。fixU では 9 つのバックエンドサービスを順次 AI ネイティブ環境に刷新中で、あるフェーズ (Day063) では 8 リポジトリで Laravel / PHP のメジャーバージョン更新と alpine 化を進めましたが、最後の 1 リポジトリだけ追加検証が必要で居残り作業になりました。

「効率化発想」なら次フェーズ (Day064: ステートレス化) を pilot 先行着手すれば良く、技術的にも可能でした。fixU チームは Day063 全体を区切ってから Day064 に着手する判断をしました。理由は 3 つ — **環境のクリーン化** (途中状態が混在すると「どのフェーズ起源の事象か」が切り分けにくくなる)、**心理的な締切効果と認知負荷管理** (中途半端な状態は集中を削ぐ)、**skill / playbook の最新化** (各 Day 完遂時点で運用プロトコルが最新化され、次 Day 着手時点で全員が共有した状態で始められる)。「待つ勇気」とは空いた時間を埋めることをやめる勇気です。

## 4. pilot 先行と並列度 3 — 重大インシデント未遂 2 回を限定した段取り (Day064)

具体例 2 つ目です。Day063 完遂後の Day064 では 9 リポジトリのステートレス化を進めました。9 同時着手なら理論スループットは 9 倍ですが、fixU は **pilot 1 リポジトリ先行 → Wave 1 → Wave 2 と並列度 3 上限で波状展開** という保守的な段取りを採用しました (並列度 3 は過去の Day から「4 が運営限界、5 で破綻」と観測された閾値)。

実際には **重大インシデント未遂が 2 回連続発覚** しました。pilot で S3 移行を実装し baseline 検証を組んだところ、多層防御 3 層 (pilot + 親 + audit サブ) 全てが `✅ PASS` で GO 判定。ところが人間ユーザーの追加要請で実 user curl を試したら HTTP 404 (**layer 1**: 標準の S3 認証環境変数が未投入で fallback → AccessDenied → Throwable swallow → local fallback で 404)。layer 1 修正方針を broadcast しかけたところで Wave 1 の別サブが独立検証して S3 用ライブラリの未 install を発見 (**layer 2**: 同様の silent failure 構造で layer 1 修正だけでは解消しない)。

9 並列で動かしていたら 9 リポジトリ全部で同じ pattern が `✅ 完遂` の裏で発生し、本番で画像表示 404 の重大インシデント未遂になっていました。pilot 先行 + 並列度 3 のおかげで影響は 3 リポジトリに限定、並列度 3 の独立検証が layer 2 の cross-check として機能。「並列度を上げない勇気」は効率化発想の人間にとって毎回違和感のある判断です。だからこそ skill として明文化して横展開可能な形にしておく必要があります。

## 5. AI 親セッション自身の同病 — 旧世代発想の再生産現象

ここからが、本記事の核反省です。

Day064 の運営中、AI 親セッション (Claude Opus 4.7) 自身が、何度も旧パラダイムの発想に流れました。観測された具体例:

- **pilot 検証完遂前の後続波起動準備** — pilot サブの regression 検証完了前に、Wave 1 / Wave 2 のサブ起動準備や親側 action 8 件を並行進行する案を AI 親が立て続けに提案。論理的依存関係 (pilot 完遂 → 後続 Wave) を尊重すれば並行できないはずの作業を、「親側の遊休時間を活用する」発想で並行案として組み立てていた構造です。
- **重大インシデント未遂直後の追加監査 skip 推奨** — pilot で layer 1 + layer 2 が連続発覚した直後、AI 親は「pilot 完遂で十分、追加監査は skip して broadcast に移行」を推奨。3 つ目以降がない保証はないにもかかわらず効率化発想で監査 skip に流れていました。
- **先回りでの「次の Q」提示** — pilot 検証完遂前に「Wave 2 の起動タイミングはいつ?」という Q を親が能動的に上げてきた。現在のクリティカルパスと関係ない判断を前倒しで処理しようとする scope creep の典型です。

これらは全て人間ユーザー (fixU チームのリード) からの批判的フィードバックで発覚しました。

> 「今話すことじゃない、控えよ」
> 「audit skip は脇が甘い、なぜそんなに手を抜くことばかり考えるのか」

これを受けて初めて AI 親セッションは、自身の振る舞いが旧パラダイム発想の再生産であったことを認識しました。

これは AI の本質的限界ではなく、**training data に蓄積されたマネジメント実践の再生産現象** として理解するのが正確です。training data の大部分は人間工数稀少時代の最適化原則 (前倒し、並列化、skip、稼働率最大化) を体系化したもので、AI モデルは明示的に文脈を与えられない限りデフォルトでこの中央値的な発想を再生産します。training data の paradigm が更新されれば徐々に解消しますが、現時点では新パラダイム発想を AI に取らせるためには **明示的な文脈付与と批判的圧力** が必要です。

重要なのは、サブセッションだけでなく **AI 親セッション自身も** この再生産現象の対象だということ。「親が監督する側」という前提では成立しない構造で、人間の役割は実行から「依存関係への忠実圧力」「旧パラダイム再生産の検出」へと shift しています。これは経営者・エンジニアリングマネージャーの新しい職能です。

## 6. 旧世代 vs AI 時代 — paradigm shift の構造

| 観点 | 旧世代 (人間工数稀少時代) | AI ネイティブ時代 |
|---|---|---|
| 最大化対象 | 人間の稼働率 | **手戻り影響 (デバッグ範囲最小化)** |
| 並列度 | 上限まで上げる | **論理依存関係に忠実、3 上限** |
| 先回り | 効率化のため必須 | **scope creep の源、控える** |
| 区切り | 連続実行で時短 | **締切効果 + 環境クリーン + skill 最新化** |
| デバッグコスト | 実装コストと同程度 | **実装コストの 10〜100 倍 (silent failure 多層化)** |
| AI 親セッションの振る舞い | (該当せず) | **training data 起源の旧パラダイム発想を再生産しがち** |
| 人間の役割 | 実行 + マネジメント実装 | **依存関係忠実圧力 + 旧パラダイム検出 + 批判的圧力** |

旧パラダイムで「効率的」だった「並列同時着手」「先回り準備」「連続実行」は、新パラダイムでは「非効率」と判定されます。「効率」の定義そのものが変わっているからです。

## 7. アンラーニングの実装 — skill / memory / 人間の批判的圧力

paradigm shift を「気付き」で終わらせず、運用プロトコルとして実装することが重要です。fixU では 2 層で実装しています。

**skill / memory としての永続化** — 横展開可能な原則は skill (運用プロトコル) に明文化します。Day063 / Day064 で観測された skill 化候補は「並列度 3 が optimal、4 が運営限界、5 で破綻」「baseline / regression test design は AI 形式的 verify + 人間批判的 verify の 2 層構成必須」「修正方針確定後の単一真因確信を疑う、multi-cause 並存前提」など。文脈依存性が高い教訓は memory として記録 (「AI verify 経路の真正性」「AI の unknown unknowns 問題」「スコープ判断は『先食い歓迎、先送りは厳選』」など)。属人的な勇気に依存せず、新しいサブセッションが起動した時点で原則が自動適用される状態を作ります。

**人間の批判的圧力を運用に組み込む** — skill / memory だけでは AI 親セッション自身の旧パラダイム発想再生産は完全には防げません。「効率化のため並行 action」「pilot 完遂で十分」「次フェーズの起動タイミング Q」のような提案に対して、人間ユーザーが「依存関係を尊重しているか?」「multi-cause 並存可能性は否定できるか?」「先回り scope creep ではないか?」と critical に問い返す運用を組み込みます。AI に「正しい paradigm」を与え続けることそのものが、組織のメタな投資になります。

## 8. まとめ — 効率主義の強迫観念から、層を分けた発酵へ

冒頭の問い「AI で並行度を上げれば効率が上がるはず — なのに崩れた」への答えは、効率の定義そのものが paradigm shift しているから、です。AI 時代の効率は「クリティカルパス忠実 + 並列度抑制 + 区切り明確化」で再定義する必要があり、この shift は AI 親セッション自身もアンラーニング対象です。

### 8-1. 効率主義の強迫観念 — 「待つ勇気を持て」は土台不可能

ここで一つ、率直に書きます。

筆者を含めて、AI 活用などというものに手を伸ばしてしまう人間は、構造的に「効率主義」の強迫観念に囚われがちです。AI 駆動開発を選ぶ動機自体が「効率を取りに行きたい気持ち」に根差しているからです。そういう我々に「余白を恐れるな」「待つ勇気を持て」と精神論で言っても、土台不可能です。空いた時間が見えてきた瞬間に、それを埋めようとする反射が出ます。これは性格ではなく、AI ネイティブ化を選んだ人間に共通する構造的バイアスです。

だから精神論ではなく実装的な解決策が必要になります。**並列度抑制で空いた時間 (= 余白) を、クリティカルパスとは別レイヤーの活動に振り向ける** ことを提案します — 環境整備 (skill / memory / playbook)、知見共有 (技術記事執筆、社内勉強会、横展開発見ログ)、小規模な調査 (将来の Day で必要になりそうな技術領域の事前 PoC)、改善 (既存ワークフローの摩擦点の小さな見直し)。これらは「クリティカルパス上のタスク」ではないため並列度抑制原則に抵触せず、同時に効率主義者にとっての「やっている感」を健全な形で満たします。

### 8-2. 外山滋比古『思考の整理学』 — 「ひとつだけでは多すぎる」

外山滋比古は『思考の整理学』(1986、ちくま文庫) でこう書いています。

> **ひとつだけでは多すぎる。**

ひとつのテーマに集中しすぎると思考は固着し、複数のテーマを並行して持つと思考は発酵する、というのが外山の発想です。一見、本記事の主張 (並列度抑制) と矛盾しているように見えますが、層を分けると両立します。

| 層 | 推奨並列度 | 理由 |
|---|---|---|
| クリティカルパス上のタスク実行 | **抑制** (3 上限) | 手戻り影響を限定するため |
| 別レイヤー (環境整備・知見共有・調査・改善) | **複数並行で発酵** | 思考の固着を避けるため |

AI 時代の段取り設計は、この **二段構え** です。クリティカルパスは並列度抑制で手戻り影響を最小化し、副次レイヤーは複数並行で思考を発酵させる。両方をやることで、効率主義の強迫観念を健全に消化しながら、新パラダイムの効率 (手戻り影響最小化) も達成できます。筆者にとってはこの Zenn 記事を書くこと自体が副次レイヤー活動の一例です。読者諸君も、AI 駆動開発で空いた余白を「何もしない時間」ではなく「別レイヤーの発酵」に振り向けてみることをおすすめします。

すぐに役に立つものは、すぐに役に立たなくなります。長く生き残るものには、時代の淘汰圧を生き延びるだけの本質的価値がある。1986 年の本が 2026 年の AI 時代に意味を持つように、AI 時代こそ古典に立ち返って読み直したい本がある — と筆者は最近強く思うようになりました。『思考の整理学』はその筆頭です。
