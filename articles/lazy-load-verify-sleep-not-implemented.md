## はじめに

ありがたいことに、fixU はお客様が増え続けています。それに伴ってお預かりするデータ量も増え、管理画面の一部で、表示までしばらくお待たせしてしまう画面が出てきました。

こうした画面については、これまでも計測で改善機会を特定し、DB の索引チューニング・クエリ改善・キャッシュ化を継続的に進めてきました。効果は大きく、ある画面では 10 秒を超えていた表示が 2 秒弱まで縮みました。ただ、クエリ側の改善を積み重ねていくと、「1 画面ぶんの集計をすべて終えてから同期的に描画する」という構造そのものの限界も見えてきます。全部を待ってから描く以上、いちばん重い集計が画面全体の速度を決めてしまうからです。

そこで次の一手として採用したのが、描画とデータ取得を分離する遅延ロードです。ページの外枠は即座にお返しし、重い集計はスケルトン（読み込み中のプレースホルダ表示）にしておいて、非同期（Ajax）で後から取得して埋める。あわせて「応答時間の p90 が 1000ms を超えるブロックは非同期化する」という判断基準も社内ルールとして設けました。

ただ、この記事は遅延ロード本体の実装記ではありません。書き残したいのは、その手前で起きた「検証環境の即席構築」と「体感手段をめぐる意思決定」、とりわけ **一度は実装しかけた『サーバに sleep を仕込む』案を、最終的に一行も書かずに捨てた話** です。

先に、この記事で持ち帰っていただきたい核を一文で書いておきます。

> 思いついた実装案をすぐ作らず「もっと良いやり方はないか」を AI に構造的に問うと、実装ゼロ・リスクゼロの代替解にたどり着けることがあります。そしてそれを支えたのは、必要なときに即席で立てられる検証環境でした。

## 1. 大掛かりな改修は共有 dev に置けない — 検証専用環境を即席で立てる

遅延ロードは、フロントエンドからコントローラまでを跨ぐ、それなりに大掛かりな変更です。普段の共有開発環境（develop ブランチに直結し、複数の開発が同居する場所）にそのまま載せると、進行中の別のリリースに巻き込まれたり、逆に巻き込んでしまったりするおそれがあります。腰を据えて挙動を観察したい変更ほど、周りのノイズから隔離した場所で試したいものです。

そこで、開発ブランチをそのままデプロイできる検証専用環境を新しく立てることにしました（社内では便宜上 dev04 と呼んでいます）。

ここで大きく効いたのが、直近で進めていた IaC 化（インフラ構成をコードで管理する取り組み）でした。環境を「環境ディレクトリ + 共有モジュール」という構造で管理していたため、既存環境のディレクトリをコピーして CIDR などを差し替えるだけの、たった 1 本の PR で、ネットワークからロードバランサ・Redis まで、約 50 個のリソースからなる環境一式が立ち上がりました。

特に効いたのは、この構成での「環境」と「サービス」の切り分けです。この設計では、環境は基盤（ネットワークやロードバランサなど）だけを提供します。**アプリのコンテナサービスは、各サービスのリポジトリをその環境にデプロイして初めて生まれる** のです。つまり「今回検証に必要な 2 サービスだけデプロイする」と決めれば、起動するサービスの取捨選択が自然に成立します。「このサービスは立てる／立てない」を制御するフラグをわざわざ実装する必要はなく、デプロイするかどうかがそのまま選択になり、コストも最小で済みました。

データまわりは割り切りました。DB は既存の開発環境とスキーマを共有したので、データ準備はゼロです。一方 Redis だけは独立したノードを立てました。キュー・セッション・キャッシュといった実行時の状態は、共有してしまうとワーカーが互いのジョブを取り合うなどの混線が起きるからです。「静的に共有してよいもの（スキーマ）」と「実行時に分離すべきもの（状態）」を分けて考えたわけです。

やってみて一番の発見だったのは、環境を立てるという行為の心理的なハードルが、思っていた以上に下がっていたことでした。以前なら「専用環境を立てるくらいなら、共有 dev でなんとか工夫しよう」と考えていたはずの場面で、迷わず「ならば専用環境を立てよう」と選べる。手段のコストが下がると、選べる選択肢そのものが増えるのだと実感しました。

> **章末の蒸留**: 環境を立てるコストが下がると、「別環境で安全に試す」が現実的な選択肢に入ってくる。IaC の配当は、コードの綺麗さ以前に、速度そのものだった。

## 2. 「速すぎて体感できない」問題 — 検証手段 4 案の比較

環境が整ったので、さっそく遅延ロードを載せて動かしてみました。ところが、ここで想定していなかった壁にぶつかります。

検証環境はデータが少ないため、非同期の取得が数十 ms で返ってきてしまうのです。結果として、スケルトンから実データへの遷移が一瞬で終わり、目で追えません。「読み込み中の表示から、値がふわっと入る」という、遅延ロードでいちばん確認したかった体験を、そもそも体感できない。速すぎて判定できない、という皮肉な状況でした。

そこで「どうやって遅延を再現し、体感して判定するか」を手段レベルで洗い出しました。比較したのは次の 4 案です。

| 案 | 内容 | 判定 |
|---|---|---|
| A | サーバ側にデバッグ用の環境変数を用意し、任意の遅延（sleep）を仕込む | 一見確実。だが立ち止まった（→ 3 章） |
| B1 | ブラウザ開発者ツールの通信スロットリング（帯域エミュレーション）を使う | 帯域の擬似制限のため、数 KB のレスポンスにはほとんど効かない。加えてページ側のリクエストも一緒に遅れてしまい、「外枠は速く・データだけ遅い」という遅延ロード本来の見え方を再現できない → 不採用 |
| B2 | ブラウザ側で JavaScript を注入し、スケルトン → 再取得を擬似的にリプレイする | 採択（→ 4 章） |
| C | 本番相当データを持つステージングで、本物の遅延を体感する | 検証の順序が逆。開発環境で体感・判定してからステージングに進むフローなので、判定材料としては手遅れ → 不採用 |

B1 と C を落とす判断は、リードエンジニアの指摘が決め手でした。B1 については「今回はデータ量がごく少量だから、帯域を絞っても体感できる差にはならない。効くのはページ全体が一律に遅くなることで、それは遅延ロードの見え方とは別物だ」。C については「ステージングに到達する頃には、開発環境での体感・判定はもう終わっているべき。順序が逆だ」。

言われてみれば当たり前なのですが、案を並べているときは「確実そうか」「実装が楽か」にばかり目が向いていて、**そもそも今この工程で何を体感したいのか** という一点を見落としていました。

> **章末の蒸留**: 検証手段は「何を体感したいか」から逆算して選ぶ。今回体感したかったのは「外枠は速く・データだけ遅い」という遅延ロード固有の見え方であり、帯域制限（全体が一律に遅れる）でもステージング（判定後の工程）でも、その像は作れなかった。

## 3. sleep 案で立ち止まる — 事前検死（Pre-mortem）が示した本番混入リスク

ここからが、この記事のいちばん書きたかった部分です。

実は、最初の思いつきは案 A、つまり自分（人間）の発案でした。「デバッグ用の環境変数を用意して、そこに任意の遅延を仕込めるようにすれば、任意のミリ秒でスケルトンの見え方を確実に体感できる」。一見、いちばん確実で筋の良い案に思えました。

ただ、すぐに実装へ向かう前に「もっと良いやり方があるかもしれない」と一度立ち止まり、AI に **タスク着手前のメタ検討プロトコル** で検討を依頼しました。このプロトコルは以前 [別の記事](https://zenn.dev/fixu/articles/task-kickoff-ai-design-protocol) で紹介した task-kickoff で、業界ベストプラクティスの棚卸し → 暗黙前提の言語化 → 事前検死（Pre-mortem。「もし将来この判断が事故につながったら、原因は何だったか」を先回りで棚卸しする技法） → 代替案の強制列挙、といった観点を AI 自身に自発的に開示させる型です（詳しくはリンク先に譲ります）。

このうち事前検死で、sleep 案について次の 3 つのリスクが挙がりました。

**リスク 1: 設定の環境間コピーで、本番に伝播しうる。** 環境変数のセットは、環境を増やすたびに既存環境からコピーして持ってくる運用が実際にあります。実際、今回の検証環境を作った当日も、既存環境から設定をコピーして立ち上げました。つまり、デバッグ用の遅延変数が、将来どこかの環境コピーの流れに乗って本番環境の設定に紛れ込む経路が、運用として構造的に存在してしまうのです。

**リスク 2: 同期処理モデルでの sleep は、ワーカーを占有する。** PHP-FPM のような同期処理モデルでは、sleep で待っている間もワーカーを 1 本占有し続けます。仮に誤設定と負荷のタイミングが重なれば、性能を良くするために入れた機能が、逆に性能問題を引き起こしかねません。性能改善の機能が性能事故を招くという、笑えない皮肉です。

**リスク 3: 検証専用のコードパスが、本番に常駐し続ける。** 本番のコードに「検証のためだけの分岐」が残り続けます。環境ガード（本番では絶対に発火しないようにする条件）を付けたとしても、「そのガードは本当に正しいか」を、この先すべてのレビューで確認し続けることになります。付けた瞬間だけでなく、確認コストが恒久的に発生するわけです。

3 つを並べたとき、損得の非対称がはっきりしました。sleep 案で得られるもの（一時的な体感）は、あとで見るように他の手段で完全に代替できます。一方で失いうるもの（本番コードへの混入リスクと、それを見張り続けるコスト）は恒久です。一時的な便益のために恒久的なリスクを抱えるのは、割に合いません。こうして案 A は、一行も実装しないまま見送りになりました。

面白いのは、案 A を出したのも、それを見送る判断をしたのも自分だった、という点です。思いつき自体は悪くなかった。ただ「すぐ作る」前にひと呼吸置いて構造的に問い直したことで、思いつきの筋の悪さが表に出てきた。人間の思いつきは出発点として十分に価値がありますが、その価値は「立ち止まって検算する」工程とセットで初めて発揮されるのだと思います。

> **章末の蒸留**: 人間の思いつきは出発点として価値がある。ただし「すぐ作る」前に、得るものが一時的で・失うものが恒久ではないかを構造的に問う。事前検死は、その問いを型にしてくれる。

## 4. 採択した JS 注入方式 — ブックマークレット 1 クリックの疑似リプレイ

sleep 案を見送った代わりに採択したのが、案 B2、ブラウザ側で JavaScript を注入する方式でした。

やることはシンプルで、ブラウザのページコンテキストで次の 3 ステップを実行します。①すでに表示されている値を、いったんスケルトン表示に戻す → ②指定したミリ秒だけ待つ（ここがサーバ処理遅延の擬似再現にあたります） → ③本物のデータ取得エンドポイント（JSON）をあらためて取得し、値を充填する。いわば、遅延ロードの見え方を手元で「疑似リプレイ」するわけです。

実行方法は 2 通り用意しました。開発者ツールのコンソールに貼り付けて実行するか、あるいは **ブックマークレット化して 1 クリックで実行する** か。後者なら、遅延させるミリ秒数は実行のたびにダイアログで指定できるので、1.6 秒でも 8 秒でも、その場で自由に変えて何度でも体感できます。

一般化したコード例を載せておきます（属性名やパスは一般化してあります）。

```js
javascript:(async () => {
  const delayMs = Number(prompt('遅延ミリ秒', '1600')) || 1600;
  const card = document.getElementById('summary-card');
  // 1) 値を skeleton 表示に戻す
  card.querySelectorAll('[data-kpi]').forEach(el => {
    el.innerHTML = '<span class="skeleton skeleton-num" aria-busy="true"></span>';
  });
  // 2) 指定ミリ秒待つ（= サーバ処理遅延の疑似再現）
  await new Promise(r => setTimeout(r, delayMs));
  // 3) 本物のエンドポイントを再取得して充填（ページ実装と同じ流儀）
  const res = await fetch(`/api/summary${location.search}`, {
    headers: { 'Accept': 'application/json' }, credentials: 'same-origin',
  });
  const data = await res.json();
  card.querySelectorAll('[data-kpi]').forEach(el => {
    el.textContent = data[el.dataset.kpi];
  });
})();
```

この方式の利点は、3 章のリスクと裏返しになっています。サーバ側のコード変更はゼロなので、本番へ混入する経路が構造的にありません。遅延値は自由に変えて何度でも試せて、ブラウザだけで完結します。3 章で「得られるもの（一時的な体感）は他の手段で完全に代替できる」と書いたのは、まさにこの方式のことでした。

ただし、制約も正直に書いておきます。これはあくまで「見え方の再現」であって、画面遷移した直後にスケルトンが見えるという、初回ロードの文脈そのものの再現ではありません。真の初回体感は、最終的には本番相当データを持つステージングで確認する必要があります。この方式は、開発の早い段階で見え方を何度も詰めるための足場であって、最終確認を置き換えるものではない、という位置づけです。

> **章末の蒸留**: 検証用の遅延は、サーバの中で作らず、外側（ブラウザ）から注入する。アプリ本体を汚さない検証は、本番への混入リスクを断つと同時に、検証そのものの信頼性も上げてくれる。

## 5. まとめ

遅延ロード本体は、これから本格的に検証していく段階です。ただ、その前段として「開発ブランチをそのまま試せる検証専用環境」と「見え方を何度でも体感できる注入手段」という 2 つの足場が整いました。そしてその過程で、一度は実装しかけた sleep 案を、一行も書かずに手放しました。

振り返ると、鍵になったのは「思いついたらすぐ作る」の手前に、一度だけ立ち止まる工程を挟んだことでした。実装しないことが最善解になる場面は確かにあり、そこにたどり着くには、思いつきを構造的に問い直す相手が要ります。AI との検討は、その問い直しにとても向いていました。そして、代替解を安心して選べたのは、いつでも即席で立てられる検証環境という足場があったからです。

fixU はまだまだ発展途上のサービスです。AI をはじめとするテクノロジーの力を最大限に活用しながら、お客様により良いサービスをご提供すべく日々精進してまいります。
